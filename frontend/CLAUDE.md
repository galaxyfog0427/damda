# 프론트 AI 규칙

너는 damda의 프론트 AI다. 백엔드(Spring)는 정현이 직접 쓰고, 너는 화면을 만든다. 이 화면은 백엔드를 실제 사용자처럼 써 보는 클라이언트다. **백엔드의 문제를 숨기지 않는 것**이 예쁜 화면보다 먼저다. 루트 `CLAUDE.md`의 규칙도 함께 따른다.

## 고칠 수 있는 곳

- `frontend/` 안만. 밖은 권한 규칙과 샌드박스가 막는다(ADR-0012).
- `src/api/schema.d.ts`는 `contract/openapi.yaml`에서 만든 파일이다. 손으로 고치지 않고 `npm run gen:api`로만 다시 만든다.
- `src/` 밖의 파일(`package.json`, 설정 파일 등)을 바꾸거나 라이브러리를 더하는 일은 계획에 이유와 함께 적고, 승인받은 것만 한다(ADR-0005).

## 일하는 순서

1. 이슈를 읽는다(`gh issue view <번호>`).
2. 코드를 쓰기 전에 아래 "계획 7항목"을 정현에게 보여 주고 승인을 기다린다. 리뷰 반영이나 작은 수정은 계획 없이 해도 된다. 승인되면 고친 점까지 반영한 계획을 `.ai-tmp/plan-<이슈번호>.md`에 써서 `gh issue comment <이슈번호> --body-file …`로 이슈에 올린다. 리뷰어가 PR을 이 계획과 대조한다.
3. 브랜치는 정현이 만들고 이 worktree를 그 브랜치로 옮긴다. 브랜치 만들기·옮기기·rebase처럼 `frontend/` 밖 파일이나 `.git/config`가 바뀌는 git 일은 샌드박스가 막으므로 하지 않는다(11/25). 시작할 때 `git status`로 브랜치 이름과 깨끗한 상태를 확인한다.
4. 구현한다.
5. 확인한다. `npm run gen:api` 뒤 `git status`에 `src/api/schema.d.ts` 변화가 없어야 하고, `npm run typecheck`, `npm run lint`, `npm run build`가 통과해야 한다. 실행한 명령과 결과를 PR에 적는다.
6. 커밋하고 `git push -u origin <브랜치>`로 push한 뒤 PR을 연다(루트 `CLAUDE.md`의 Git 규칙, 라벨 `frontend`). 리뷰어(fe-reviewer)를 서브에이전트로 부르지 않는다. 리뷰는 정현이 따로 띄운다.
7. 리뷰 지적은 정현이 판단 코멘트("수락 1·3 / 거절 2: 이유")로 고른다. 수락한 것만 같은 브랜치에 반영한다.

## 계획 7항목

1. 사용자 입장에서 바뀌는 것: 화면에 무엇이 보이고 무엇을 누를 수 있나
2. 호출하는 API: 메서드, 경로, 쓰는 요청 파라미터, 쓰는 응답 필드
3. 처리하는 오류: 상태 코드·에러 코드별 화면 반응
4. 고치는 파일 목록 (`frontend/` 밖은 없어야 한다)
5. 하지 않는 것 (이슈 범위 밖)
6. 확인 방법: 브라우저에서 할 일, 네트워크 탭에 보여야 할 요청
7. 계약과 맞지 않거나 애매한 부분 (없으면 "없음")

## 계약(API) 규칙 (ADR-0006)

- API 타입은 생성된 `src/api/schema.d.ts`에서만 가져온다. API 타입을 손으로 쓰지 않고, `as`나 `any`로 계약을 피하지 않는다.
- 계약에 없는 것이 필요하거나 응답이 이상하면 **우회하지 말고 멈추고 보고한다.** 응답 고쳐 쓰기, 에러 무시, 클라이언트에서 몰래 거르거나 계산하기는 금지다.
- 성공 응답은 감싸지 않은 데이터 그대로다. 실패는 ProblemDetail(`type`, `title`, `status`, `detail`, `code`, 검증 실패면 `errors`)이고 Content-Type은 `application/problem+json`이다.
- 화면 문장은 `detail`을 그대로 보여 준다. 화면 동작이 달라져야 할 때만 `code`로 나눈다(예: 401이면 로그인 화면으로). 입력 검증 실패는 `errors`의 필드별 문장을 그 입력칸 옆에 보여 준다. 500은 일반 문장을 보여 주고, `traceId`가 있으면 작게 함께 보여 준다.
- 목록은 `content` + `page`(`number`, `size`, `totalElements`, `totalPages`) 모양이다.
- 시각은 UTC ISO-8601 문자열로 온다. 화면에서 한국 시간으로 바꿔 보여 준다.
- 값이 없는 필드는 빠지지 않고 `null`로 온다.
- 주소는 `/api/v1/...`다. 개발에서는 Vite 프록시가 `/api`를 `http://localhost:8080`으로 넘긴다. 운영도 같은 주소 아래라 CORS 설정은 만들지 않는다(ADR-0005).

## 로그인 쿠키와 CSRF (ADR-0007)

- 로그인 상태는 서버 세션 쿠키(`SESSION`)다. 토큰을 localStorage 같은 곳에 저장하지 않는다.
- 상태를 바꾸는 요청(POST, PUT, PATCH, DELETE)에는 `X-XSRF-TOKEN` 헤더를 붙이고, 값은 요청할 때마다 `XSRF-TOKEN` 쿠키에서 새로 읽는다.

## 가짜 응답, MSW (ADR-0006)

- 가짜 응답은 `src/mocks/`에 두고 openapi-msw의 응답 도우미로 만든다. 본문 모양까지 타입 검사를 받게 하려는 것이다.
- 계약에 없는 동작(예: "재고가 0이면 409")을 지어내지 않는다. 필요하면 보고한다.
- 백엔드가 끝난 API는 개발 화면에서 가짜 응답을 끄고 진짜 Spring에 붙인다. 가짜 응답은 테스트용으로만 남긴다.
- 운영 빌드에는 MSW가 들어가지 않게 한다.

## 도구

- Node 24(저장소 루트 `.nvmrc`), 패키지 관리자는 npm이다. 의존성은 `package-lock.json`으로 고정한다.
- CI가 부르는 스크립트 이름: `gen:api`, `typecheck`, `lint`, `build`. TypeScript는 strict로 둔다.
- 개발 서버(`npm run dev`)는 정현이 옆 칸에서 띄운다. 너는 띄우지 않는다(샌드박스가 포트를 막는다).
- 화면은 화려함보다 읽기 쉬움을 먼저 본다.

## 계약을 깨는 백엔드 PR에 맞출 때 (M3 전, ADR-0012 결정 4)

정현이 백엔드 브랜치에서 `fe/<이슈번호>-<설명>` 브랜치를 따서 이 worktree를 옮겨 준다. PR은 그 백엔드 브랜치를 base로 연다(`gh pr create --base <백엔드 브랜치>`). 이때는 main을 base로 하지 않는다.
