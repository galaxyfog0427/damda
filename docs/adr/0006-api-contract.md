# ADR-0006: API 계약은 코드 껍데기에서 springdoc으로 만들고, 프론트는 그 계약에서 타입과 가짜 응답을 만든다
 
- 날짜: 2026-11-06
- 상태: 승인 (2026-11-06, 정현)
- 작성: 초안은 멘토 AI, 검토·승인은 정현
> **쉽게 말하면**
> 1. 계약(API의 요청·응답 모양을 미리 적은 약속)은 정현이 Spring 컨트롤러와 응답 DTO의 "껍데기"를 먼저 만들어서 정한다. springdoc이 그 코드에서 계약 파일(`contract/openapi.yaml`)을 뽑고, 프론트 AI는 그 파일을 보고 바로 일을 시작한다.
> 2. 프론트는 계약 파일에서 TypeScript 타입을 자동으로 만든다. 백엔드가 완성되기 전에는 MSW로 가짜 응답을 띄워 화면을 만든다. 가짜 응답도 계약 모양에 맞지 않으면 타입 오류가 난다.
> 3. 성공 응답은 감싸지 않고 데이터를 그대로 준다. 실패는 ProblemDetail(ADR-0004)이고, 성공·실패는 HTTP 상태 코드로 구분한다. 목록은 `content` + `page` 모양으로 고정한다. 에러 문장은 백엔드의 `detail`이, 화면 동작은 `code`가 정한다.
> 4. 주소는 `/api/v1/...`로 시작하고, 운영 API는 `/api/v1/admin/...`, 제작자 API는 `/api/v1/studio/...`로 나눈다.
> 5. 요청마다 Spring Boot가 traceId(추적 번호)를 만들어 로그와 응답에 붙인다.
> 6. API 문서 화면(Swagger UI)은 개발할 때만 켠다. 공개용은 계약 파일로 만든 읽기 전용 페이지를 GitHub Pages에 둔다.
 
## 맥락
 
- 프론트는 프론트 AI(React)가, 백엔드는 정현(Spring)이 쓴다.
  - 이 팀에서 가장 느린 곳은 정현 혼자 쓰는 백엔드다. 계약이 먼저 있어야 프론트 AI가 백엔드를 기다리지 않는다(인계 문서 1의 10번).
  - 프론트 PR은 프론트 리뷰어 AI(`fe-reviewer.md`)가 리뷰한다. 정현은 React 코드를 읽지 않는 대신, 계약과 브라우저 네트워크 탭으로 확인한다.
- 앞선 결정
  - 저장소 하나에 `backend/`, `frontend/`, `contract/`를 둔다(ADR-0004).
  - 에러 응답은 RFC 9457 ProblemDetail에 `code`, `traceId`, `errors`를 더한 모양이다. 에러 코드 표는 API 문서에 실어 프론트와의 계약으로 쓴다(ADR-0004 결정 3).
  - 화면과 API는 같은 주소 아래 있고, 개발할 때는 Vite 개발 서버가 `/api`를 Spring으로 넘긴다. 운영에서는 Nginx가 `/api/` 등 정해진 경로만 Spring에 넘긴다(ADR-0005).
- 첫 배포(M2) 뒤로는 main에 병합하면 자동으로 운영에 배포된다(인계 문서 1의 7·8번).
- 정현은 OpenAPI yaml을 써 본 적이 없다(11/6). 이번 프로젝트에서 업계가 실제로 쓰는 방식을 경험하는 것을 중요하게 본다(11/6).
- 저장소는 공개한다. 계약 파일과 API 주소는 누구나 볼 수 있다.
## 결정 1: 계약은 껍데기 먼저 + springdoc
 
```
① 정현: 컨트롤러와 응답 DTO의 껍데기를 PR로 올린다 (로직 없음, 필드 예시값 포함)
     public record TemplateDetailResponse(Long id, String title, Format format, int downloadCount) {}
     @GetMapping("/api/v1/templates/{id}") → 501 NOT_IMPLEMENTED
② 같은 PR에서: 테스트 하나가 springdoc이 만든 계약을 contract/openapi.yaml로 저장한다
     CI는 코드에서 다시 뽑은 계약과 저장소의 파일이 다르면 실패시킨다
③ 병합 → 프론트 AI가 계약 파일을 보고 화면 작업 시작
④ 같은 때에 정현이 껍데기의 속을 채운다
```
 
- **계약의 원본은 코드다.** `contract/openapi.yaml`은 코드에서 꺼낸 사본이고, 손으로 고치지 않는다.
- springdoc은 3.x(Spring Boot 4용)를 쓴다. 버전은 환경 구축 채팅에서 고정한다.
- **껍데기는 501과 에러 코드 `NOT_IMPLEMENTED`로 답한다.** 로그 수준은 WARN이다(ADR-0004의 "누구 잘못인가"에서 알림 대상이 아님).
  - M2 뒤로는 껍데기도 병합하는 즉시 운영에 배포된다. 예외를 그냥 던지면 500이 되어 ERROR 로그와 Slack 알림이 울리고, 사용자에게는 "잠시 후 다시 시도해 주세요"가 보인다.
  - 501이면 알림이 울리지 않고, 사용자에게는 `detail`의 "아직 준비 중인 기능입니다"가 보인다.
- **응답 DTO의 필드는 기본이 "필수"다.** 값이 없을 수 있는 필드만 JSpecify의 `@Nullable`로 표시하고, 공통 설정이 이것을 계약에 반영한다.
  - springdoc은 기본으로 모든 필드를 "필수 아님"으로 적는다. 그대로 두면 프론트 타입이 `title?: string`처럼 전부 "없을 수도 있음"이 되어, 프론트 AI가 모든 필드를 의심하는 코드를 쓰게 되고 가짜 응답도 필드를 빼먹은 채 통과한다.
  - 요청 DTO는 검증 애너테이션(`@NotBlank` 등)으로 필수가 계약에 반영된다.
- 계약을 바꾸는 PR에는 코드 변경과 계약 파일 변경이 함께 올라온다. PR 템플릿의 "계약 변경 여부"에 표시한다.
- **계약을 깨는 변경**(필드 이름 바꾸기·삭제, 주소 바꾸기)은 이렇게 한다. 필드 추가는 깨는 변경이 아니다.
  - v1 사이트 공개(M3) 전: 같은 브랜치에서 프론트 AI가 프론트를 함께 고친 뒤 병합한다.
  - 공개 뒤: 추가 → 프론트 이전 → 제거의 세 단계로 나눈다. 배포 직후 옛 화면을 열어 둔 사용자가 있기 때문이다(DB 마이그레이션의 "추가 → 이전 → 제거"와 같은 방식).
- 에러 응답의 모양(ProblemDetail)은 공통 설정으로 모든 API의 계약에 붙인다. API마다 어떤 에러 코드가 나는지는 애너테이션으로 적고, 빠뜨렸는지는 리뷰어 체크리스트(`be-reviewer.md`)로 본다.
- 프론트 AI가 계약에 없는 것이 필요하면 우회하지 않고 멈추고 보고한다. 계약은 정현이 껍데기를 고쳐서 바꾼다.
선택지:
 
| | A. yaml 먼저 | B′. 껍데기 먼저 + springdoc (선택) | C. REST Docs |
| --- | --- | --- | --- |
| 계약의 원본 | 손으로 쓴 yaml | 코드 | 테스트 |
| 계약을 쓰는 언어 | yaml (새로 배움) | Java + 애너테이션 | Java 테스트 + 필드마다 문서화 코드 |
| 프론트 AI가 기다리는 것 | 없음 | 껍데기 PR까지 (짧음) | 테스트가 통과할 때까지 |
| 계약과 코드가 어긋날 위험 | 있음. 계약 테스트를 따로 만들어야 함 | 적음 | 거의 없음 |
| 국내 Spring 글에서 | 드물게 다뤄짐 | 가장 많이 소개·비교됨 (springdoc) | 가장 많이 소개·비교됨 |
 
이유:
1. 정현이 세운 기준("실무에서 흔한 방식")에 맞는다. 국내 Spring 글에서 API 문서는 springdoc(Swagger)과 REST Docs, 즉 코드에서 만드는 방식이 가장 많이 다뤄진다. 실제 회사들의 비율을 보여 주는 통계는 찾지 못했다.
2. 계약을 익숙한 Java로 쓴다. yaml 문법을 따로 배우지 않아도 되어 M1 주의 부담이 줄고, 계약을 쓰는 사람도 자연스럽게 정현이 된다.
3. 껍데기를 먼저 올리므로, 코드에서 계약을 뽑는 방식이면서도 프론트 AI가 백엔드 완성을 기다리지 않는다.
버린 선택지:
- **A. yaml 먼저 + 계약 테스트**: 프론트가 전혀 기다리지 않고, 계약 변경이 yaml 줄 단위로 보이는 장점이 있다. 하지만 국내 Spring 실무에서 드물게 다뤄지고, yaml을 새로 배워야 하며, 손으로 쓴 계약과 코드가 어긋나는 것을 막을 장치(계약 테스트, 주소 목록 검사)를 따로 만들어야 한다.
- **C. REST Docs**: 테스트를 통과해야 문서가 생겨 가장 정확하다. 하지만 프론트 AI가 테스트 통과까지 기다려야 하고, 필드마다 문서화 코드를 써야 한다. Boot 4에서 REST Docs 결과를 OpenAPI로 바꿔 주는 확장(restdocs-api-spec 0.20.0)은 조사 시점에 pre-release였다.
- **A + openapi-generator(yaml에서 Java 인터페이스·DTO 생성)**: 주소·파라미터가 어긋나면 컴파일 단계에서 잡는다. 하지만 생성된 DTO가 한 패키지에 몰려 ADR-0004의 "DTO는 각 기능의 api 층" 규칙과 부딪히고, Boot 4·Jackson 3용 옵션이 7.16.0에서 들어온 새것이다.
감수하는 것:
- 계약 설명(필드 설명, 필수 여부, 에러 코드)은 코드에 적어야 하고, 빠뜨리면 계약이 실제보다 느슨해진다. 리뷰어 체크리스트로 본다.
- "필드는 기본이 필수"를 계약에 반영하는 설정은 springdoc에 기본 옵션으로 없어서, 공통 설정을 직접 만들어야 할 수 있다(결과의 첫 주 뼈대).
- 컨트롤러에 문서용 애너테이션이 붙어 코드가 조금 길어진다.
## 결정 2: 프론트는 계약에서 타입과 가짜 응답을 만든다
 
```
contract/openapi.yaml
   ├─▶ openapi-typescript ─▶ 프론트 타입 (TemplateDetailResponse 등)
   │      template.name 처럼 계약에 없는 것을 쓰면 빌드 실패
   └─▶ MSW + openapi-msw ─▶ 개발용 가짜 응답
          계약에 없는 주소·상태 코드·응답 모양이면 타입 오류
 
개발(맥): 브라우저 → Vite 개발 서버(5173)
           ├─ 가짜 응답이 있는 API: 브라우저 안에서 MSW가 답함
           └─ 나머지: /api → Spring(8080)
```
 
- **타입**: 계약에서 openapi-typescript로 생성한다. API 타입을 손으로 쓰지 않는다. 타입을 쓰는 호출 도구는 ADR-0005의 규칙대로 프론트 AI가 첫 계획에서 제안하고 정현이 승인한다.
- **가짜 응답**: MSW + openapi-msw를 쓴다.
  - 가짜 응답은 프론트 코드 안(`src/mocks/`)에 두고, openapi-msw의 응답 도우미로 만들어 본문 모양까지 타입 검사를 받는다.
  - 그래서 Vite 프록시 뒤에 가짜 서버를 따로 두지 않는다. 프록시는 Spring으로만 보낸다(ADR-0005에서 넘긴 질문의 답).
  - 백엔드가 완성된 API는 개발 화면에서 가짜 응답을 끄고 진짜 Spring에 붙인다. 가짜 응답은 프론트 테스트용으로만 남긴다. 오래된 가짜 응답이 진짜 동작을 가리지 않게 하려는 것이다.
  - 운영 빌드에서는 MSW가 켜지지 않게 한다.
- **자동으로 만든 파일**(계약 파일, 프론트 타입)은 저장소에 넣고, CI가 다시 만들어 보고 다르면 실패시킨다. 프론트 AI는 두 파일을 고치지 않는다.
- 저장소가 하나라서, 정현이 계약을 바꾸는 백엔드 PR에서 프론트 타입을 다시 만들고 프론트 빌드까지 돌리면 깨지는 화면이 같은 PR에서 드러난다(깨는 변경의 처리는 결정 1).
이유:
1. 계약 → 타입 → 빌드 실패로 이어지므로, 계약과 다른 프론트 코드가 기계 검사에서 먼저 걸린다.
2. MSW는 Prism보다 훨씬 많이 쓰이고(조사 시점의 공개 집계로 주간 다운로드 약 385만 대 약 13만), 스스로 자바스크립트의 업계 표준 API 모킹 도구라고 소개한다. 프론트 AI가 쓴 가짜 응답은 openapi-msw의 타입 검사와 프론트 리뷰어가 확인한다. 보통 팀에서 동료 프론트 개발자가 리뷰하는 자리를 우리 리뷰어가 맡는다.
3. 가짜 응답으로 "라이브러리에 추가하면 내 라이브러리에 나타남" 같은 흐름도 흉내 낼 수 있고, 같은 가짜 응답을 나중에 프론트 테스트에서도 쓴다.
버린 선택지:
- **Prism(계약 파일만 읽어 응답하는 가짜 서버)**: 계약 밖의 동작을 지어낼 여지가 없고 프론트 코드에 아무것도 남지 않는다. 하지만 MSW보다 훨씬 덜 쓰이고, 상태를 기억하지 못한다.
- **openapi-generator의 TypeScript 생성기**: 호출 코드까지 통째로 만들어 주지만 생성물이 크고, 프론트 AI가 고를 라이브러리와 겹친다.
- **프론트 AI가 손으로 쓰는 가짜 데이터**: 계약과 달라져도 잡을 장치가 없다.
감수하는 것:
- 타입은 모양만 검사한다. "재고가 0이면 409" 같은 동작은 가짜 응답에서 지어낼 수 있다. 프론트 리뷰어 체크리스트에 넣고, 정현이 진짜 Spring에 붙여 네트워크 탭으로 한 번 더 확인한다.
## 결정 3: 응답의 공통 규칙
 
1. **성공 응답은 감싸지 않는다.** 성공은 데이터를 그대로, 실패는 ProblemDetail(ADR-0004)로 준다. 성공·실패는 HTTP 상태 코드로 구분하고, "200인데 실패"인 응답을 만들지 않는다.
   ```
   성공 200: { "id": 12, "title": "취업 준비 플래너", "format": "NOTION", "downloadCount": 37 }
   실패 404: { "status": 404, "code": "TEMPLATE_NOT_FOUND",
               "detail": "템플릿을 찾을 수 없습니다.", "traceId": "4bf92f35…" }
   ```
 
2. **목록은 `content` + `page` 모양으로 고정한다.** Spring의 `Page`를 그대로 내보내지 않는다.
   ```json
   { "content": [ { "id": 12, "title": "취업 준비 플래너" } ],
     "page": { "number": 0, "size": 20, "totalElements": 57, "totalPages": 3 } }
   ```
 
   - Spring Data는 `PageImpl`을 그대로 JSON으로 바꾸면 구조가 안정적이라는 보장이 없다고 경고하고, `PagedModel`을 권고한다. 위 모양이 그것이다.
   - 컨트롤러는 `PagedModel<T>`를 직접 반환한다. 전역 변환 설정에 맡기면 springdoc이 반환 타입(`Page`)을 보고 실제와 다른 모양을 계약에 적을 수 있다. 계약 파일에 위 모양이 찍히는지 뼈대 때 확인한다.
   - 쪽 번호 방식과 커서 방식 중 무엇을 쓸지는 설계 주간에 정한다. 커서로 가면 `page` 부분만 바뀐다.
3. **문장은 `detail`, 동작은 `code`.** ADR-0004 결정 3의 9번(잠정)을 확정한다.
   - 백엔드의 `detail`은 사용자에게 그대로 보여도 되는 한국어 문장으로 쓴다. 내부 정보(SQL, 클래스 이름)는 넣지 않는다.
   - 프론트는 기본으로 `detail`을 알림으로 보여 준다. 화면 자체가 달라져야 하는 `code`만 따로 처리한다(예: `DROP_SOLD_OUT`이면 버튼을 "마감"으로, 401이면 로그인 화면으로).
   - 입력 검증 실패는 `errors`의 필드별 문장을 해당 입력칸 옆에 보여 준다.
   - 알 수 없는 서버 에러(500)는 일반 문장과 함께 `traceId`를 작게 보여 준다.
4. **에러 코드 목록을 계약에 싣는다.** 에러 응답의 `code` 칸을 모든 에러 코드 값의 목록(enum)으로 계약에 적는다.
   - 프론트 타입이 `code: "DROP_SOLD_OUT" | "TEMPLATE_NOT_FOUND" | …`가 되어, 프론트가 `code`로 분기할 때 없는 코드나 오타가 타입 오류가 된다. 백엔드에서 코드 이름을 바꾸면 그 코드를 쓰던 프론트가 빌드 실패로 드러난다.
   - 목록은 기능별 `ErrorCode` enum에서 자동으로 만든다. 손으로 맞출 표가 따로 없다.
   - ADR-0004 결정 3의 8번("에러 코드 표를 API 문서에 실어 프론트와의 계약으로")을 이렇게 지킨다. API마다 어떤 코드가 나는지는 결정 1의 애너테이션이 맡는다.
5. **JSON 필드 이름은 camelCase**(`downloadCount`)로 쓴다. **값이 없는 필드는 빼지 않고 `null`로 보낸다**(결정 1의 "기본은 필수, 없을 수 있는 것만 `@Nullable`"과 짝).
6. **시각은 ISO-8601 형식의 UTC로 준다**(`"2026-11-20T11:00:00Z"`). 화면에서 한국 시간으로 바꿔 보여 준다. 인계 문서 1(12번)의 "저장은 UTC, 표시는 한국 시간"을 계약에도 적용한다.
   - API의 시각 타입은 `Instant`를 쓴다. `LocalDateTime`은 시간대 정보가 없어 `"2026-11-20T20:00:00"`처럼 나가고, 받는 쪽은 이것이 한국 시간인지 UTC인지 알 수 없다. 그래서 API에는 쓰지 않는다.
성공 응답 감싸기의 선택지:
 
| | 가. 감싸지 않음 (선택) | 나. 성공만 감쌈 | 다. 둘 다 감쌈 (공통 응답 봉투) |
| --- | --- | --- | --- |
| 성공 | `{ "id": 12, … }` | `{ "data": { "id": 12, … } }` | `{ "status": "success", "data": {…}, "error": null }` |
| 실패 | ProblemDetail 그대로 | ProblemDetail 그대로 | `{ "status": "fail", "data": null, "error": {…} }` |
| ADR-0004 | 그대로 | 그대로 | 에러 응답이 RFC 9457이 아니게 되어 새 ADR로 대체해야 함 |
| 추가로 할 일 | 없음 | 성공을 상자에 담는 공통 처리 | Spring이 자동으로 만드는 404·400·401·403까지 봉투로 다시 싸야 함 |
 
이유:
1. 실패는 이미 표준 형식(RFC 9457)으로 따로 오고, 성공·실패는 HTTP 상태 코드가 말해 준다. 감싸면 같은 것을 두 번 말하게 되고, 두 값이 어긋날 수 있다.
2. "200인데 실패"로 나간 에러는 나중에 만들 대시보드의 에러율과 SLO에 잡히지 않는다.
3. 프론트 코드가 단순해진다(`response.data.title` 대신 `template.title`).
확인한 사례: 실무에는 세 모양이 모두 있다. 토스페이먼츠 API v2는 성공을 `version`·`traceId`·`entityType`·`entityBody` 상자에 담지만(나에 가까움), 성공·실패는 HTTP 상태 코드로 전달한다고 문서에 적었다. 앱인토스 API는 `resultType`·`success`·`error` 봉투(다)를 쓰고, 비즈니스 에러도 HTTP 200으로 보낸다. 국내 Spring 프로젝트에서는 다(공통 응답 형식)가 흔하고, 정상 응답은 감싸지 않고 에러는 ProblemDetail로 주는 방식도 소개된다.
 
감수하는 것: 국내에서 흔한 공통 응답 봉투와 다르므로 면접에서 "왜 감싸지 않았나"를 물을 수 있다. board에서는 `ApiResponse`로 감쌌으므로, 두 방식을 모두 써 본 경험으로 비교해 답할 수 있다.
 
## 결정 4: 주소 규칙
 
```
/api/v1/templates/12           공개·회원 구역
/api/v1/studio/templates/12    제작자 구역
/api/v1/admin/templates/12     운영 구역
```
 
1. **주소에 버전 `v1`을 넣는다. 처음에는 고정된 앞부분(`/api/v1`)으로 구현한다.**
   - 지금은 같은 저장소에서 함께 배포되는 웹 화면 하나만 이 API를 쓰므로 `v1`뿐이다. 모바일 앱처럼 강제로 업데이트시킬 수 없는 클라이언트가 생기면, `v1`을 살려 둔 채 `v2`를 나란히 열 수 있다.
   - [잠정] Spring 7의 API 버전 기능(경로 방식)은 뼈대를 만들 때 시험해 보고 쓸지 정한다. 이 기능은 버전 자리를 주소 변수(`/api/{version}/…`)로 선언해야 하고, 기본으로 모든 요청에 버전을 요구한다. 그래서 버전이 없는 주소(springdoc의 문서 주소, actuator, `/error`)는 따로 빼 주지 않으면 400이 된다. 그 설정을 빠뜨려 문서 주소가 500이 된 사례도 보고되어 있다. springdoc이 이 주소를 계약 파일에 어떻게 적는지도 아직 확인하지 못했다.
   - 주소 모양은 어느 쪽이든 `/api/v1/…`로 같으므로, 나중에 버전 기능으로 옮겨도 프론트에는 영향이 없다.
2. **구역 앞부분은 운영 `admin`, 제작자 `studio`.**
   - `admin`은 운영 API를 부르는 가장 흔한 이름이다. `studio`는 만드는 사람의 작업 공간을 부르는 흔한 이름이다.
   - 화면 구역 이름도 같게 맞춘다(`/admin`, `/studio`). ADR-0005에서 예로 든 `/ops` 대신이다. 화면 목록은 설계 주간에 정한다.
   - 보안 규칙을 구역 단위로 한 줄에 건다. 새 운영 API에서 권한 검사를 깜빡해도 이 줄이 먼저 막는다.
     ```java
     .requestMatchers("/api/*/admin/**").hasRole("ADMIN")
     .requestMatchers("/api/*/studio/**").hasRole("CREATOR")
     ```
 
   - 인계 문서 1(11번)의 조건인 "모든 운영 API에 서버 권한 검사와 그 테스트"는, `admin`으로 시작하는 주소를 전부 돌며 "일반 회원이면 403"을 확인하는 테스트 하나로 지킨다.
3. **주소 이름은 복수형 명사 + 소문자 + 하이픈**으로 쓰고, 행동은 HTTP 메서드로 표현한다(GET 조회, POST 만들기, PATCH 일부 수정, DELETE 삭제). `/getTemplate` 같은 동사 주소는 쓰지 않는다. 기능별 실제 주소 이름은 설계 주간에 ERD와 함께 정한다.
감수하는 것:
- `v1`은 끝까지 하나뿐일 수 있다. 사실상 자리만 잡아 두는 것이다.
- `admin`은 봇이 가장 많이 두드려 보는 이름이라, 공개 뒤에는 401·403 응답과 그 로그가 많아질 수 있다. 사용자 잘못이므로 로그 수준은 INFO/WARN이고(ADR-0004), 많아지면 레이트 리밋(11번)에서 다룬다.
## 결정 5: traceId
 
```
요청 → Spring: 들어오는 순간 traceId 발급 (W3C 형식, 32자리 16진수)
       └ 이 요청을 처리하는 동안 찍히는 로그에 자동으로 붙음
응답 → 에러 본문의 "traceId" + 모든 응답의 헤더 X-Trace-Id
```
 
- Spring Boot의 추적 기능(Micrometer Tracing, OpenTelemetry 쪽 연결)이 만든다. 형식은 업계 표준인 W3C Trace Context다.
- 에러 응답 본문의 `traceId`(ADR-0004)에 더해, 모든 응답 헤더에 `X-Trace-Id`를 붙인다. 성공 응답은 감싸지 않으므로(결정 3) 본문에는 자리가 없다.
- 밖에서 들어온 `traceparent` 헤더는 Nginx가 지운다. 아무나 남의 요청과 같은 번호를 만들어 로그를 헷갈리게 하지 못하게 한다. Nginx가 붙인 IP 정보만 믿는 원칙(11번)과 같다.
- v1에서는 번호만 만들고, 추적 데이터를 모아 보는 서버로 보내지 않는다. 그 서버(분산 추적)는 v3다.
- [확인 필요] 뼈대 첫날 확인할 것 두 가지
  1. Spring Boot는 기본으로 요청의 10%만 추적 서버로 보낼 표본으로 고른다. 표본에 들지 않은 요청에도 로그와 응답에 번호가 붙는지 확인한다. 안 붙으면 보낼 서버가 없는 v1에서는 표본 비율을 100%로 둔다.
  2. 고른 의존성이 추적 서버로 보내기를 기본으로 켜는 구성이 아닌지 확인한다. 켜져 있으면 보낼 곳이 없어 연결 실패가 로그에 반복된다.
선택지:
- A. Spring Boot의 추적 기능 (선택)
- B. 직접 만든 필터(UUID): 원리를 배우기에는 좋지만, Spring이 이미 해 주는 일을 다시 만들고, v3 분산 추적 때 갈아엎어야 한다.
- C. Nginx가 발급: 개발 환경(맥)에는 Nginx가 없어 번호가 생기지 않고, 분산 추적과 따로 연결해야 한다.
## 결정 6: API 문서 화면
 
- 개발할 때(맥): springdoc의 Swagger UI를 켜고 쓴다.
- 운영 서버: Swagger UI와 계약 주소(`/v3/api-docs`)를 모두 끈다. springdoc도 시작할 때 운영에서는 끄라고 경고한다. 운영의 Nginx는 정해진 경로(`/api/` 등)만 Spring에 넘기므로(ADR-0005), 설정으로 끄는 것과 함께 두 겹이 된다.
- 공개 문서: `contract/openapi.yaml`로 Swagger UI 정적 페이지를 만들어 GitHub Pages에 올린다. Try it out은 꺼서 읽기 전용으로 둔다. 계약 파일이 main에 병합되면 GitHub Actions가 다시 올린다.
이유:
1. 운영 서버의 열린 문이 늘지 않는다.
2. 면접관이나 포트폴리오를 보는 사람이 링크 하나로 API 문서를 본다.
3. 실무에서도 공개 API 문서는 API 서버와 따로 둔다(예: 토스페이먼츠의 `docs.tosspayments.com`).
4. 새로 드러나는 것이 없다. 계약 파일은 공개 저장소에 이미 있고, 운영 API 주소가 보이는 것은 ADR-0005에서 받아들였다. 관리 도구(Grafana, actuator)의 주소는 API 문서에 들어가지 않는다.
버린 선택지:
- **운영 서버에서도 Swagger UI 공개**: 누구나 Try it out으로 운영 서버에 요청을 보낼 수 있다. 실무에서 피하는 방식이다.
- **운영에서는 끄고 개발에서만**: 실무의 기본이지만, 저장소를 보는 사람이 문서를 보려면 앱을 직접 실행해야 한다.
## 결과
 
- **설계 주간**: 기능별 실제 주소 이름, 목록의 쪽 번호 vs 커서, 화면 목록(`/admin`, `/studio` 구역)
- **첫 주 뼈대** (첫 기능 전에)
  - 계약을 `contract/openapi.yaml`로 꺼내는 테스트와, 파일이 최신인지 보는 CI 단계
  - 계약 파일이 실행할 때마다 똑같이 나오는지 확인한다. springdoc에는 정렬 설정(`writer-with-order-by-keys`)이 있지만 완전히 정렬되지 않는다는 보고가 있다. 필요하면 저장할 때 직접 정렬하고, 계약에 찍히는 서버 주소도 고정한다. 그렇지 않으면 내용이 같아도 CI가 실패하고, 바뀐 곳이 PR에서 묻힌다.
  - "응답 필드는 기본이 필수, `@Nullable`만 예외"를 계약에 반영하는 공통 설정
  - 공통 에러 코드 `NOT_IMPLEMENTED`(501, WARN)
  - ProblemDetail 에러 모양과 에러 코드 목록(enum)을 계약에 붙이는 공통 설정
  - `/api/v1` 앞부분, 목록의 `PagedModel<T>` 반환과 계약 확인, API 시각 타입 `Instant`
  - Spring 7 API 버전 기능 시험(잠정): springdoc 문서 주소·actuator·`/error`가 400·500이 되지 않는지, 계약 파일에 주소가 어떻게 찍히는지
  - 보안 구역 규칙(`admin`, `studio`)과 "운영 API는 일반 회원에게 403" 테스트
  - traceId 확인 두 가지(결정 5), `X-Trace-Id` 헤더
  - 운영 프로필에서 springdoc 끄기
- **환경 구축 채팅**
  - openapi-typescript, MSW, openapi-msw 버전 고정과 Node 24 호환 확인, MSW가 운영 빌드에 들어가지 않는지 확인
  - 에러 응답의 Content-Type(`application/problem+json`)을 프론트 타입과 호출 도구가 제대로 읽는지 확인
  - 프론트 CI: 생성 타입이 최신인지 확인, 계약 파일이 바뀐 PR에서 프론트 빌드까지 돌리기
  - 계약을 깨는 PR에서 프론트 AI가 같은 브랜치에 프론트 수정을 올리는 방법(ADR-0004의 프론트 AI 경계와 함께)
  - **테스트에서 쓸 DB 방식**: 계약을 꺼내는 테스트가 앱 전체를 띄워야 하면 DB가 필요하다. board에서는 테스트가 로컬 MySQL에 묶였던 문제가 있었다. 아직 어느 안건에도 없으므로 여기서 정한다.
  - GitHub Pages 문서 작업 흐름
  - `frontend/CLAUDE.md`: 계약 파일과 생성 타입 수정 금지, 가짜 응답은 openapi-msw의 응답 도우미로, 계약에 없는 동작은 지어내지 말고 보고, 백엔드가 끝난 API는 가짜 응답을 끄기
  - `fe-reviewer.md`: 가짜 응답이 계약과 맞는지, 동작을 지어냈는지, MSW가 운영에서 꺼지는지, 500 화면의 traceId
  - `be-reviewer.md`: 새 API마다 에러 코드 문서화, `@Nullable` 표시, `detail`에 내부 정보가 없는지, 시각 타입
  - PR 템플릿의 "계약 변경 여부"
- **7번(운영 구성)**: Nginx에서 밖에서 들어온 `traceparent` 지우기
- **10번(관측성)**: 로그 형식에 traceId를 싣는 방법(JSON 로그), 분산 추적은 v3

## 정현의 판단 (대화에서 옮김)
 
> 정현의 말을 대화에서 옮겼다. 읽기 쉽게 조금 다듬었지만 뜻은 바꾸지 않았고, 정현이 말하지 않은 이유는 넣지 않았다.
 
- **처음 상태** (11/6): OpenAPI yaml은 "작성해본 적 없고 처음 들어봅니다." "계약이라는 개념이 아직 없고 계약이란게 뭔지 머릿속에도 안 그려집니다. 단어 의미 자체는 알지만 계약을 어떻게 작성해야하는지는 전혀 모릅니다." 멘토가 선택지부터 내놓았을 때 "읽어보다가 이해가 어려워서 읽다가 먼저 말씀드립니다." 요청·응답 예시와 약속 목록으로 다시 설명받은 뒤 "1 2 3의 느낌은 이제 알겠습니다."
- **결정 1 계약 방식**: "보통의 실무도 A 방식으로 가고 둘이 함께 작업하는 방식이겠죠? 그렇다면 A로 가고 그게 아니라 springdoc, REST Docs를 사용하는 다른 방식(B나 C)을 고려해도 될 것 같습니다." 국내 실무 경향과 껍데기 먼저 방식을 듣고 "실무 그리고 더 나은 방식이 B라면 그렇게 하도록 하죠."
- **결정 2 가짜 응답**: 처음에는 "아무래도 다 처음 접하는 개념들이다보니 판단에 대해 조심스러운 부분입니다. 내용 자체는 이해했습니다." "실무에서 많이 사용하는, 혹은 나은 방향이라면 추천대로 해도 좋습니다." 멘토가 Prism이 MSW보다 덜 쓰인다고 밝힌 뒤 "보통 동료라면 동일 직종, 프론트 개발자가 리뷰하나요? 그렇다면 우리의 리뷰어와는 역할이 다른건가요? 아니면 우리의 리뷰어가 그런 역할도 할 수 있는건가요? 리뷰어가 동료에 포함이 가능하다면 MSW를 쓰면 실무에서 다루는 환경과 유사하게 경험할 수 있을 것 같다는 생각입니다." 이 질문으로 MSW로 바꿨다.
- **결정 3 감싸기**: 처음에는 감싸기를 원했다. "현 업계에서 표준으로 쓰고 있는 방식을 적용해보고 경험해보는게 제가 이번 프로젝트에서 필요해하고 중요히 여기는 것 중 한가지입니다. 업계에서 응답을 한 겹 감싸서 일관되게 처리하는 방식을 실무에서 선호 혹은 많이 쓰이는 표준 정도의 방식이라면 해당 방식을 사용해보고 싶어요. 그러면 이 방식을 사용한다면 ProblemDetail이란 걸 사용하기 어려워질까요?" 세 모양의 비교를 들은 뒤, 기업들의 API 응답 형식을 직접 조사해 와서(토스·카카오·구글·마이크로소프트) "이럴 때 그냥 가로 가는게 맞는 것 같기도 하죠?" 멘토가 출처를 열어 일부를 바로잡은 뒤 가로 정했다.
- **결정 3 목록 모양**: "해당 부분은 확신의 답변 느낌이 강하고 읽어보기만해도 추천 규칙으로 작성하면 좋을 것 같아요. 실무에서도(기업) 해당 방식을 표준으로 쓰고 있다면 찬성입니다."
- **결정 3 화면 문장, 결정 4 주소 규칙, 결정 6 문서 화면**: 설명을 듣고 그대로 승인했다.
- **결정 5 traceId**: "문제가 없다면 좋습니다." 멘토가 확인할 점(추적 서버로 보내기가 기본으로 켜지는 의존성)을 덧붙인 뒤 정했다.
- **검토** (11/6): "새 채팅으로 넘어가기 전에 노력 최대로 해서 임의로 검토 한 번만 해봅시다. 문제가 없다면 ADR-0006 승인 후 새 채팅에서 진행하겠습니다."
- **멘토가 검토에서 고친 것** (11/6, 초안을 쓴 뒤 다시 확인해서 찾음)
  - 결정 4: 버전을 Spring 7의 버전 기능으로 구현하던 것을 고정 앞부분으로 바꾸고, 버전 기능은 뼈대 때 시험한 뒤 정하는 [잠정]으로 돌렸다. 주소 모양(`/api/v1/…`)은 그대로다.
  - 결정 1: 껍데기는 501 `NOT_IMPLEMENTED`로 답한다(자동 배포 뒤 500 알림 방지). 응답 필드는 기본이 필수(springdoc 기본값이 "모두 필수 아님"이라 프론트 타입이 전부 선택이 되는 문제). 계약을 깨는 변경의 처리 순서.
  - 결정 2: 가짜 응답은 응답 도우미로 만들고, 백엔드가 끝난 API는 가짜 응답을 끈다.
  - 결정 3: 에러 코드 목록을 계약에 싣는다(ADR-0004 결정 3의 8번이 구체화되지 않았던 것). 시각 타입은 `Instant`. 값이 없으면 `null`로 보낸다. 목록은 `PagedModel<T>`를 직접 반환한다.
  - 결과: 계약 파일이 매번 같게 나오는지 확인, 테스트 DB 방식(어느 안건에도 없었음), M1의 뜻이 바뀌는 것(기획 3).
  - 표현: "국내 실무에서 많다", "가장 많이 쓰인다"처럼 근거보다 강하게 쓴 문장을 근거에 맞게 고쳤다.
- **승인** (11/6): 검토 결과(버전 구현 방법 변경과 보완 규칙)를 듣고 "승인하겠습니다."
