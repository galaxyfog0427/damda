# ADR-0009: 비밀번호는 8~20자에 영문·숫자·특수문자를 모두 넣고, BCrypt로 저장한다
 
- 날짜: 2026-11-12
- 상태: 승인 (2026-11-12, 정현)
- 작성: 초안은 멘토 AI, 판단은 정현
> **쉽게 말하면**
> 1. 비밀번호는 8자 이상 20자 이하이고, 영문·숫자·특수문자를 각각 하나 이상 넣는다. 국내 사이트에서 흔히 보는 규칙이다.
> 2. 업계 기준(NIST)은 더 길게(비밀번호만 쓸 때 15자) 하고 조합 규칙을 두지 말라고 한다. 우리는 가입을 망설이게 하지 않는 쪽을 골랐고, 그만큼 레이트 리밋과 해시 강도에 기댄다.
> 3. 저장은 BCrypt 해시로 한다. 원래 비밀번호는 어디에도 남지 않는다.
 
## 맥락
 
- ADR-0007은 v1 로그인을 이메일·비밀번호로 정했고, 비밀번호 규칙과 저장 방식을 11번(레이트 리밋)으로 넘겼다. 기획 3(11/8 검토)이 이것을 11/11 요구사항으로 당겼다. 가입 화면과 요구사항(A-6)이 이 결정에 기댄다.
- NIST SP 800-63B-4(2025) 3.1.1.2, 3.2.2:
  - 반드시(SHALL): 비밀번호만으로 로그인하면 최소 15자, 다단계 인증의 한 요소이면 최소 8자. 흔하거나 예상하기 쉽거나 유출된 비밀번호 목록(서비스 이름·아이디 같은 문맥 단어 포함)과 비밀번호 전체를 비교한다. 한 계정의 연속 로그인 실패는 100회 이하로 제한한다.
  - 하지 않음(SHALL NOT): 문자 조합 규칙, 주기적 변경 강제.
  - 권장(SHOULD): 최대 길이 64자 이상 허용, 출력 가능한 ASCII 문자와 공백 허용, 유니코드 허용.
- Spring Security의 BCrypt: 72바이트를 넘는 비밀번호는 만들 때(encode) 거부한다(CVE-2025-22228의 수정). 확인할 때(matches)는 길이를 보지 않고 비교한다(이 검사가 응답 시간으로 계정을 드러내던 CVE-2025-22234의 수정).
- OWASP Password Storage Cheat Sheet: 새 시스템에는 Argon2id를 쓰라고 하고, bcrypt는 "레거시 시스템"용으로 둔다(작업 계수는 서버가 허락하는 만큼 크게, 최소 10, 72바이트 제한).
- 개인정보보호위원회 "개인정보의 안전성 확보조치 기준 안내서"(2024-10): 비밀번호를 일방향 암호화할 때 솔트를 쓰고, 로그인 반복 실패에는 계정 잠금 외에 캡차·재시도 시간 제한 같은 방법을 든다 [확인 필요: 안내서 원문].
- 우리 사이트는 로그인 없이도 둘러보고 받을 수 있다(ADR-0008). 가입은 라이브러리와 드롭이 필요할 때 하는 선택이라, 가입 화면의 부담이 곧 가입 포기로 이어지기 쉽다.
## 결정 1: 규칙은 8~20자, 영문·숫자·특수문자를 각각 하나 이상
 
- 쓸 수 있는 문자는 ASCII 0x21~0x7E 94자뿐이다.
  - 영문: `A`~`Z`, `a`~`z` (대소문자를 구별함)
  - 숫자: `0`~`9`
  - 특수문자 32자: ``! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ ` { | } ~``
- 그 밖의 문자(공백, 탭, 한글, `₩`, 전각 문자 `！` 등, 이모지)가 하나라도 있으면 거절한다. `₩`와 전각 문자에는 "영문 입력 상태에서 입력하세요"라고 안내한다(맥 한글 입력에서 `` ` `` 키를 누르면 `₩`가 나온다).
- 길이: 허용 문자 검사를 통과한 뒤 센다. 8자 이상 20자 이하(허용 문자는 모두 1바이트라 20자 = 20바이트).
- 조합: 영문, 숫자, 특수문자를 각각 하나 이상 넣는다.
- 앞뒤 공백을 자르지 않는다(가입과 로그인이 같은 문자열을 보게).
- 규칙은 비밀번호를 만들 때(가입, 재설정)만 검사한다. 로그인에서는 규칙을 검사하지 않는다.
- 그 밖의 규칙(흔한·유출 비밀번호 검사, 연속 문자, 이메일 포함 금지, 주기적 변경)은 없다.
- 일반 회원, 공식 제작자 계정, 운영 계정 모두 같은 규칙이다.
- 서버가 검사한다(화면의 검사는 안내용). 화면에는 규칙을 입력 칸 옆에 미리 보여 준다. 입력 칸에는 `autocomplete="new-password"`와 `passwordrules`를 붙인다.
선택지:
 
| | 나. NIST 방식 | 가-2. 8자 + 조합 없음 | **가-1. 국내 흔한 방식 (선택)** |
| --- | --- | --- | --- |
| 길이 | 15자 이상, 64자 이상 허용 | 8~64자 | 8~20자 |
| 조합 규칙 | 없음(금지) | 없음 | 영문·숫자·특수문자 모두 |
| 흔한·유출 비밀번호 검사 | 있음 | 있음 | 없음 |
| 만들 때의 고민 | "15자를 어떻게?" | 거의 없음 | 조합 맞추기(익숙함) |
 
이유:
1. 가입을 하려다 비밀번호 때문에 그만두는 이용자가 없게 한다(정현의 판단). 15자는 정현도 만들 때 고민했던 길이다.
2. 국내 사이트에서 흔히 보는 규칙이라 설명 없이 통한다. 옛 보호조치 기준이 예로 들던 "2종류 조합 10자 이상 또는 3종류 조합 8자 이상"의 3종류 쪽과 같은 모양이다. 현행 고시는 조합과 길이를 정해 두지 않는다 [확인 필요: 안내서 원문].
버린 선택지:
- **나**: 업계 기준에 가장 가깝지만, 로그인 없이 쓸 수 있는 사이트에서 가입 장벽이 된다.
- **가-2**: 조합 고민이 없고 NIST의 최소 8자 쪽 모양이지만, 정현이 익숙한 가-1을 골랐다.
감수하는 것:
- NIST의 SHALL과 다르다. 비밀번호만 쓰는 회원에게 15자가 아니라 8자이고, NIST가 금지한 조합 규칙을 두며, 유출 비밀번호 검사가 없다. 조합 규칙은 `Password1!`처럼 예측하기 쉬운 모양으로 사람을 몰아간다는 것이 NIST의 이유다.
- NIST의 SHOULD와도 다르다. 20자 상한 때문에 긴 문장형 비밀번호나 비밀번호 관리자가 만든 긴 값은 쓸 수 없고, 공백과 한글을 쓸 수 없다.
- 짧고 흔한 비밀번호가 들어올 수 있다.
  - 다른 사이트에서 유출된 비밀번호를 대입하는 공격을 막는 일은 **로그인 레이트 리밋**(11번, M3 전)에 더 크게 기댄다.
  - DB나 백업이 새어 나가면 짧고 예측하기 쉬운 비밀번호는 서버 밖에서 풀어 낼 수 있다. 레이트 리밋은 이것을 막지 못한다. 해시 강도(결정 2)와 백업 보호(7번에서 백업 암호화를 함께 정함)에 기댄다.
- 공식 제작자 계정은 비밀번호만으로 공개 파일을 바꿀 수 있는 계정인데 같은 규칙을 쓴다. 그래서 운영 서버에 만드는 정현의 두 계정(공식 제작자, 운영)은 비밀번호 관리자로 만든 20자 무작위 값을 쓴다(런북).
- 브라우저·비밀번호 관리자가 제안하는 비밀번호가 "특수문자 필수"에 걸릴 수 있다. `passwordrules`를 지원하는 곳은 아직 고르지 않다.
- 규칙을 바꾸면 기존 회원의 비밀번호는 그대로 두고 새로 만들 때만 새 규칙을 적용한다(해시에서 길이를 알 수 없음).
## 결정 2: 저장은 BCrypt
 
- Spring Security의 `DelegatingPasswordEncoder`를 쓰고 기본 방식은 bcrypt다. 해시 앞에 `{bcrypt}`가 붙는다.
  - 4주 차에 강도를 정하면서 bcrypt만 넣어 직접 구성한다(Argon2로 옮길 때 그것을 더한다). `PasswordEncoderFactories.createDelegatingPasswordEncoder()`는 강도가 10으로 고정이고, 옛 방식(MD5·SHA-1 등)으로 저장된 값도 맞춰 본다. 새 시스템이라 옛 해시가 없으므로 쓰지 않는다.
  - 방식이나 강도를 바꾸면 회원이 로그인할 때 새 방식으로 다시 저장한다. 이 일은 `UserDetailsPasswordService`를 만들어야 일어난다.
- 솔트는 BCrypt가 해시마다 무작위로 만들어 해시 문자열 안에 함께 저장한다(개인정보위 안내서의 솔트).
- 강도(cost)는 10에서 시작한다 [잠정: 4주 차]. 운영 서버 사양에서 해시 한 번의 시간을 재서 정한다. OWASP는 "서버가 허락하는 만큼 크게, 최소 10", Spring 문서는 "확인 한 번이 대략 1초"를 권한다. 강도를 1 올리면 시간이 두 배다.
- 결정 1의 규칙 때문에 비밀번호는 최대 20바이트다. BCrypt의 72바이트 제한에 걸리지 않는다. 규칙을 바꿔 길이를 늘리거나 한글을 받게 되면 이 결정을 다시 본다.
선택지:
- **BCrypt (선택)**: Spring Security에 들어 있어 의존성이 더 필요 없고, 정현이 board에서 써 봐서 익숙하다. 해시 하나에 쓰는 메모리가 작다(약 4KB).
- **Argon2id**: OWASP가 새 시스템에 먼저 권한다. 메모리를 일부러 써서 GPU로 한꺼번에 맞히기 어렵다. Spring의 현재 기본값은 해시 하나에 16 MiB(반복 2)이다. OWASP는 메모리를 줄이고 반복을 늘린 같은 강도의 설정(7 MiB·반복 5까지)도 들지만, 그래도 BCrypt의 천 배가 넘는다. 로그인이 몰리면 그만큼 서버 메모리를 쓰고, BouncyCastle 의존성이 더 필요하다. 작은 서버 하나로 시작하는 v1에서는 메모리 쪽 위험이 더 크다고 봤다.
이유:
1. 결정 1의 규칙 안에서는 BCrypt의 약점(72바이트)이 문제가 되지 않는다.
2. 작은 서버(7번)에서 로그인이 몰릴 때 메모리를 덜 쓴다.
3. 정현이 익숙하고 설정이 가장 적다.
4. 접두사 방식이라 나중에 Argon2id로 옮기기 쉽다(로그인할 때 다시 저장).
감수하는 것:
- OWASP 권장 밖이다. OWASP는 bcrypt를 레거시 시스템용으로 두는데 우리는 새 시스템이다. DB가 새면 Argon2id보다 GPU로 더 빨리 맞혀 볼 수 있다.
- 해시마다 CPU를 쓴다. 로그인 한 번마다(없는 이메일이어도 응답 시간을 맞추려고) 해시를 한 번 하므로, 레이트 리밋이 들어오기 전에는 로그인 요청만으로 CPU를 쓸 수 있다. 로그인이 몰릴 때의 CPU는 6주 차 부하 테스트에서 본다.
## 결과
 
- **요구사항**: A-6, N-3이 이 ADR을 가리킨다. 4번 표에 "흔한·유출 비밀번호 검사: 하지 않음".
- **11/13 ERD**: 비밀번호 해시 칸은 VARCHAR(255). bcrypt는 `{bcrypt}`를 포함해 68자, Argon2로 옮기면 약 125자다.
- **11번(레이트 리밋)**: 짧은 비밀번호를 고른 만큼 로그인 레이트 리밋의 무게가 커진다. NIST의 "계정당 연속 실패 100회 이하"에 맞게 IP 단위에 더해 계정 단위로도 센다. 재시도 시간 제한·캡차를 함께 본다. 실패 응답은 이유와 관계없이 같아야 한다(요구사항 A-3).
- **4주 차(계정)**:
  - 가입·재설정의 규칙 검사(서버 Bean Validation + 화면 안내), `DelegatingPasswordEncoder` 구성과 강도 측정, `UserDetailsPasswordService`.
  - 규칙 테스트: 경계(7·8·20·21자), 각 종류가 빠진 경우, 특수문자 32자 각각 통과, 공백·탭·한글·`₩`·전각 문자·이모지 거절.
  - 로그인 테스트: 73바이트가 넘는 값을 넣어도 같은 401(500이 아님), 규칙에 맞지 않는 비밀번호로도 로그인 시도는 그대로 처리됨, 강도가 낮은 옛 해시가 로그인 뒤 다시 저장됨.
- **런북**: 운영 서버의 공식 제작자·운영 계정은 비밀번호 관리자로 만든 20자 무작위 비밀번호를 쓴다.
- **용어 사전**: "비밀번호 규칙" 한 줄.
## 다시 검토할 때
 
- 유출 비밀번호 검사는 Spring Security 6.3부터 있는 `CompromisedPasswordChecker`(Have I Been Pwned) 빈 하나로 붙일 수 있다. 외부 호출이라 6번의 타임아웃·재시도와 함께 본다.
- Argon2id로 옮길 때는 Spring 기본값이 아니라 그때의 OWASP 표에 맞춰 값을 정한다.

## 정현의 판단 (대화에서 옮김)
 
> 정현의 말을 대화에서 옮겼다. 읽기 쉽게 조금 다듬었지만 뜻은 바꾸지 않았고, 정현이 말하지 않은 이유는 넣지 않았다.
 
- 멘토의 처음 추천은 "나"(NIST 방식) + Argon2id였다. 초안은 가-1 + Argon2id로 썼다.
- **결정 1** (11/12): "가로 가고 싶어요. 국내 흔한 방식이라고 작성하셔서 그런 것도 있기도 한데, 로그인 없이 우리 서비스를 사용할 수 있는 상황에서 회원가입을 할 때 15자 이상이면 저도 어떻게 만들어야 할까 고민했던 적이 많았어요. 이 고민 때문에 회원가입을 하려다 관두는 이용자가 없었으면 해요. 그래서 저는 가입니다."
  - 멘토가 조합 규칙도 같은 고민을 만든다며 가-1(국내 흔한 그대로)과 가-2(8자 + 조합 없음 + 유출 검사)를 나눠 보였다. 정현: "가-1로 하죠"
  - 특수문자 목록(11/12 검토): ASCII 32자 전부, `₩`·전각 문자는 거절하는 추천에 "좋습니다". 정현이 전각 `！`와 ASCII `!`가 다른 문자인지 물어 확인했다.
- **결정 2** (11/12): "그냥 Bcrypt로 진행해도 될까요? 친근하기도 하고, 다른 AI에 물어봤을 때도 이런 답변을 받아서요." 다른 AI의 답(요약): Argon2id는 해시마다 메모리를 크게 써서 작은 서버에서 동시 로그인이 몰리면 메모리가 모자랄 수 있고, BCrypt는 가볍다. Spring 기본 `BCryptPasswordEncoder`에 강도 10~12면 충분하다.
  - 멘토의 답(요약): 결정 1의 규칙(최대 20바이트) 안에서는 BCrypt의 72바이트 제한이 문제가 되지 않아 BCrypt가 맞다. 메모리 걱정도 맞는 지적이다(Spring의 Argon2 기본값은 해시 하나에 16 MiB). 강도는 4주 차에 서버에서 재서 정한다.
