# ADR-0007: v1 로그인은 이메일·비밀번호로 하고, 로그인 상태는 Redis에 둔 서버 세션으로 기억하며, 운영 계정은 따로 두고 패스키로 한 번 더 확인한다
 
- 날짜: 2026-11-07
- 상태: 승인 (2026-11-07, 정현)
- 작성: 초안은 멘토 AI, 검토·승인은 정현
- 검토: 11/7 멘토의 최대 노력 검토를 반영했다. 바뀌거나 더한 곳은 "(검토)"로 표시했다. 요약은 "정현의 판단"의 "검토" 항목에 있다.
> **쉽게 말하면**
> 1. v1 로그인은 이메일·비밀번호로 한다. 가입 인증 메일과 비밀번호 재설정 메일이 함께 들어온다. 카카오·구글 로그인은 시간이 되면 v1에, 아니면 v2에 붙인다.
> 2. 로그인한 사람은 서버가 기억한다(세션). 기억은 Redis에 두고, 브라우저에는 번호표(`SESSION` 쿠키)만 준다. 자바스크립트는 이 번호표를 읽지 못한다. JWT는 쓰지 않는다.
> 3. 다른 사이트가 사용자의 브라우저를 시켜 요청을 보내는 공격(CSRF)은 쿠키의 `SameSite=Lax`와 CSRF 토큰 두 겹으로 막는다. Nginx 뒤에서도 Spring이 "원래 https로 왔는지, 원래 사용자 IP"를 읽게 설정한다.
> 4. 계정은 회원 / 로그인 방법 / 역할 / 제작자 프로필 네 조각으로 나눈다. 소셜 로그인을 나중에 붙여도 회원 테이블은 그대로다. 템플릿은 회원이 아니라 제작자 프로필에 묶는다.
> 5. 정현은 운영 계정과 공식 제작자 계정을 따로 쓴다. 운영 구역에 들어갈 때는 비밀번호에 더해 패스키(지문)로 한 번 더 확인한다. 패스키를 하나 더 등록할 때도 기존 패스키로 먼저 확인한다(검토).
> 6. 드롭은 "계정당 1개"이고, 이메일 인증을 마친 계정만 받는다(검토). 본인인증이 없으므로 한 사람이 계정을 여러 개 만드는 것은 막지 못한다.
 
## 맥락
 
- 화면과 API는 같은 출처에 있고, 프론트는 React SPA다. 운영 화면은 같은 앱 안의 구역이다(ADR-0005). 이 API를 쓰는 곳은 우리 웹 화면 하나다. 모바일 앱이나 외부 공개 API는 계획에 없다.
- API 계약은 코드에서 springdoc으로 뽑는다(ADR-0006). 에러 응답은 ProblemDetail이다(ADR-0004). 보안 구역 규칙은 `/api/*/admin/**` → `ADMIN`, `/api/*/studio/**` → `CREATOR`로 적어 두었다(ADR-0006).
- 운영은 NCP 서버 한 대 + compose이고, 앞에 Nginx를 둔다. HTTPS는 Nginx에서 끝나고 Spring은 http로 요청을 받는다. v1부터 K8s에 올릴 수 있는 앱(앱이 상태를 갖지 않음)으로 만든다(인계 문서 1의 6번).
- 기획 1에서 "소셜 로그인과 이메일·비밀번호를 함께 쓰고, JWT 여부는 실무 판단에 맡긴다"고 정했다. 전체 검토 1에서 v1이 무거워 로그인을 하나로 줄이는 안이 나왔다.
- 정현은 board에서 세션(formLogin), BCrypt, CSRF, Spring Session(Redis)을 써 봤다. OAuth2는 개념만 배웠고, JWT는 이 프로젝트로 미뤘다. board에서 Redis가 세션의 단일 장애점이 된다는 것과, CSRF 토큰을 세션에 두면 로그인하지 않은 사용자의 로그인 폼까지 Redis에 묶인다는 것을 실험으로 확인했다.
- 정현이 로그인하는 계정과 공개되는 공식 제작자 프로필을 분리하기로 했다(인계 문서 1의 4번). 저장소는 공개한다.
- 정현의 운영 접속 환경은 집(맥북, 윈도우 데스크탑)과 밖(맥북, 갤럭시 S25 울트라)이다.
- 기반은 Spring Boot 4.1이고, 함께 오는 Spring Security는 7.1이다(정확한 버전은 환경 구축 채팅에서 고정).
  - (검토) Spring Security는 7.1.1 이상이어야 한다(결정 5의 "버전과 사용자 확인"). Boot 4.1.0에 들어 있는 것은 7.1.0이다.
## 결정 1: v1 로그인은 이메일·비밀번호, 소셜(카카오·구글)은 시간이 되면 v1, 아니면 v2
 
- [확정] v1은 이메일·비밀번호로 한다. 가입 인증 메일과 비밀번호 재설정 메일을 포함한다. 메일(기획 2의 6번)은 v1에 남는다.
- [잠정: 기획 3] 소셜 로그인은 카카오·구글로 한다. 기획 3에서 주별 시간을 넣어 보고 되면 v1에, 아니면 v2의 첫 작업으로 붙인다. 최종 모양은 두 방식을 다 쓰는 것이다.
- [잠정] 네이버는 사이트 공개(M3) 뒤 검수를 받아 붙인다.
- 소셜을 붙일 때 카카오도 OpenID Connect를 켠다. 구글과 같은 방식으로 다루기 위해서다.
공급자 조건 (11/6 조사):
- 카카오
  - 필요한 설정은 REST API 키, 카카오 로그인 활성화, 리다이렉트 URI, 동의항목, OpenID Connect 활성화(선택)다.
  - 기본 로그인(닉네임·프로필 사진)에 따로 심사가 있다는 내용은 찾지 못했다 [확인 필요: 앱 등록 때 실제 화면에서].
  - 이메일은 본인인증 뒤 "개인 개발자 비즈 앱 전환"(설정)을 하면 선택 동의로 받을 수 있다. 사용자가 주지 않을 수 있으므로, 회원은 이메일이 아니라 카카오 회원번호로 구별한다(결정 4).
- 구글: 기본 정보(`openid`, `email`, `profile`)만 쓰면 앱 검증을 꼭 받지 않아도 된다. 동의 화면에 앱 이름과 로고를 띄우려면 더 가벼운 브랜드 검증을 받는다.
- 네이버: 검수를 받기 전에는 등록한 테스트 아이디만 로그인할 수 있다. 검수에는 운영 중인 사이트에서 로그인을 끝내기까지의 화면 캡처가 필요해서, 사이트가 공개된 뒤에야 신청할 수 있다.
선택지:
 
| | A. v1에 둘 다 | B. v1 이메일 → 소셜 (선택) | C. v1 소셜 → v2 이메일 |
| --- | --- | --- | --- |
| v1 입구 수 | 3 | 1 (+시간이 되면 2) | 2 |
| v1에 메일(6번) | 들어옴 | 들어옴 | 빠짐 |
| 비밀번호 보관 책임 | 있음 | 있음 | 없음 |
| 공급자 계정이 없는 사람 | 가입 가능 | 가입 가능 | v1에서 가입 못 함 |
| 계정 여러 개 만들기 | 이메일 쪽이 쉬움 | 가장 쉬움 | 조금 번거로움(막지는 못함) |
 
이유:
1. 공급자 계정이 없거나 쓰기 싫은 사람이 우리 서비스를 쓰지 못하는 일을 피한다. 이메일은 누구나 가진 입구다(정현의 판단).
2. 일정 때문에 줄여야 하면 소셜을 뒤로 미루고, 시간이 남으면 당긴다(일정 앞당기기 원칙). 결정 4의 계정 구조가 로그인 방법을 나중에 더할 수 있게 해 준다.
멘토의 추천은 C였다. 메일 묶음이 v1에서 빠지고 비밀번호 보관 책임이 없어지기 때문이었다. 정현이 위 이유로 B를 골랐다.
 
버린 선택지:
- **A를 처음부터**: v1이 가장 무겁다. 인계 문서 1의 11번이 첫 번째로 줄일 후보로 꼽았다. 시간이 되면 결과적으로 A가 된다.
- **C**: 공급자 계정이 없는 사람이 v1에서 가입하지 못한다.
- **D. 비밀번호 없는 이메일 로그인**(메일로 받은 링크로 로그인, Spring Security의 일회용 토큰 로그인): 비밀번호 보관은 없지만, 로그인할 때마다 메일이 와야 해서 메일 장애가 곧 로그인 장애가 된다.
감수하는 것:
- 비밀번호 해시를 보관하고, 유출된 비밀번호를 돌려 넣는 공격이 우리 로그인 API로 들어온다. 레이트 리밋(11번)의 무게가 커진다.
- 메일 서비스, 발신 도메인 설정, 비동기 발송·재시도(6번)가 설계 주간에 남는다.
- 계정을 여러 개 만들기 가장 쉬운 방식이다. 결정 4-5에서 규칙 문장을 "계정당 1개"로 고친다.
- (검토) 비밀번호 규칙(최소·최대 길이, 금지 목록)과 저장 방식(BCrypt 또는 Argon2id)은 11번에서 정한다. 넘겨줄 사실은 "결과"의 11번 항목에 적었다.
## 결정 2: 로그인 상태는 서버 세션 + Redis(Spring Session)로 기억한다. JWT는 쓰지 않는다
 
```
세션 (선택)
  로그인 응답   Set-Cookie: SESSION=Y2Q4…; Path=/; HttpOnly; Secure; SameSite=Lax
  다음 요청     Cookie: SESSION=Y2Q4…   (브라우저가 알아서 붙임)
  서버          Redis에 "Y2Q4… = 회원 7, 역할 [...]"을 물어봄
 
JWT (버림)
  로그인 응답   { "accessToken": "eyJ…" }   (서명된 "회원 7, ~22:15까지" 신분증)
  다음 요청     Authorization: Bearer eyJ…  (프론트 코드가 직접 붙임)
  서버          서명과 만료만 계산, 저장소를 보지 않음 → 만료 전에는 회수할 수 없음
```
 
- 세션 저장소는 Redis다(8번 안건 중 세션 부분). 앱은 상태를 갖지 않으므로 앱을 여러 개 띄워도 같은 세션을 읽는다.
- 유지 기간 [잠정: 숫자는 설계 주간]
  - 활동이 30분 없으면 만료한다(Spring 기본값, board와 같음).
  - 로그인할 때 "로그인 상태 유지"를 고르면 2주 유지한다. Spring Session의 로그인 유지 연동 기능으로 한다.
  - 활동과 관계없는 최대 수명(절대 만료)을 둘지도 설계 주간에 정한다.
  - 운영 계정은 결정 5를 따른다.
- 비밀번호를 변경·재설정하거나, 역할이 바뀌거나, 회원이 정지되면 그 회원의 세션을 모두 끊는다. Spring Session의 회원별 세션 찾기 기능(인덱스 저장소)을 쓴다.
  - (검토) 설정은 `spring.session.data.redis.repository-type=indexed`다. Boot 4에서 `spring.session.redis.*`가 `spring.session.data.redis.*`로 이름이 바뀌었으므로, Boot 3 시절 글의 이름을 쓰면 적용되지 않는다.
  - (검토) 이 저장소는 회원별로 찾기 위한 색인을 Redis에 더 둔다(8번의 메모리 계산).
선택지:
 
| | A. 세션 + Redis (선택) | B. JWT 액세스(짧게) + 리프레시(쿠키 + Redis) | C. JWT만 (회수 장치 없음) |
| --- | --- | --- | --- |
| 비밀번호 변경·정지 때 바로 끊기 | 됨 | 액세스 토큰 만료까지 기다리거나 취소 목록을 둠 | 안 됨 |
| 자바스크립트가 토큰을 읽나 | 못 읽음 | 액세스 토큰은 읽음 | 못 읽음(쿠키) |
| 앱이 상태를 갖지 않음 | 됨(상태는 Redis) | 됨 | 됨 |
| Redis 의존 | 모든 요청 | 재발급·로그아웃 (취소 목록을 두면 모든 요청) | 없음 |
| 직접 만들 것 | 거의 없음 | 발급, 재발급, 회전, 취소, 프론트 재시도 | 발급 |
| 어울리는 구조 | 같은 출처의 웹 화면 하나 | 모바일 앱, 여러 서비스, 다른 도메인 | 회수가 필요 없는 짧은 용도 |
 
이유:
1. (검토) OAuth 표준 문서가 이 구조를 인정한다. IETF의 RFC 10017(OAuth 2.0 for Browser-Based Applications, BCP 212, 2026년 8월)은 서론에서 화면과 API가 같은 도메인에 있으면 OAuth에 기대지 않는 구조가 가능하다고 하고, 이 경우를 문서의 범위 밖으로 둔다. 7.1절은 그런 앱이 액세스 토큰 대신 서버 쪽 쿠키 기반 세션 상태에 기댈 수 있다고 하고, 단순한 앱이 세션 관리를 대신하려고 OAuth를 써서 불필요하게 복잡해지는 경우가 많다고 경고한다.
   - 읽을 때 주의: 7.1절은 7장 "권하지 않거나 폐기된 구조" 안에 있어서 "세션 방식을 권하지 않는다"로 잘못 읽기 쉽다. 7.1의 제목은 "OAuth를 쓰지 않는 같은 도메인 앱"이고, 본문은 위와 같다. 같은 절은 OAuth를 쓰면 나중에 유연하다는 장점도 함께 적는다.
   - 초안은 이것을 "우리 구조에 대한 표준 권고"라고 썼다. 문서가 이 경우를 범위 밖으로 두므로 "인정한다"가 정확하다.
2. 즉시 끊을 수 있다. 결정 1로 비밀번호 로그인이 들어왔으므로, 비밀번호 재설정이나 계정 탈취 때 다른 기기의 로그인을 바로 끊어야 한다.
3. 세션 번호는 HttpOnly 쿠키에만 있어서, XSS(우리 페이지에 남의 스크립트가 끼어드는 공격)가 생겨도 번호를 들고 나갈 수 없다. OWASP도 세션 식별자를 local storage에 두지 말라고 한다.
   - (검토) 다만 XSS가 생기면, 그 스크립트는 페이지가 열려 있는 동안 사용자 대신 요청을 보낼 수 있다. 브라우저가 쿠키를 알아서 붙이기 때문이다. RFC 10017 5.1.4절은 이것을 앱 수준의 장치로는 막을 수 없다고 한다. HttpOnly는 피해를 그 시간 안으로 줄일 뿐이므로, XSS 자체를 막는 일(React의 기본 이스케이프, CSP 헤더)은 따로 한다(7번).
4. 실수할 곳이 적다. 발급·재발급·취소를 직접 만들지 않고 Spring Session과 Spring Security의 표준 동작을 쓴다. board에서 써 본 조합이다.
5. K8s 준비 원칙(앱이 상태를 갖지 않음)을 지킨다.
확인한 업계 사정: 국내 Spring 글과 신입 프로젝트에서는 JWT가 매우 흔하다. 회사들이 실제로 어느 쪽을 더 쓰는지 보여 주는 통계는 찾지 못했다. 세션에서 JWT로 바꾼 한 프로젝트는 리프레시 토큰을 Redis에 두고 모든 요청에서 Redis 취소 목록을 확인했다. JWT도 안전하게 쓰면 서버가 다시 상태를 갖게 된다.
 
유지 기간의 근거: OWASP는 흔한 유휴 만료 범위를 가치가 큰 애플리케이션 2~5분, 위험이 낮은 애플리케이션 15~30분으로 든다. NIST의 가장 낮은 단계는 전체 재인증 주기 30일 이하, 유휴 만료는 선택이다. 무료 템플릿 사이트는 위험이 낮은 쪽이다.
 
버린 선택지:
- **B**: 실무에서 흔하고 모바일 앱이나 여러 서비스에 맞는 방식이다. 우리 구조에서는 Redis를 그대로 쓰면서 직접 만들 것만 늘고, 즉시 끊기는 A보다 약하다.
- **C**: 비밀번호 로그인이 있는 서비스에서 로그인을 회수할 수 없다.
- **토큰을 localStorage에 두기**: 국내 글에서 흔히 보이지만, RFC 10017과 OWASP가 피하라고 하는 방식이다.
감수하는 것:
- Redis가 멈추면 로그인이 풀리거나 막힌다(board에서 확인). Redis의 재시작 정책과 재시작 뒤 세션 유지는 7·8번에서 정한다.
- 요청마다 Redis를 한 번 읽는다. 드롭 부하 테스트(12번)에서 실제 비용을 숫자로 본다.
- JWT를 직접 발급하는 경험은 이번에 없다.
  - 소셜을 붙이면 카카오·구글이 주는 ID 토큰이 JWT다. Spring이 공개키로 그 서명을 검증하는 과정을 보게 된다(로그인 순간에 서버끼리 한 번 쓰고, 그 뒤 API 인증은 세션 그대로).
  - JWT 발급은 모바일 앱, 외부 공개 API, v3 챗봇 도구를 MCP로 열 때 다시 본다. Spring Security 7에는 토큰을 발급하는 Authorization Server가 들어 있다.
## 결정 3: 쿠키·CSRF·로그인 API·프록시는 표준 설정을 따른다
 
```
브라우저 ──https──▶ Nginx ──http──▶ Spring
  쿠키 SESSION=Y2Q4…       (HttpOnly: 자바스크립트가 못 읽음)
  쿠키 XSRF-TOKEN=8f1c…    (자바스크립트가 읽음)
  헤더 X-XSRF-TOKEN: 8f1c… (프론트가 위 쿠키를 읽어 직접 붙임)
                           Nginx가 덮어쓰는 메모
                             X-Forwarded-Proto: https / X-Forwarded-For: 사용자 IP / X-Forwarded-Host
```
 
### 3-1 세션 쿠키
 
| 표시 | 값 |
| --- | --- |
| 이름 | `SESSION` (Spring Session 기본) |
| HttpOnly | 켬 |
| Secure | 운영: 켬(설정으로 고정) / 로컬: 끔 (http://localhost) |
| SameSite | `Lax` (Spring Session 기본) |
| Path | `/` |
 
- (검토) RFC 10017의 6.1.3.2절(BFF가 쓰는 쿠키의 규칙. 7.1절이 세션 쿠키 보호에 이 절을 가리킨다)은 HttpOnly와 Secure를 반드시 켜고, SameSite=Strict도 켜는 것이 좋다고 한다. 우리는 Strict 대신 **Lax**로 둔다.
  - 소셜 로그인을 붙이면 공급자에서 우리 사이트로 돌아오는 이동이 "다른 사이트에서 시작한 이동"이 된다. Strict면 이때 세션 쿠키가 붙지 않아, Spring이 로그인 시작 때 세션에 적어 둔 확인값(state)을 찾지 못하고 로그인이 실패한다. Okta를 쓰던 개발자가 같은 문제를 SameSite=lax로 바꿔 해결한 사례가 있다.
  - 우리 API 요청은 우리 페이지에서 나가는 같은 사이트 요청이라 Lax로도 쿠키가 붙는다. Strict가 더 막는 것은 다른 사이트에서 링크로 들어오는 GET 이동뿐이고, 우리 GET은 상태를 바꾸지 않는다(ADR-0006의 메서드 규칙).
  - 대신 CSRF 토큰(3-2)을 함께 쓴다. 공개 사례로 GitHub은 로그인 쿠키(`user_session`)와 별도로 요청이 GitHub에서 시작했는지 확인하는 쿠키(`__Host-user_session_same_site`)를 둔다.
- (검토) SameSite를 적지 않은 쿠키를 Lax로 다루는 것은 크롬·엣지이고, 파이어폭스(설정 뒤에 숨어 있음)와 사파리(지원 안 함)는 그렇지 않다. 그래서 브라우저 기본값에 기대지 않고 명시적으로 적는다(Spring Session의 기본값이 이미 Lax다).
### 3-2 CSRF
 
- CSRF 보호를 켜고, SPA 방식으로 쓴다: `http.csrf(csrf -> csrf.spa())`.
  - 서버가 `XSRF-TOKEN` 쿠키로 토큰을 주고, 프론트가 상태를 바꾸는 요청(POST·PUT·PATCH·DELETE)에 그 값을 `X-XSRF-TOKEN` 헤더로 돌려보낸다. 이름은 AngularJS의 관례를 따른 Spring의 기본값이다.
  - 다른 사이트는 우리 쿠키를 읽을 수 없어서(같은 출처 정책) 이 헤더를 만들 수 없다.
- 토큰은 쿠키에 둔다. 세션에 두지 않으므로, CSRF 때문에 로그인하지 않은 방문자에게 세션이 생기지는 않는다.
- (검토) **요청 저장을 끈다.** 위 줄만으로 익명 세션이 0이 되지는 않는다.
```
로그인하지 않은 봇 ── GET /api/v1/me ──▶ Spring: 401
                                         + "로그인 뒤 여기로 돌려보내자"며 이 요청을 세션에 저장
                                           → 세션이 새로 생겨 Redis에 30분 남음
```
 
  - Spring Security는 로그인하지 않은 사람이 보호된 주소를 GET으로 부르면, 로그인 뒤 그 주소로 돌려보내려고 요청을 세션에 저장한다(요청 저장, `HttpSessionRequestCache`. 세션을 새로 만드는 것이 기본값). `Accept: application/json`이나 `X-Requested-With` 헤더가 붙은 요청은 빼지만, 이 헤더가 없는 요청(헤더를 정하지 않은 `fetch`, 봇)은 저장된다.
  - SPA는 로그인 뒤 어디로 갈지를 스스로 정하므로 이 저장이 필요 없다. `http.requestCache(c -> c.requestCache(new NullRequestCache()))`로 끈다. Spring 문서는 `NullRequestCache`를 세션 생성을 원하지 않을 때 쓰는 구현이라고 적는다.
  - 이렇게 하면 board에서 겪은 "Redis가 죽으면 로그인 폼도 실패"가 생기지 않는다. 로그인하지 않은 사람에게 세션이 생기는 곳은 패스키 확인 준비(결정 5)와, 나중의 소셜 로그인 시작뿐이다.
- (검토, [확인 필요]를 풂) 로그인·로그아웃 뒤의 CSRF 쿠키
  - 로그인에 성공하면 Spring Security는 기존 CSRF 쿠키를 지우고 새 토큰을 미뤄서 만든다. SPA용 처리기는 요청마다 미뤄 둔 토큰을 꺼내므로, 로그인 응답에 새 `XSRF-TOKEN` 쿠키가 바로 실린다. 패스키 확인(결정 5)도 같다.
  - 로그아웃은 쿠키를 지운다. 다음 요청(아무 GET)의 응답에 새 쿠키가 실린다.
  - 그래서 프론트는 토큰을 앱 시작 때 한 번 읽어 두지 않고, **요청마다 쿠키에서 읽어** 헤더에 붙인다. 3-3의 테스트 2로 확인한다.
선택지:
- A. CSRF 켜고 SPA 방식 (선택)
- B. CSRF 끄고 SameSite만: OWASP는 토큰 기반 방어를 주된 방어로 권하고, SameSite 같은 보조 수단을 단독으로 쓰지 말라고 한다. Spring Security 책임자(rwinch)도 SameSite가 하위 도메인이나 오래된 브라우저를 막지 못한다며 토큰을 대체하게 두면 안 된다고 했다. 국내 JWT 글에서 `csrf.disable()`이 흔한 것은 토큰을 Authorization 헤더로 보내기 때문이고, 쿠키를 쓰는 우리에게는 해당되지 않는다.
- C. 토큰을 세션에 저장(board 방식): 로그인하지 않은 방문자마다 Redis에 세션이 쌓인다.
### 3-3 로그인·로그아웃·내 정보 API
 
```
로그인     POST  (이메일, 비밀번호, 로그인 상태 유지)
           → 204 + 새 SESSION 쿠키 (+ 새 XSRF-TOKEN 쿠키)
           → 401 LOGIN_FAILED  "이메일 또는 비밀번호가 맞지 않습니다."
             (계정이 없는지, 비밀번호가 틀렸는지, 계정이 정지됐는지 구분하지 않음: 가입된 이메일을 캐내지 못하게)
로그아웃   POST  → 204. 서버에서 세션 삭제, 쿠키 지움
내 정보    GET   → 200 { id, nickname, roles } / 401
           (프론트가 처음 뜰 때 호출. roles는 메뉴를 보여 줄지 정하는 데만 쓰고, 진짜 문은 서버)
```
 
- 주소 이름은 설계 주간에 정한다.
- `/api` 아래의 401·403은 로그인 페이지로 보내지 않고(302 금지) ProblemDetail로 답한다(ADR-0004 결정 3의 6번). 코드 후보는 `UNAUTHENTICATED`(401 → 프론트는 로그인 화면), `ACCESS_DENIED`(403), `CSRF_TOKEN_INVALID`(403 → 프론트가 토큰을 새로 받고 한 번만 다시 시도), 결정 5의 추가 인증 요구 코드다. 이름은 설계 주간에 정한다.
  - (검토) [잠정: 설계 주간] 추가 인증 요구는 401로 답한다. 로그인은 했지만 인증이 "부족한" 경우라서, OAuth의 단계 올리기 표준(RFC 9470)도 이 경우에 401과 `insufficient_user_authentication`을 쓴다. 401이 두 가지가 되므로 프론트는 상태 코드가 아니라 `code`로 화면을 나눈다.
- (검토) **로그인 실패는 이유와 관계없이 모두 같은 401로 답한다.**
  - Spring의 기본 순서는 계정 상태(잠김·비활성·만료) 검사를 비밀번호 검사보다 **먼저** 한다. 상태마다 다른 문구를 내면, 비밀번호를 몰라도 "이 이메일은 정지된 계정"이라는 것을 캐낼 수 있다.
  - Spring도 이 상태 값을 쓸 때 응답 시간 차이로 상태가 드러나는 문제를 보안 공지(CVE-2026-22746, 7.0.5에서 고침)로 다뤘다. 시간 차이는 Spring이 막고, 문구 차이는 우리가 막는다.
  - 정지된 사람에게 "정지된 계정"이라고 알려 주고 싶다면, 비밀번호가 맞은 뒤에만 알려 준다(설계 주간).
- (검토) **가입과 비밀번호 재설정도 이메일이 가입되어 있는지 드러내지 않는다.** (정현 동의 11/7, 문구는 설계 주간)
  - 재설정: 주소와 관계없이 "메일을 보냈습니다"로 답한다. 가입된 주소에만 실제 메일이 간다.
  - 가입: 언제나 "인증 메일을 보냈습니다"로 답한다. 이미 가입된 주소면 그 주소로 "이미 가입되어 있습니다(로그인·비밀번호 재설정 안내)" 메일을 보낸다.
  - 이유: 로그인만 같게 답하고 가입에서 "이미 가입된 이메일입니다"라고 알려 주면, 로그인 쪽의 노력이 소용없어진다. OWASP의 점검 지침은 가입·재설정 화면도 계정 캐내기 점검 대상으로 둔다.
  - 버리는 것: 국내 가입 화면에서 흔한 이메일 "중복 확인" 버튼.
  - [잠정: 설계 주간] 메일에 "본인이 아니라면" 안내를 넣는다(정현의 제안). 메일 종류에 따라 문구를 나눈다.
    - 아무것도 바뀌지 않은 메일("이미 가입되어 있습니다", 요청하지 않은 재설정 메일): 남이 주소를 넣었을 뿐 계정은 안전하다. "본인이 아니라면 무시해도 됩니다. 걱정되면 비밀번호를 바꿀 수 있습니다"로 쓴다.
    - 실제로 무언가 바뀐 메일(비밀번호 변경 알림, 패스키 등록 알림): "본인이 아니라면 바로 비밀번호를 재설정하세요"로 쓴다.
  - [잠정: 설계 주간] 비밀번호가 바뀌면 그 회원에게 알림 메일을 보낸다(위 문구).
- [잠정: 첫 주 뼈대] 로그인은 Spring Security의 **표준 로그인 필터**를 성공·실패 처리만 바꿔서 쓴다.
  - 세션 ID 바꾸기(세션 고정 공격 방지), CSRF 토큰 교체, 로그인 유지를 필터가 자동으로 한다. 컨트롤러에서 직접 인증하면 이것들을 직접 챙겨야 하고, 빠뜨리면 보안 구멍이 된다.
  - 요청 본문은 폼 형식(`application/x-www-form-urlencoded`)이다.
  - 로그인·로그아웃은 컨트롤러가 아니라 필터라서 계약(ADR-0006)에 자동으로 실리지 않는다. springdoc의 `show-login-endpoint` 설정으로 나오는 자동 항목은 요청·응답이 자세하지 않으므로, **OpenApiCustomizer로 두 항목을 직접 적는다.** 손으로 적은 항목은 "계약의 원본은 코드"의 작은 예외다. 패스키 주소도 같은 방식으로 적는다(결정 5, 검토).
  - Spring이 그려 주는 기본 로그인 페이지는 끈다(화면은 우리 SPA).
  - 뼈대에서 아래 테스트를 통과시키는 것으로 확정한다.
    1. 로그인 뒤 세션 ID가 바뀐다.
    2. 로그인 뒤 새 CSRF 토큰으로 POST가 된다.
    3. 없는 이메일과 틀린 비밀번호의 응답이 같다.
    4. (검토) 정지된 계정에 틀린 비밀번호를 넣은 응답도 3과 같다.
    5. (검토) 로그인하지 않고 보호된 주소를 GET으로 불러도 `SESSION` 쿠키가 생기지 않는다(3-2).
### 3-4 프록시 뒤의 원래 요청 정보
 
- 설정이 없으면 세 가지가 틀어진다.
  1. Spring Session은 Secure 여부를 "이 요청이 https인가"로 정하는데, Spring이 보기엔 http라 Secure가 빠진다.
  2. 소셜 로그인의 돌아올 주소를 `http://…`로 만들어 공급자가 거절한다.
  3. 로그와 레이트 리밋(11번)에 사용자 IP 대신 Nginx의 IP가 찍힌다.
- Nginx(네트워크 맨 앞)는 밖에서 들어온 `X-Forwarded-*`를 자기 값으로 덮어쓴다. Spring Security 문서도 맨 앞의 프록시가 밖에서 온 forwarded 헤더를 지우거나 덮어쓰라고 한다. ADR-0006의 `traceparent` 지우기와 같은 원칙이다.
- Spring은 `server.forward-headers-strategy=native`로 둔다. 내장 Tomcat의 RemoteIpValve가 메모를 읽고, 믿는 프록시는 기본값이 내부 IP 목록이다. compose 안의 Nginx는 내부 IP라 믿고, 밖에서 바로 온 요청의 메모는 믿지 않는다. `framework` 방식만의 장점(`X-Forwarded-Prefix`)은 우리에게 필요 없다.
- (검토) 이 설정은 "Spring에 오는 요청은 모두 Nginx를 거친다"는 전제 위에 있다. Spring의 포트는 서버 밖으로 열지 않는다(7번).
- 운영의 세션 쿠키 Secure는 메모와 별개로 설정에서도 켜 둔다(두 겹).
- 첫 배포 때 확인한다: 응답 `Set-Cookie`에 `Secure`가 있는지, 로그에 실제 사용자 IP가 찍히는지.
- 앞에 CDN을 두면 믿을 프록시 목록이 바뀐다(7번).
### 3-5 소셜 로그인 주소 [잠정: 소셜을 붙일 때]
 
- Spring의 기본 주소(`/oauth2/authorization/{공급자}`, `/login/oauth2/code/{공급자}`)는 `/api` 밖이다. 그대로 두면 Nginx·Vite 규칙을 더해야 하고, 빠뜨리면 화면 파일(`index.html`)로 빠지는 함정이 생긴다(ADR-0005).
- 두 주소를 `/api` 아래로 옮긴다(예: `/api/v1/auth/oauth2/…`). Spring은 두 기본 경로를 설정으로 바꿀 수 있다. 그러면 소셜 로그인 때문에 "Nginx와 Vite는 `/api`만 Spring으로"라는 규칙이 깨지지 않는다. 공급자 콘솔에 등록하는 돌아올 주소도 이 경로로 적는다.
  - (검토) 패스키 주소는 바꿀 방법이 없을 수 있어 이 규칙의 예외가 될 수 있다(결정 5의 "패스키 주소").
- 이것은 업계 표준이 아니라 우리 구조를 위한 선택이다. Spring 기본 주소를 그대로 쓰는 경우가 더 흔하다.
## 결정 4: 계정은 회원 / 로그인 방법 / 역할 / 제작자 프로필로 나누고, 운영 계정과 공식 제작자 계정을 따로 둔다
 
### 4-1 네 조각
 
```
회원 (member)              사이트 안의 사람 한 명. 닉네임, 상태(활동·정지·탈퇴)
 ├─ 로그인 방법 (여럿)      이메일+비밀번호 / (소셜) 카카오 회원번호 / 구글 회원번호
 ├─ 역할 (여럿)             CREATOR → /studio, ADMIN → /admin
 └─ 제작자 프로필 (0~1개)   공개 화면에 "만든 사람"으로 보이는 카드: 이름, 소개, 공식 배지
 
템플릿 ──▶ 제작자 프로필에 묶음 (회원에 직접 묶지 않음)
```
 
- 로그인 방법을 회원과 처음부터 나눈다. 소셜을 붙일 때 회원 테이블은 바뀌지 않고 소셜 로그인 정보만 더해진다.
  - board에서 소셜 로그인을 미룬 이유가 "비밀번호 nullable화 등 회원 스키마 변경 비용"이었다.
  - Supabase Auth도 identity를 "사용자와 연결된 인증 방법 하나"로 두고, 한 사용자가 여러 identity를 가질 수 있게 한다. 외부 로그인은 이메일 대신 공급자 회원번호를 기본 식별자로 쓴다.
- 이메일 로그인 정보: 이메일(중복 불가), 비밀번호 해시, 이메일 인증 시각
- (검토) [잠정: 첫 주 뼈대] 로그인 이름(Spring의 `getName()`)은 이메일로 둔다. 세션 찾기(결정 2), 패스키의 사용자 이름, 두 요소 합치기(결정 5)가 모두 이 값에 묶인다. 이메일 변경 기능을 넣을 때 셋을 함께 다시 본다.
- 소셜 로그인 정보: 공급자 + 공급자 회원번호(중복 불가)로 찾는다. 이메일로 찾지 않는다.
- [잠정: 소셜을 붙일 때] 이메일이 같다고 자동으로 합치지 않는다. 로그인한 상태에서 "카카오 연결하기" 같은 동작으로만 묶는다.
  - Ory는 자동 합치기가 이메일 같은 외부 속성을 같은 사람이라는 증거로 쓰기 때문에 위험하다고 하고, NextAuth.js는 이 기능에 `allowDangerousEmailAccountLinking`이라는 이름을 붙였다.
  - Supabase도 인증되지 않은 이메일로 자동으로 합치는 것은 계정 탈취로 이어질 수 있다고 한다.
- 테이블 수와 칸 이름은 설계 주간의 ERD에서 정한다. 결정 5의 패스키 테이블 둘도 여기에 들어간다.
### 4-2 역할
 
- 한 회원이 여러 역할을 가질 수 있는 목록으로 둔다. 이름은 `CREATOR`, `ADMIN`이다(ADR-0006 그대로).
- 일반 회원에게는 역할을 주지 않고 "로그인함"으로 판단한다.
- ADMIN이 CREATOR를 자동으로 포함하지 않는다(역할 사이에 위아래가 없음).
- 역할이 바뀌면 그 회원의 세션을 끊는다. 세션에는 로그인할 때의 역할이 담겨 있어서, 끊지 않으면 다음 로그인까지 옛 권한이 남는다(결정 2의 장치).
- **ADMIN은 화면에서 줄 수 없다.** 운영 계정은 일반 가입을 한 뒤 운영 서버에서 런북의 절차로 역할을 붙인다. 공개 저장소이므로 코드와 마이그레이션에 운영 계정의 이메일·비밀번호를 넣지 않는다.
### 4-3 제작자 프로필
 
- 템플릿은 제작자 프로필에 묶는다. 공개 API는 제작자 이름과 공식 배지만 내보내고, 회원 정보(닉네임, 이메일)는 내보내지 않는다.
- 회원 하나에 제작자 프로필은 0개 또는 1개다. v2에서 제작자가 늘어도 같은 모양이다.
- "공식"은 제작자 프로필의 표시 하나다(배지).
### 4-4 운영 계정과 공식 제작자 계정을 따로 둔다
 
```
운영 계정        역할: ADMIN만       이메일: 새로 만든 구글 메일   로그인 유지 없음, 패스키 필수(결정 5)
공식 제작자 계정  역할: CREATOR       공식 제작자 프로필 소유        /studio에서 템플릿 등록·수정
흐름: 제작자로 등록(/studio) → 운영으로 공개(/admin)   (v2의 "공개 전 검수"와 같은 흐름)
```
 
선택지:
 
| | A. 로그인 계정 하나 | B. 로그인 계정 둘 (선택) |
| --- | --- | --- |
| 모양 | 회원 하나에 ADMIN + CREATOR + 공식 제작자 프로필 | 운영 계정(ADMIN) + 공식 제작자 계정(CREATOR + 공식 프로필) |
| 평소 세션(2주 유지, 휴대폰 포함)에 운영 권한 | 있음. 결정 5의 추가 인증에만 기댐 | 없음. 운영 세션은 운영할 때만, 짧게 |
| v2 제작자 화면 미리 써 보기 | 운영 권한이 섞인 제작자로 써 봄 | 다른 제작자와 같은 권한으로 써 봄 |
| 기록 | 운영 작업과 일반 활동이 한 회원에 섞임 | 운영 작업은 운영 계정에만 남음(v2 감사 로그와 맞음) |
| 불편 | 없음 | 계정을 오감. 브라우저 프로필을 둘로 나누면 거의 없음 |
 
이유:
1. 보안 지침의 기본 원칙(최소 권한)이다.
   - 벨기에의 CyberFundamentals는 누구도 일상 업무에 관리자 권한을 쓰지 않아야 하고, 관리자 계정과 사용자 계정을 분리하라고 한다.
   - UC 산타바버라의 IT 지침은 이 요건이 SaaS 서비스에도 적용된다고 적었다.
   - 미국 에너지부 자료는 일상 업무용 계정과 관리 작업용 계정을 따로 두고, 모든 권한 계정에 다단계 인증을 걸라고 한다.
   - 이 지침들은 회사 IT를 위한 것이고, 우리 사이트에 그대로 적용되는 규정은 아니다. 같은 원칙을 옮겨 오는 것이다.
2. 큰 회사는 운영(백오피스) 계정을 고객 계정과 아예 다른 체계로 둔다(ADR-0005). B는 그것의 작은 판이다.
3. 공식 계정이 v2 제작자들이 쓸 제작자 화면을 같은 권한으로 먼저 써 본다(인계 문서 1의 4번).
버린 선택지:
- **A**: 틀린 선택은 아니다. 작은 서비스에서는 계정 하나에 역할을 주고 운영 구역에 들어갈 때만 다시 인증하는 방식도 흔하다. 데이터 모양이 같아서 나중에 바꾸기 쉽다.
- **계정 전환 기능**(스팀처럼 기억된 계정을 골라 바로 전환): 정현이 물어 검토했다.
  - 운영 계정을 자동 전환 목록에 넣으면 B의 장점이 사라진다.
  - Spring Security는 세션 하나에 로그인 한 명이 기본이라 동시 로그인형은 직접 만드는 큰 기능이다.
  - 정현이 생각을 바꿔 넣지 않기로 했다. 브라우저 프로필과 패스키의 계정 선택 화면(결정 5)으로 대신한다.
감수하는 것: 이메일이 둘 필요하다(운영 계정용 구글 메일을 새로 만든다). 학교 메일은 졸업 뒤 없어질 수 있어서 운영 계정에 쓰지 않는다.
 
### 4-5 드롭은 "계정당 1개"
 
인계 문서 1의 4번과 용어 사전의 "1인 1개"를 아래 문장으로 바꾼다.
 
> 드롭은 계정당 1개이고, 이메일 인증을 마친 계정만 받을 수 있다. 본인인증이 없으므로 한 사람이 계정을 여러 개 만드는 것은 막지 못한다. 이메일 인증은 "메일을 받을 수 있는 주소"를 요구할 뿐이고, 구글 메일은 점(.)이나 +태그만 바꿔도 같은 메일함으로 오므로 이 수고는 작다.
 
- (검토) 초안의 문장("가입 때 이메일 인증으로 계정을 만드는 수고를 조금 높일 뿐이다")은 미인증 계정이 드롭을 받을 수 없을 때만 맞다. 그래서 "인증을 마친 계정만"을 규칙 문장에 넣었다. 구글 메일의 점은 무시되고(구글 도움말), +뒤의 글자도 무시되어 같은 메일함으로 온다.
- (검토) 미인증 계정은 로그인은 되고, 라이브러리 추가와 드롭 받기만 막는다(정현 동의 11/7). 답은 403 + 코드(예: `EMAIL_NOT_VERIFIED`, 이름은 설계 주간)다.
  - 인증 메일 다시 보내기를 로그인한 화면에서 할 수 있다. 로그인 전 화면에서 이메일을 받아 다시 보내 주는 주소를 만들면, 그 주소가 다시 계정 캐내기와 메일 폭탄의 통로가 된다.
  - 미인증을 Spring의 `isEnabled`로 막지 않는다. 그 값은 비밀번호보다 먼저 검사되어(3-3) 로그인 실패 문구로는 이유를 알려 줄 수 없다.
  - 버리는 것: 인증 전에는 로그인 자체를 막는 방식(Supabase Auth의 기본값). Supabase도 미인증 로그인을 허용하고 인증 여부로 권한을 나누는 설정을 따로 둔다.
- 소셜 로그인도 이것을 막지 못한다. 카카오 계정은 이메일만으로도 만들 수 있고, 전화번호가 없는 계정도 카카오 로그인이 된다.
- 사람 단위로 막으려면 휴대폰 본인인증 같은 별도 장치가 필요하고, 이번 범위 밖이다.
- (검토) [설계 주간] 함께 정할 것
  - 탈퇴한 뒤 같은 이메일로 다시 가입하면 드롭을 다시 받을 수 있는가. 막으려면 탈퇴 뒤에도 무언가를 남겨야 하고, 그 보관은 개인정보처리방침과 맞춰야 한다 [확인 필요].
  - 중복 검사에 구글 메일의 점·+태그를 정리한 주소를 쓸지. 쓰면 같은 메일함의 계정 여러 개를 막지만, 다른 메일 서비스에는 규칙이 다르다.
## 결정 5: 운영 구역은 비밀번호 + 패스키를 항상 요구한다
 
```
운영 계정
1) 이메일·비밀번호 로그인        → 세션: [ADMIN, FACTOR_PASSWORD]
2) /api/v1/admin/** 호출          → 규칙: ADMIN + FACTOR_PASSWORD + FACTOR_WEBAUTHN 필요
                                    → 없으면 추가 인증 요구 코드(401) → 프론트가 패스키 창을 띄움
3) 지문 (맥북 Touch ID / 갤럭시 지문 / 윈도우)  → 세션에 [FACTOR_WEBAUTHN] 추가
4) 운영 API 사용
```
 
```
패스키 등록 (검토, 운영 계정만)
  패스키 0개 (처음 등록·비상 절차, 런북 안에서만)   비밀번호 로그인 → 등록 → 1개인지 확인
  패스키 1개 이상                                   비밀번호 + 기존 패스키 확인 → 새 패스키 등록
  등록되면                                          운영 메일로 알림 [잠정]
```
 
- Spring Security 7의 다단계 인증으로 운영 구역(`/api/*/admin/**`)에만 건다.
  - 공식 문서에 `/admin/**`에 여러 요소와 `ROLE_ADMIN`을 함께 요구하는 예가 있다. 그 예의 둘째 요소(메일 일회용 토큰)를 패스키로 바꾼 것이 우리 규칙이다.
  - (검토) [잠정: 첫 주 뼈대] 모양: `@EnableMultiFactorAuthentication(authorities = {})`로 기능만 켜고(전체에는 걸지 않음), 운영 규칙은 `AuthorizationManagerFactories.multiFactor().requireFactors(FACTOR_PASSWORD, FACTOR_WEBAUTHN)`로 만든 규칙의 `hasRole("ADMIN")`이다.
  - (검토) ADR-0006의 `/api/*/admin/**` → `hasRole("ADMIN")` 줄은 이 규칙으로 바뀐다. ADR-0006 본문은 고치지 않고 여기서 넓힌다.
  - (검토) 운영 역할이 없는 회원은 "추가 인증 요구"가 아니라 403을 받아야 한다(ADR-0006의 403 테스트). 역할과 요소가 함께 빠졌을 때 Spring이 어느 쪽으로 답하는지 확인하고 테스트로 묶는다 [확인 필요: 첫 주 뼈대].
  - 문서에는 "패스키를 등록한 사람에게만" 요구하는 조건 옵션도 있다. 운영 구역에는 그 옵션을 쓰지 않는다. 등록 전에는 비밀번호만으로 들어가는 구멍이 생기기 때문이다. 운영 구역에는 **항상** 요구한다. (검토) 이 조건은 아래 "패스키 등록"에 쓴다.
- 패스키는 Spring Security 내장 기능을 쓴다. 저장은 `JdbcPublicKeyCredentialUserEntityRepository`와 `JdbcUserCredentialRepository`로 한다(ERD에 테이블 둘).
- (검토) **패스키 등록** (초안의 "처음 등록" 줄을 바꿈)
  - 초안은 처음 등록만 적고, 등록 주소를 누가 부를 수 있는지는 적지 않았다. Spring의 기본은 "로그인한 사람이면 자기 패스키를 등록할 수 있다"이다. 그대로면 운영 계정의 비밀번호만 훔친 사람이 자기 기기의 패스키를 더해 둘째 요소를 통과한다. 결정 5 전체가 무너지는 구멍이다.
  - 규칙: 패스키 등록은 운영 계정(ADMIN)만 한다. 패스키가 이미 있으면, 새 패스키를 더하기 전에 기존 패스키로 확인한다(`FACTOR_WEBAUTHN`). Spring의 "패스키를 등록한 사람에게만" 조건이 바로 이 모양이라, 운영 구역 대신 등록 주소에 쓴다 [확인 필요: 첫 주 뼈대, 이 조건을 등록 주소에만 거는 방법].
  - 패스키가 0개인 상태는 런북 절차 안에서만 생긴다(처음 등록, 모두 잃었을 때). 운영 역할을 붙이거나 패스키 기록을 지운 그 자리에서 바로 등록하고, 등록된 패스키가 1개인지 확인한다.
  - [잠정] 패스키가 등록되면 운영 메일로 알림을 보낸다. 모르는 등록을 바로 알아챈다.
  - 테스트: 패스키가 있는 운영 계정이 비밀번호만 마친 상태로 새 패스키를 등록하면 막힌다. 운영 계정이 아닌 회원은 패스키를 등록할 수 없다.
- (검토) **패스키 주소**
  - Spring의 패스키 주소(`POST /webauthn/register/options`, `POST /webauthn/register`, `POST /webauthn/authenticate/options`, `POST /login/webauthn`)는 `/api` 밖이고, 로그인처럼 필터라서 계약에도 실리지 않는다. 그대로면 Nginx가 Spring으로 보내지 않아 운영에서 패스키가 동작하지 않는다(ADR-0005).
  - 7.1의 패스키 설정 목록에는 rpId·이름·허용 출처·기본 등록 페이지 끄기 등이 있고, 주소를 바꾸는 항목은 보이지 않는다.
  - [잠정: 첫 주 뼈대] 주소를 `/api` 아래로 옮길 방법이 없으면, Nginx·Vite에 `/webauthn/`로 시작하는 주소와 `/login/webauthn`만 더한다(3-5 규칙의 예외). 어느 쪽이든 로그인·로그아웃처럼 OpenApiCustomizer로 계약에 적는다.
  - 넷 모두 POST라 CSRF 헤더가 필요하다. 준비 주소는 확인값(challenge)을 세션에 저장한다. 그래서 패스키 확인 준비는 로그인 전에도 세션을 만든다(11번 레이트 리밋 대상).
  - Spring이 그려 주는 기본 등록 페이지는 끈다(화면은 우리 SPA).
  - 패스키의 사이트 식별자(rpId)와 허용 출처는 환경마다 다르다(로컬은 `localhost`와 Vite 주소, 운영은 도메인). 설정으로 밖에서 넣는다. 로컬에서 만든 패스키는 운영에서 쓰지 못한다.
- (검토) **두 요소를 합친 뒤의 세션**
  - 패스키 확인이 끝나면 Spring은 패스키 쪽 인증 객체에 두 요소의 권한을 합쳐 세션에 둔다. 그래서 세션의 principal(로그인한 사람을 나타내는 객체)이 우리 회원 객체에서 패스키의 사용자 정보로 바뀐다.
  - 그러므로 컨트롤러는 principal을 우리 클래스로 형변환하지 않고, 이름(`getName()`)으로 회원을 찾는다(결정 4-1). 형변환하면 운영 계정만 패스키 확인 뒤 `/me` 같은 API가 깨진다.
  - 합치기는 두 요소의 이름이 같을 때만 일어난다(7.0.0-RC2에서 고친 #18112). 로그인한 상태에서 패스키를 등록하므로 같은 이름이 된다 [확인 필요: 아래 "두 요소가 남는다" 테스트로].
- (검토) **버전과 사용자 확인**
  - Spring Security 7.1.0에는 패스키의 사용자 확인(지문·PIN) 요구가 Redis 같은 분산 세션 저장소를 거치면 조용히 꺼지는 취약점(CVE-2026-47841, 2026-08)이 있다. 7.1에서는 7.1.0만 영향 범위이므로 **7.1.1 이상**을 쓴다. Boot 4.1.0에는 7.1.0이 들어 있다.
  - [잠정] 운영 패스키는 사용자 확인을 "필수"로 둔다. 기기를 훔쳐도 지문·PIN 없이는 쓸 수 없다. 위 취약점은 "필수"로 둔 앱에만 해당한다.
  - 패스키 객체를 Redis 세션에 넣는 것(직렬화)은 6.x와 7.0 초기에 실패했고, 7.1.0에서 고쳐졌다. 테스트: 패스키 확인을 거친 세션이 실제 Redis에 저장되고 다시 읽힌다. 가짜 세션으로 하는 테스트는 저장을 거치지 않아 이 문제를 잡지 못한다.
- 운영 세션 [잠정: 숫자는 설계 주간]
  - "로그인 상태 유지"를 쓸 수 없다.
  - 활동이 없을 때 만료를 짧게 둔다(OWASP의 가치가 큰 애플리케이션 범위 쪽으로).
  - 패스키 인증이 얼마나 최근이어야 하는지(Spring Security의 유효 기간 지정)도 함께 정한다.
  - 운영 계정으로 라이브러리 추가 같은 일반 활동은 하지 않는다.
  - (검토) 이 규칙은 서버가 강제한다. 화면에서 체크박스를 숨기는 것만으로는, 요청에 "로그인 상태 유지" 값을 직접 넣으면 뚫린다. 테스트: 운영 계정이 "로그인 상태 유지"를 보내도 세션 유지 시간이 늘지 않는다. 운영 세션에 짧은 유휴 만료가 걸린다.
- 패스키 인증이 빠진 상태로 운영 API를 부르면, 프론트가 패스키 창을 띄울 수 있게 별도 코드로 답한다(예: `ADDITIONAL_FACTOR_REQUIRED`, 이름은 설계 주간). Spring의 기본 동작은 그 요소의 로그인 페이지로 보내는 것이라 API용으로 바꾼다. (검토) 빠진 요소마다 처리를 정하는 Spring의 `DelegatingMissingAuthorityAccessDeniedHandler` 설정으로 바꾸고, 상태 코드는 401이다(3-3).
- 기기와 복구
  - 구글 비밀번호 관리자는 패스키를 안드로이드 크롬과 macOS·Windows·Linux의 크롬 사이에 동기화한다. 갤럭시 S25 울트라에서 한 번 등록하면 맥북과 윈도우의 크롬(같은 구글 계정)에서도 쓴다.
  - (검토) 패스키는 정현의 **개인 구글 계정**(기기에 이미 로그인된 계정)에 저장하고, 운영 메일(새 구글 메일)과 섞지 않는다. 운영 메일은 비밀번호 재설정 메일을 받으므로 첫째 요소를 지키고, 개인 구글 계정은 둘째 요소를 지킨다. 한 계정이 털려도 두 요소를 함께 잃지 않는다. **두 계정 모두** 2단계 인증을 켠다.
  - (검토) 운영 화면은 크롬으로 연다(구글 비밀번호 관리자의 패스키는 크롬 사이에서 동기화된다).
  - 기기 하나를 잃어도 동기화된 다른 기기로 들어온다. 모두 잃으면 운영 서버에서 그 계정의 패스키 기록을 지우고 다시 등록한다(런북의 비상 절차, 위 "패스키 등록"의 0개 상태 규칙).
- 패스키는 사이트마다 브라우저가 계정 목록을 띄워 준다. 계정 전환 기능 대신 이 선택 화면을 쓴다(결정 4-4).
- (검토, [확인 필요]를 풂) 7.0.0-RC2 시절에 패스키를 둘째 요소로 쓰면 `FACTOR_WEBAUTHN`이 기존 요소에 합쳐지지 않고 `FACTOR_PASSWORD`를 대체하는 버그 보고(#18128)가 있었다. 7.0.0 정식판의 변경 목록에 "Fix webauthn multifactor authentication"(#18163)이 있다. 테스트는 그대로 둔다: 비밀번호 → 패스키 순서로 인증한 뒤 두 요소가 모두 남는다.
선택지:
 
| | 가. 패스키 (선택) | 나. 인증 앱 코드 (TOTP) | 다. 메일 일회용 링크 (OTT) | 라. 접속 IP 제한 |
| --- | --- | --- | --- | --- |
| Spring 지원 | 내장 (패스키 + 다단계 인증 요소) | 문서에서 내장 요소를 찾지 못함 | 내장 | 설정 |
| 피싱 | 강함(브라우저가 진짜 도메인에서만 열쇠를 꺼냄) | 약함(가짜 사이트에 넣은 코드가 그대로 넘어감) | 약함 + 메일 계정 보안에 달림 | — |
| 정현의 기기 | 기기 셋 다(동기화) | 휴대폰 앱 | 어디서나 | 집 밖·휴대폰에서 못 씀 |
 
이유:
1. 피싱에 강한 방법이 운영 계정의 업계 기준이다. 미국 CISA는 FIDO/WebAuthn과 PKI 기반의 피싱에 강한 MFA를 권한다. Microsoft Entra ID 문서를 인용한 글은 관리 권한이 있는 계정이 공격자가 자주 노리는 대상이라 피싱에 강한 MFA를 요구하는 것이 위험을 줄이는 쉬운 방법이라고 한다.
2. Spring Security 7에 내장되어 있어 직접 만드는 보안 코드가 거의 없다(결정 2, 3과 같은 이유).
3. 정현의 기기 셋에서 모두 된다.
버린 선택지:
- **나. 인증 앱 코드**: 업계에서 여전히 흔하지만, 피싱에 약하고 Spring에 내장되어 있지 않다.
- **다. 메일 일회용 링크**: 운영 계정의 보호가 메일 계정의 보안과 메일 발송 상태에 달린다.
- **라. 접속 IP 제한**: 정현의 접속 환경(집 밖, 휴대폰)과 맞지 않는다.
- **운영 화면을 VPN 뒤로**: 큰 회사 방식(ADR-0005)이다. 이 규모에서는 과하고 휴대폰 접속이 번거롭다.
- **하드웨어 보안 키(YubiKey 등)**: 가장 강하지만 따로 사야 하고 기기 셋에서 쓰기 번거롭다. 나중에 패스키를 하나 더 등록하는 것으로 붙일 수 있다.
공개 범위 규칙의 조건(인계 문서 1의 11번)과의 대조:
 
| 조건 | 어디서 지키나 |
| --- | --- |
| 모든 운영 API에 서버 권한 검사와 그 테스트 | ADR-0006의 403 테스트 + "패스키 인증이 없는 운영 세션도 막힌다" 테스트 + (검토) "비밀번호만으로 패스키를 더할 수 없다" 테스트 |
| 관리 도구는 공개 도메인에 열지 않기 | 7·10번 |
| 운영 계정 보호 | 이 결정 |
| 로그인 레이트 리밋 | 11번 (M3 전) |
 
## 결과
 
- **인계 문서 1** (승인 때 반영)
  - 3번: 로그인 결정을 이 ADR로 바꾼다(v1 이메일·비밀번호, 소셜은 [잠정]).
  - 4번: 드롭 "1인 1개" → "계정당 1개, 이메일 인증을 마친 계정만", 공식 계정의 분리 방식(결정 4-4)
  - 5번 표: v1 받기 칸의 로그인을 "이메일·비밀번호(+소셜은 기획 3)"로
  - 10번: 5번 행과 "5 → 6, 8" 연결 갱신, 11번: v1 줄일 후보의 로그인 항목 갱신
- **6번(메일과 외부 호출)**: 그대로 설계 주간에 정한다. v1 메일은 가입 인증과 비밀번호 재설정이다. (검토) "이미 가입되어 있습니다" 안내 메일(3-3), 비밀번호 변경 알림(3-3), 패스키 등록 알림(결정 5)이 더해진다. "본인이 아니라면" 문구는 메일 종류에 따라 나눈다(3-3).
- **7번(운영 구성)**: Nginx가 `X-Forwarded-*`를 덮어쓰기, `/api`만 Spring으로(소셜 주소 포함), Redis 재시작 정책
  - (검토) 패스키 주소(`/webauthn/`, `/login/webauthn`)의 예외, Spring 포트를 밖으로 열지 않기, XSS 피해를 줄이는 CSP와 HSTS 헤더를 어디서 붙일지
- **8번(Redis)**: 세션 저장소가 Redis로 정해졌다. v1 서버에 Redis가 확실히 들어간다(7번 메모리 계산). Redis가 멈추면 로그인이 멈춘다는 것을 장애 표에 넣는다. (검토) 회원별 세션 찾기(인덱스 저장소)가 Redis에 색인을 더 둔다.
- **11번(레이트 리밋)**: 비밀번호 로그인이 공개되므로 로그인 레이트 리밋의 무게가 커진다. CDN을 두면 믿을 프록시 목록이 바뀐다.
  - (검토) 대상: 로그인, 가입, 재설정 메일 보내기(남의 메일함에 메일을 쏟아붓는 데 쓰이지 않게), 패스키 확인 준비(부를 때마다 세션이 생김)
  - (검토) 비밀번호 규칙과 저장 방식도 여기서 정한다. 넘겨줄 사실:
    - NIST SP 800-63B-4(2025)는 비밀번호만으로 로그인할 때 최소 15자, 다단계 인증의 한 요소일 때 최소 8자를 요구하고, 64자 이상 허용, 문자 조합 규칙 금지, 흔하거나 유출된 비밀번호 목록 검사를 요구한다. 일반 회원은 비밀번호만 쓰므로 15자 쪽이고, 운영 계정은 8자 쪽이다.
    - Spring의 BCrypt는 72바이트를 넘는 비밀번호를 거부한다(CVE-2025-22228을 고치며 생긴 동작). 한글은 한 글자가 3바이트라 24자면 72바이트다. "64자 이상 허용"과 부딪힌다.
    - OWASP는 새 시스템에 Argon2id를 먼저 권하고, BCrypt는 72바이트 제한을 지켜 쓰라고 한다.
    - 개인정보보호위원회의 "개인정보의 안전성 확보조치 기준 안내서"(2024-10)는 비밀번호를 일방향 암호화할 때 솔트를, 로그인 반복 실패에는 계정 잠금 외에 캡차·재시도 시간 제한 같은 방법을 든다.
- **12번(부하 테스트)**: 요청마다 Redis에서 세션을 읽는 비용을 숫자로 본다.
- **설계 주간**
  - ERD: 회원, 이메일 로그인 정보, 역할, 제작자 프로필, 패스키 테이블 둘(소셜 로그인 정보는 붙일 때)

  - 회원 가입 흐름(이메일 인증 전에 무엇을 할 수 있는지)은 6번과 함께. (검토) 미인증 계정에게 보여 줄 안내(4-5), 가입·재설정·알림 메일 문구(3-3), 탈퇴 뒤 재가입과 드롭, 구글 메일 주소 정리 여부, 정지된 사람에게 알려 주는 방법

  - 멘토의 답(요약): 같지 않다. 소셜(OpenID Connect)의 ID 토큰이 JWT라서 받아서 공개키로 검증하는 쪽을 경험하고, 우리 API 인증은 세션 그대로다. JWT 발급은 모바일 앱, 외부 공개 API, v3 MCP 때 다시 본다. 30분은 OWASP가 위험이 낮은 애플리케이션의 흔한 범위(15~30분)로 드는 값의 끝이다.
- **결정 3** (11/7): "어려운 부분은 구글 AI를 쓰면서 보느라 좀 걸렸습니다. 그래도 어려운 내용이기는 마찬가지긴 하네요. 모두 좋은 것 같습니다. 약한 이해긴 한데 (로그인을 표준 필터로) 한다면 우리도 OpenApiCustomizer를 사용하게 되는 건가요? 여기의 선택들은 대부분 기업들이 많이 선택하는, 많이 쓰는 표준이라고 봐도 되나요?"
  - 멘토의 답(요약): 그렇다. 로그인·로그아웃 두 항목을 OpenApiCustomizer로 적는다. 표준인지는 근거를 나눠 답했다. 쿠키 표시·CSRF 토큰·프록시 헤더는 표준 문서와 프레임워크 기본값에 근거하고, 로그인 구현 방식과 소셜 주소 위치는 우리 구조를 위한 판단이다. 회사 내부 설정은 공개되지 않아 "얼마나 많이 쓰나"는 비율로 확인하지 못했다.
- **운영 화면 접속 환경** (11/6, 멘토가 물음): "집에서 맥북과 윈도우 데스크탑, 밖에서 맥북과 안드로이드 휴대폰(갤럭시 S25 울트라)으로 가능하면 이것들로 접근하게 하고 싶습니다."
- **결정 4** (11/7): 데이터 모양, 역할, 규칙 문장은 "좋습니다." 규칙 문장에 대해 "이게 맞기도 하고요." 운영·공식 계정 분리(B)에 대해 "이메일 두 개는 구글 메일 하나 더 파면 될 것 같으니 상관은 없을 것 같습니다." 이어서 "B의 불편에서 보고 든 생각인데, 그러면 우리 사이트에서 다른 계정으로 로그인 혹은 다른 계정으로 전환 같은 기능도 쓸 수 있나요? 예시로 스팀의 계정 변경 같은 시스템이요. 계정 전환을 누르면 인증된 계정들이 네모 칸으로 좌르륵 있고, 그중 네모(계정) 하나를 선택하면 자동으로 그 계정으로 전환 로그인되는 시스템 같은 거요."
  - 멘토의 답(요약): 만들 수 있지만, 운영 계정을 자동 전환에 넣으면 B의 장점이 사라지고 직접 만드는 큰 기능이다. 브라우저 프로필과 패스키의 계정 선택 화면으로 대신할 수 있다.
  - 정현(11/7): "생각해 봤는데, 계정 전환 기능은 굳이 안 넣어도 될 것 같다고 다시 생각을 바꿨습니다. 없던 안으로 합시다."
- **결정 5** (11/7): 패스키, 운영 세션 규칙, 처음 등록과 복구에 대해 "2, 3, 4번은 좋습니다."
- **검토** (11/7): "초안 먼저 작성하시고, 바로 다음 채팅에서 노력을 최대로 바꿔서 검토를 진행해 보도록 하죠." 검토를 시작하며 "오케이 우선 검토 부탁드립니다."
  - 멘토가 검토에서 고친 것(요약)
    - 보안 구멍: 비밀번호만으로 새 패스키를 더할 수 있던 등록 규칙(결정 5). Redis 세션에서 패스키 사용자 확인이 꺼지는 7.1.0의 취약점(Spring Security 하한 7.1.1).
    - 동작하지 않았을 곳: 패스키 주소가 `/api` 밖이라 Nginx를 지나지 못함. 패스키 확인 뒤 principal이 바뀌어, 형변환으로 회원을 찾으면 운영 계정에서 깨짐.
    - 틀리거나 넘친 문장: "로그인하지 않은 방문자에게는 세션이 생기지 않는다"(요청 저장이 세션을 만듦), "브라우저는 SameSite가 없으면 Lax로 다룬다"(크롬·엣지만), RFC 10017을 "표준 권고"로 쓴 것과 쿠키 규칙의 절, XSS 문장의 빠진 절반.
    - 빠진 것: 계정 상태로 이메일을 캐내는 길과 그 테스트, 운영 세션 규칙을 서버가 강제한다는 것과 그 테스트, 두 구글 계정의 역할, "계정당 1개" 문장의 전제(인증을 마친 계정만)와 구글 메일의 점·+태그, ADR-0006 운영 규칙이 바뀐다는 것, 11번에 넘길 비밀번호 규칙의 사실.
    - [확인 필요] 셋을 풂: 회원별 세션 찾기 설정 이름, #18128, 로그인 뒤의 CSRF 쿠키.
  - 멘토가 정현에게 물은 것: 미인증 계정이 할 수 있는 것(4-5), 가입·재설정에서 가입 여부를 알려 줄지(3-3). 둘 다 멘토의 추천은 A였다.
- **검토 뒤의 답** (11/7 밤): "내용이 어렵네요. 1. 좋습니다. 2. 좋습니다. 메일로 본인이 아니라면 비밀번호 변경 등 조치를 취하라고 메시지를 추가하면 좋을 것 같네요."
  - 멘토의 답(요약): 메일 종류에 따라 나누자고 제안했다. 가입 시도 안내처럼 아무것도 바뀌지 않은 메일은 "무시해도 되고, 걱정되면 비밀번호를 바꿀 수 있다"로, 비밀번호 변경·패스키 등록처럼 실제로 바뀐 메일은 "본인이 아니면 바로 재설정"으로 쓴다. 비밀번호 변경 알림 메일을 [잠정]으로 더했다(3-3).
- **승인 전에 꺼낸 질문** (11/7 밤): "우리 템플릿을 다운로드 받을 때 로그인이 굳이 필요할까? 로그인 없이도 우리 템플릿을 다운받을 수 있도록 할 수 있을까? 다만 로그인을 안 했을 때는 라이브러리나 이런 건 못 쓰겠지만, 로그인을 안 해도 템플릿은 다운로드 받을 수 있게. 드롭은 그래도 로그인한 상태에서만 다운받을 수 있게 해야 할까? 큰 이슈 같아서 ADR 승인 전에 말씀드려 봐요."
