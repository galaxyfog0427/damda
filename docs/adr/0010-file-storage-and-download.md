# ADR-0010: 파일은 NCP의 S3 호환 창고에 두고, 템플릿 파일은 5분짜리 만료 링크로 내준다

- 날짜: 2026-11-12
- 상태: 승인 (2026-11-13, 정현)
- 작성: 초안은 멘토 AI, 판단은 정현

> **쉽게 말하면**
> 1. 파일은 서버 디스크가 아니라 NCP의 파일 창고(S3 호환 Object Storage)에 둔다. 서버가 상태를 갖지 않는다. board의 `S3FileStore`를 연결 설정(주소·지역·키)만 바꿔 다시 쓴다.
> 2. 창고 안을 두 구역(버킷)으로 나눈다. 썸네일은 파일마다 읽기만 공개하고, 템플릿 파일은 공개하지 않는다. 버킷 목록은 어느 쪽도 공개하지 않는다.
> 3. 받기를 누르면 서버가 확인을 마친 뒤 5분 동안만 열리는 링크(만료 링크)를 만들어 주고, 브라우저는 창고에서 바로 받는다. 파일은 서버를 지나가지 않는다.
> 4. DB에는 파일 주소가 아니라 창고 안의 이름(키)만 적는다.

## 맥락

- ADR-0008과 요구사항 D-1·D-2: 받기는 POST이고, 응답으로 PPT의 만료 링크나 노션 링크를 준다. 로그인 없이 누구나 받으므로 전송량이 비용이 된다는 것도 감수했다(9번에서 본다).
- 기획 3의 4-2: 9번에서는 모양(창고 + 만료 링크, 로컬 대역, ERD에 들어갈 칸)만 정하고, NCP의 요금·전송량·만료 링크 지원은 7번에서 확인한다.
- 정현은 board에서 `FileStore` 인터페이스, `LocalFileStore`, `S3FileStore`(LocalStack), 저장 이름 규칙(`StoreFileNames`), "파일 먼저 저장 → DB 저장, 실패하면 파일 지우기" 보상 순서를 만들었다. board는 서버가 파일을 읽어 그대로 내려 주는 방식이었다.
- board의 README에 "알려진 한계"로 남긴 것 중 넷을 이 결정이 다룬다: 서명 URL은 규모가 커지면(미룸), S3 응답에 Content-Length 없음(진행률이 안 보임), 업로드 바이트 검증 없음(저장형 XSS), 한글 파일명 NFD.
- NCP에는 S3 호환 창고가 둘 있다. Object Storage는 공개를 ACL(버킷·파일마다 표시)로만 걸고, 버킷 정책은 문서에 없다. 콘솔의 "버킷 공개"는 파일을 여는 것이 아니라 목록을 여는 설정이다(공식 FAQ는 파일 업로드까지 된다고 적음). Ncloud Storage(2025-04 OBT로 시작)는 버킷 정책과 퍼블릭 액세스 차단을 준다. 둘 다 S3 API이고 서명은 Version 4를 쓸 수 있다.
- v1의 링크 미리보기는 사이트 공통 카드다(ADR-0005 결정 4, 요구사항 B-5). og:image는 사이트 대표 이미지 하나라 템플릿 썸네일을 쓰지 않는다. 템플릿별 카드는 v1 후보다(이 ADR에서 v2에서 옮김, 결과 참고).

## 결정

1. **창고**: NCP의 S3 호환 창고. 상품(Object Storage / Ncloud Storage)은 7번에서 요금·공개 방식·정식 출시 여부를 보고 고른다. 코드는 board의 `FileStore` 인터페이스와 `S3FileStore`를 다시 쓰고, 만료 링크를 만드는 기능을 더한다.
2. **버킷 둘** (상품과 관계없이 지킬 규칙):
   - 썸네일 버킷: 썸네일 파일마다 읽기만 공개한다. 버킷 목록은 공개하지 않는다(Object Storage라면 콘솔의 "버킷 공개"를 켜지 않는다).
   - 템플릿 버킷: 템플릿 파일(PPT). 공개 표시를 붙이는 코드가 이 길에는 아예 없다. 창고에 공개 차단 기능이 있으면 켠다. 만료 링크로만 받는다.
3. **만료 링크**: 링크를 내주는 입구는 둘이고, 서버가 확인을 마친 뒤에만 서명한다.
   - ① 받기 POST(D-1): 공개된 일반 템플릿만(B-6, 드롭 전용 아님 R-3).
   - ② 라이브러리에서 다시 받기(D-6): 그 회원의 주문이 있는 템플릿만(내린 템플릿 포함 D-7, 드롭 R-3).
   - 부를 때마다 새 링크를 만들고, 링크는 5분 뒤 만료된다. 받을 것이 없으면 서명하지 않고 "받을 수 없음"으로 답한다(D-9).
   - 받은 수를 세는 때는 요구사항 D-3을 따른다(이 ADR에서 고침: 두 입구 모두 링크를 내줄 때 센다. 같은 템플릿은 회원이면 회원 번호로, 방문자면 IP로 1시간에 한 번만 센다). 방문자의 IP는 원래 값을 알아볼 수 없게 바꾼 값(비밀 키를 쓴 HMAC)으로만 Redis에 1시간 두고 지운다. ADR-0008 결정 3(방문자 데이터는 템플릿별 숫자만)에 이 1시간짜리 값이 더해진다.
4. **이름**: 창고의 키는 `UUID.확장자`다(board의 `StoreFileNames`). 받을 때의 파일 이름은 **템플릿 제목 + 확장자**다(예: `주간 플래너.pptx`). 파일 이름에 못 쓰는 문자는 바꾸고 NFC로 정리한다. 링크가 다른 출처(창고)라 `<a download>`는 무시되므로, 이름은 창고 응답의 `Content-Disposition: attachment; filename="…"; filename*=UTF-8''…`(RFC 6266)로 정한다. 링크에 이 값을 붙이는 기능(response-content-disposition)이 NCP 문서에 없다 [확인 필요: 7번]. 안 되면 올릴 때 파일 정보에 적어 두고, 제목을 고칠 때 다시 적는다.
5. **올리는 길**: 제작자 화면 → Spring(멀티파트) → 창고.
   - 허용 형식: PPT는 `.pptx`, 썸네일은 JPG·PNG. 창고에 적는 Content-Type은 서버가 정한다(브라우저가 보낸 값을 믿지 않는다).
   - 순서: 파일을 먼저 저장하고 DB에 적으며, 실패하면 저장한 파일을 지운다(board의 보상 순서).
   - 바꾸기(C-2): 새 키로 올리고, DB 커밋이 끝난 뒤 옛 파일을 지운다(커밋 전에 지우면 롤백 때 깨진 참조가 생긴다). 키가 늘 새것이라 썸네일에 오래 캐시(`Cache-Control: public, max-age=31536000, immutable`)를 붙인다.
   - 썸네일 규격: 링크 미리보기 카드 비율(약 1.91:1, 예: 1200×630 [확인 필요: 카카오 권장 크기]), damda 공통 틀 + 템플릿마다 다른 내용, 중요한 내용은 가운데. 목록 화면은 이 비율로 줄이거나 가운데를 잘라 보여 준다.
   - [잠정: 템플릿 시험 때] 템플릿마다 썸네일을 만들어 보고, 글씨가 들어가도 무슨 템플릿인지 알려 주면서 예쁘고 한결같으면 이대로 간다. 맞추기 어려우면 **링크 미리보기 카드만** damda 공통 그림 하나를 쓰고, 목록·상세의 썸네일은 템플릿마다 다르게 둔다.
   - 파일·썸네일 크기 상한 [잠정: 4주 차].
6. **로컬 대역**: LocalStack. `backend/compose.yaml`(Compose 지원)에 더한다.
   - 토큰: 2026-03부터 LocalStack은 토큰이 있어야 켜진다(CI 포함). 정현은 GitHub 학생 팩의 학생 플랜(board와 같음, 저장 유지·CI 포함)을 쓰고, 토큰은 `backend/.env`에만 둔다(루트 `.gitignore`의 `.env` 규칙이 막음).
   - CI: 토큰을 Actions 비밀값과 **Dependabot 비밀값 둘 다**에 넣는다. Dependabot이 연 PR의 워크플로는 Dependabot 비밀값만 읽으므로, 빼먹으면 Dependabot PR의 `backend` 필수 검사가 실패해 병합이 막힌다.
   - 만료 링크의 서명·만료 검사는 LocalStack에서 기본으로 꺼져 있다. `S3_SKIP_SIGNATURE_VALIDATION=0`을 켜고 시험한다.
7. **ERD에 들어갈 칸**(11/13): 템플릿 파일의 키·크기·콘텐츠 타입, 썸네일의 키, 노션 링크 주소. 모두 비워 둘 수 있다(C-1, D-9). 창고에 있는 파일은 주소 전체가 아니라 키만 저장하고, 노션 링크는 주소 그대로 저장한다. 원래 파일 이름 칸은 두지 않는다(결정 4).

```
NCP 창고
 ├─ 썸네일 버킷   파일마다 "읽기만 공개"    목록은 닫아 둠
 └─ 템플릿 버킷   공개 표시 없음            만료 링크로만 열림

링크를 내주는 입구는 둘
 ① 받기 POST            확인: 공개된 일반 템플릿인가
 ② 라이브러리 다시 받기   확인: 이 회원의 주문이 있는가
      └→ 서버가 5분짜리 링크에 서명 → 브라우저가 창고에서 바로 받음
```

## 선택지

### 내려 주는 방식

| | 가. 서버가 중계 (board 방식) | **나. 만료 링크 (선택)** |
| --- | --- | --- |
| 파일이 지나가는 길 | 창고 → 서버 → 브라우저 | 창고 → 브라우저 |
| 서버 부담 | 받는 동안 스레드와 회선을 씀 | 링크 서명만 함(창고에 묻지 않는 서버 안 계산) |
| POST 받기와 맞추기 | POST 응답으로 파일을 주면 화면이 파일 전체를 메모리에 받아 저장해야 한다. 링크로 주려면 서버가 일회용 링크를 따로 만들어야 한다(만료 링크를 직접 만드는 셈) | 응답으로 링크를 주고 화면이 그 링크로 이동한다 |
| 실제로 받았는지 | 셀 수 있음 | 링크를 내준 것까지만 셈 |

- **링크를 계정에 묶기 (정현의 아이디어, 철회)**: 링크를 주문한 계정에서만 열리게 하자는 생각. 창고는 우리 회원을 모르므로 확인하려면 받을 때마다 서버를 거쳐야 하고(가로 돌아감), IP에 묶으면 휴대폰은 받는 중에도 IP가 바뀐다. 무엇보다 목적이었던 "라이브러리 주인 말고는 파일을 쓰지 못하게"는 받은 파일 자체를 넘길 수 있어 이 방법으로 막을 수 없다.

### 버킷

| | 하나 + 파일마다 공개 표시 | **둘로 나눔 (선택)** |
| --- | --- | --- |
| 실수했을 때 | 썸네일과 PPT가 같은 코드 길을 지나 표시 하나로 갈린다. 잘못 붙이면 PPT가 샌다 | PPT를 올리는 길에는 공개 표시 코드가 없다. 테스트로 확인하고, 공개 차단이 있는 상품이면 창고도 막는다 |
| 썸네일 | 파일마다 공개 표시 | 파일마다 공개 표시(Object Storage) 또는 버킷 정책(Ncloud Storage) |
| 나중에 CDN | 공개 파일만 골라야 함 | 썸네일 버킷만 앞에 둠 |

### 올리는 길

- **서버를 거침 (선택)**: 서버가 올리기 전에 형식·크기를 본다. 올리는 사람이 공식 계정 하나인 v1에 단순하다.
- 브라우저가 만료 링크(PUT)로 창고에 바로 올리기: 큰 파일에서 흔한 방식이지만, 창고에 CORS가 필요하고 서버가 올리기 전에 검사하지 못해 올린 뒤 따로 검사해야 한다. v2의 다른 이용자 업로드 때 다시 본다.

### 로컬 대역

- **LocalStack (선택)**: board에서 써 봤고, 서명 검사를 켜면 만료 링크까지 로컬에서 시험할 수 있다.
- `LocalFileStore`(로컬 디스크): 가장 가볍지만 만료 링크를 만들 수 없어, 로컬과 운영의 받기 흐름이 달라진다.

## 이유

1. 파일을 서버 디스크에 두지 않아 앱이 상태를 갖지 않는다(N-10, K8s 준비 원칙).
2. 파일이 서버를 지나가지 않아 작은 서버 하나로 시작하는 v1에서 스레드와 회선을 아낀다. 인터넷으로 나가는 전송 요금은 어느 쪽이든 생긴다(창고에서 NCP 서버로 가는 내부 전송은 무료라 가에서는 서버가 내보내는 몫이 된다). 창고가 Content-Length를 주므로 board와 달리 진행률이 보인다.
3. 템플릿 파일은 공개 표시를 붙이는 코드가 없는 버킷에만 들어간다. 썸네일은 목록에서 한 번에 여러 장 보이므로 주소가 늘 같아야 브라우저 캐시가 먹는다(서명 링크는 부를 때마다 주소가 바뀐다). 템플릿별 미리보기 카드의 og:image도 영구 주소가 필요하다.
4. 5분: 화면이 응답을 받자마자 링크로 이동하므로 몇 초면 충분하고, 남는 시간은 느린 회선을 위한 여유다. S3는 만료를 요청이 들어올 때만 보므로 시작된 다운로드는 만료가 지나도 이어진다. Amazon S3 콘솔도 다운로드 버튼을 누를 때 300초 링크를 만든다. NCP의 동작은 [확인 필요: 7번].
5. board에서 만든 `FileStore`, 저장 이름 규칙, 보상 순서, LocalStack 설정을 가져온다.
6. 키만 저장하므로 창고나 도메인을 바꿔도 DB는 그대로다(board의 저장소 이전 실습에서 확인한 것).

## 감수하는 것

- 받은 수는 링크를 내준 순간 센다. 받다가 취소하거나 끊긴 경우도 센다.
- 링크 하나는 만료 전까지 몇 번이든 쓸 수 있다. 5분 안에는 링크를 퍼 갈 수 있고, 봇이 링크 하나로 반복해 받으면 전송량이 는다. 레이트 리밋은 링크를 내주는 횟수만 막는다. 마지막 장치는 예산 알림(다음 날 옴)이다. 받은 파일 자체를 퍼 가는 것은 막지 못한다(ADR-0001·0008과 같음).
- 받다가 끊기고 5분이 지나면 이어 받기가 실패한다. 다시 누르면 새 링크가 나온다.
- 공개 전·내린 템플릿의 썸네일도 키를 알면 열린다. 키는 추측할 수 없고 목록은 닫혀 있다. 권리 문제로 내릴 때(D-7)는 런북이 썸네일까지, 그리고 창고 파일과 DB 키를 함께 지운다(키만 남기면 서명은 되지만 브라우저에 창고의 오류 화면이 뜬다).
- 같은 IP를 여럿이 쓰는 곳(학교, 회사, 카페)에서는 1시간 안에 같은 템플릿을 받은 여러 사람이 1로 센다. 반대로 휴대폰처럼 IP가 자주 바뀌면 한 사람이 여러 번 셀 수 있다. 방문자의 IP를 1시간 담아 두는 것은 새로 모으는 정보라 처리방침에 적는다.
- 보상 실패나 바꾸기 뒤 지우기 실패로 고아 파일이 남을 수 있다. board처럼 ERROR 로그를 남기고, v1에는 정리 배치가 없다.
- LocalStack은 흉내 낸 창고라, NCP에서만 생기는 차이(체크섬, 링크에 이름 붙이기, 주소 형식)는 운영에 올려야 드러난다. 첫 파일 배포 때 운영에서 받기 한 번을 확인한다.
- NCP의 요금·전송량·만료 링크 동작은 아직 확인하지 않았다 [확인 필요: 7번].

## 결과

- **요구사항** (이 ADR의 PR에서 고침): D-2의 [잠정] → 5분. D-3 → 두 입구 모두 링크를 내줄 때 세고, 같은 템플릿은 회원 번호·IP별로 1시간에 한 번 [잠정: 숫자](정현 11/13). N-5의 모으는 것에 "받은 수를 세려고 IP를 알아볼 수 없게 바꾼 값(1시간)". 4번 표의 "템플릿별 링크 미리보기 카드"를 v1 후보로. 5번 표의 "만료 링크 시간, 파일 저장 모양" 줄을 지운다. D-9의 근거에 이 ADR.
- **11/13 ERD**: 결정 7의 칸. M2 시드에는 썸네일이 없다(기획 3의 15번 10: 4주 차에 붙임). M2 화면과 11월 말 포트폴리오에 빈 썸네일이 괜찮은지 M2 데이터와 함께 본다.
- **11/14 API 껍데기**: API는 키가 아니라 완성된 썸네일 주소를 준다(앞부분은 설정값). 받기 응답에 받는 방식(용어 사전 DeliveryType: FILE·LINK)을 넣는다. 라이브러리 다시 받기는 받기 POST와 다른 입구다.
- **7번(운영 구성)**: 창고 상품 고르기(Object Storage / Ncloud Storage: 요금, 공개 방식, 정식 출시 여부), 요금·전송량, 만료 링크 동작(이름 붙이기, Cache-Control 포함), 두 버킷 만들기, 접근 키는 Object Storage 권한만 있는 서브 계정 키를 서버 환경 변수로(공개 저장소에 쓰지 않음), CSP `img-src`에 썸네일 주소(N-12), 백업 범위(파일도 백업하는가). CORS는 v1 흐름(이미지 태그, 링크 이동)에 필요 없다.
- **3주 차(파일 저장)**: `S3FileStore` 가져오기, 만료 링크 기능, LocalStack을 Compose에 더하기와 CI 비밀값 둘. 테스트: 받기 API가 링크를 돌려줌(링크 만들기는 서버 안 계산이라 LocalStack 없이 됨), 주문 없는 회원의 라이브러리 받기는 막힘, 드롭 전용·공개 전·내린 템플릿에 받기 POST는 링크 없음, 템플릿 버킷에 공개 파일이 없음. AWS SDK 2.30.0부터 올리기에 체크섬이 기본으로 붙어 S3 호환 창고에서 실패한 사례가 있다. NCP에서 한 번 확인하고, 안 되면 `WHEN_REQUIRED` [확인 필요]. 만료 링크는 서명이 든 출입증이라 통째로 로그에 남기지 않는다(N-3). 1시간에 한 번 세기(Redis, 회원 번호·IP 해시 + 템플릿)와 3주 차의 짧은 처리방침에 IP 해시 한 줄. `FileStore`의 패키지 위치는 ADR-0004의 의존 방향(구현은 infrastructure). 프론트 지침 [잠정]: PPT 링크는 같은 창에서 연다(attachment라 화면이 바뀌지 않음). 노션은 응답 뒤 새 창이 팝업 차단에 걸릴 수 있어, 누르는 순간 빈 창을 먼저 열고 응답이 오면 주소를 바꾼다.
- **4주 차(제작자 화면)**: 크기 상한. 기본값은 Spring 1MB(파일)·10MB(요청), Nginx 1MB라 그대로면 첫 PPT부터 막힌다. 넘었을 때의 응답도 ProblemDetail(N-13)이어야 하므로 Nginx와 Spring 중 어느 쪽이 먼저 막을지 정한다. 허용 형식 검사, 썸네일 규격, 올리기 보상 순서·바꾸기 테스트.
- **11번(레이트 리밋)**: 링크를 내주는 입구 둘을 모두 대상으로 본다(라이브러리 다시 받기는 N-4에 아직 없음). 1시간 세기가 숫자를 정직하게 하고, 막는 일은 11번이 한다.
- **v1 후보**: 템플릿별 링크 미리보기 카드(어림 3~4시간 [잠정]). 템플릿 주소로 요청이 오면 서버가 HTML의 og 태그(제목, 썸네일)를 넣어 답한다. 썸네일 규격은 결정 5에서 미리 맞춘다.
- **v2**: 다른 이용자 업로드 때 업로드 검증·직접 올리기를 다시 보고, 조작할 이유가 생기므로 받은 수의 사후 보정 같은 더 강한 방법을 본다.
- **용어 사전** (보강 때): 만료 링크(서명 URL, presigned URL), 창고(Object Storage), 버킷, 키, 보상 순서, LocalStack.
- **학습**: 『가상 면접 사례로 배우는 대규모 시스템 설계 기초 1』의 유튜브 설계 장에서 서명 URL 부분만 3주 차 전에 본다. 기획 3의 6번 표에는 11/15 점검 때 더한다.

## 정현의 판단 (대화에서 옮김)

> 정현의 말을 대화에서 옮겼다. 읽기 쉽게 조금 다듬었지만 뜻은 바꾸지 않았고, 정현이 말하지 않은 이유는 넣지 않았다.

- 결정 1~7 (11/12): 설명을 듣고 추천대로 정했다. 결정 2(버킷 둘)는 정현이 더 풀어 달라고 했다.
- 최대 노력 검토 (11/12 밤~11/13): [고침] 21개, [질문] 5개. 멘토가 고친 것: 11/12 설명의 두 전제가 틀렸다. 썸네일이 v1 미리보기 카드 때문에 영구 주소여야 한다고 했지만 v1은 공통 카드다. "공개 버킷 = 구역 전체가 공개"라고 했지만 NCP Object Storage의 "버킷 공개"는 목록을 여는 설정이다. 라이브러리 다시 받기의 권한 확인과, 받은 수를 D-3과 다르게 적은 것도 고쳤다.
- 창고 상품: Ncloud Storage가 원하는 모양에 가깝지만 정식 출시 기록이 없어 "구현에 제한된 게 있다면 조심스럽게 고려해야" 한다고 봤고, 추천대로 7번에서 고르기로 했다.
- 받는 이름: 제목 + 확장자. "NCP의 링크에 이름 붙이기가 안 되는 것이 정확히 확인된다면 어느 정도 감수할 부분이 생기겠네요."
- 미리보기 카드: 템플릿마다 카드 이미지를 다르게 하는 비용을 물었다. "사이트만의 무언가 통일된 느낌을 주면서 각 템플릿만의 이미지를 가졌으면 좋겠다." 설명을 듣고 썸네일 규격은 지금, 태그 넣기는 v1 후보로 정했다. 썸네일은 "우선 각 템플릿별마다 해 보고, 나오는 디자인을 봐서 수정해서라도 일관되게 괜찮다 싶으면 그렇게 가고, 어렵다 하면 우리의 공통 썸네일을 하나 만들어서 쓰자." 걱정한 것은 "상품에 대한 이미지를 보여야 할 것 같은데 거기에 글씨가 들어가 있으면 별로 안 예쁠 것 같다"는 점이고, 공통 그림은 링크 미리보기 카드에만 쓰고 목록은 템플릿마다 다르게 둔다는 뜻이었다.
- 받은 수: 라이브러리에서 다시 받는 것과 드롭도 세고 싶어 했다. "라이브러리에 있는 것을 자신의 다른 노션 계정 혹은 다른 PPT에도 사용할 목적이라면 그 다운로드의 카운트도 세 줘야 한다." 다른 사람이 올린 템플릿의 다운로드 수를 올리는 조작은 막아야 하므로, 같은 계정은 일정 시간 동안 다시 세지 않게 하자고 했다. 멘토가 24시간을 제안했고, 정현은 "24시간은 너무 긴 것 같고 1시간 정도"로 정했다. 다른 곳의 대처를 구글 AI에게 물어 와서, IP 기준으로 반복을 빼는 것이 생각을 넓히는 부분이라고 봤다. 방문자의 IP 기준 집계 제외는 처음에 하지 않기로 했다가(질문 5, 가), 처리방침에 알리면 짧게 보는 것도 되는지 묻고 "IP 별로도 1시간에 한 번"으로 바꿨다(11/13).
- 링크를 계정에 묶기: 정현이 제안했다가 철회했다. "취지가 다운로드의 파일을 라이브러리의 주인이 아닌 다른 사람이 할 수 없게 해보자는 것이었는데, 그 취지를 이런 접근으로는 막을 수 없으니 철회하는 게 나을 것 같다."
- 승인 (11/13): 바뀐 곳을 읽고 "오케이 승인할게요".
- 설명 확인 (11/13): 네 문항에 답했다. "버킷 공개"가 목록을 여는 설정이라는 것과, 만료 시각을 고치지 못하게 막는 것은 5분이 아니라 서명이라는 것을 바로잡았다.
