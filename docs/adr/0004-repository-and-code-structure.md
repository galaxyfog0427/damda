# ADR-0004: 저장소는 하나로 두고, 백엔드는 기능별 패키지 + 같은 네 층으로, 예외는 ProblemDetail 한 형식으로 처리한다
 
- 날짜: 2026-11-05
- 상태: 승인 (2026-11-05, 정현)
- 작성: 초안은 멘토 AI, 검토·승인은 정현
> **쉽게 말하면**
> 1. 백엔드, 프론트, API 계약, 문서를 저장소 하나에 둔다. 계약을 바꿀 때 백엔드와 프론트가 한 번에 함께 움직이게 하려는 것이다.
> 2. 백엔드 코드는 기능(템플릿, 드롭, 주문 …)별 폴더로 나누고, 각 폴더 안은 똑같이 네 칸으로 나눈다: api(요청 받기), application(일 처리 순서), domain(핵심 규칙과 데이터), infrastructure(바깥 서비스 연결). 이 규칙은 테스트가 자동으로 검사한다.
> 3. 에러 응답은 업계 표준 양식(Problem Details) 하나로 통일하고, 에러 코드는 기능별로 나눠 관리한다.
 
## 맥락
 
- 프론트(React, 프론트 AI가 작성)와 백엔드(Spring, 정현이 작성)가 OpenAPI 계약으로 연결된다.
- AI 팀이 저장소를 함께 쓴다.
  - 프론트 AI는 git worktree에서 작업한다.
  - 리뷰어 AI는 백엔드·프론트 PR을 모두 리뷰한다.
  - 멘토는 claude.ai에서 GitHub를 읽는다.
  - 환경 문서의 herdr 탭 배치 초안은 저장소 하나를 기준으로 짜여 있다.
- board에서 겪은 것
  - 패키지 구조가 "바깥은 기능별, 큰 기능(post)만 안쪽을 계층별로"였다. 기능마다 안쪽 구조가 달라 새 코드를 어디에 둘지 매번 정해야 했다.
  - 예외는 기능별 커스텀 예외를 핸들러에서 하나씩 상태 코드에 연결했다.
- 저장소는 공개하고, 포트폴리오로 쓴다.
## 결정 1: 저장소는 하나 (모노레포)
 
```
<저장소>/
├─ backend/     Spring Boot (Gradle, 자체 gradlew)
├─ frontend/    React + TS + Vite (Node 24)
├─ contract/    openapi.yaml (위치와 작성 방식은 기획 2의 4번에서 확정)
├─ docs/        adr/, glossary.md, requirements.md, runbook/ …
├─ docker/      compose·Nginx·모니터링 설정 (board와 같은 이름)
├─ .github/     workflows/, 이슈·PR 템플릿
├─ .claude/     settings.json, agents/ (리뷰어 지침)
├─ CLAUDE.md
└─ README.md
```
 
이유:
1. 계약과 백엔드·프론트가 한 곳에 있어서, 계약을 바꾸는 PR 하나로 양쪽이 함께 움직인다. 저장소를 나누면 계약을 복사하거나 따로 배포해야 하고, 그 과정에서 어긋나기 쉽다.
2. AI 팀 운영이 단순하다. 리뷰어, 멘토, claude.ai 동기화, herdr 워크스페이스가 모두 저장소 하나만 보면 된다.
3. 링크 하나로 백엔드·프론트·문서·인프라·ADR 전체를 보여 줄 수 있고, 버전 태그(`v1.0.0`)도 하나다.
버린 선택지:
- **백엔드·프론트 저장소 분리**: 프론트 AI가 백엔드 코드를 물리적으로 건드릴 수 없다는 장점이 있다. 하지만 계약 동기화 비용과 관리할 대상이 두 배가 된다. 같은 경계는 아래 세 겹으로 만들 수 있다.
- **계약 전용 저장소까지 셋**: 1인 팀에는 과하다.
감수하는 것:
- **프론트 AI가 `frontend/` 밖을 고칠 위험**: 세 겹으로 막는다. 세부는 환경 구축 채팅에서 정한다.
  1. `frontend/CLAUDE.md` 지침
  2. 권한 규칙: 프론트 AI는 `frontend/` 밖을 수정할 수 없다
  3. CI 검사: 프론트 작업 PR이 `frontend/` 밖을 바꾸면 실패한다
- **CI를 백엔드·프론트로 나눌 때의 함정**: 경로 필터로 건너뛴 워크플로는 필수 검사가 "대기 중"으로 남아 병합이 막힌다(GitHub 문서). 워크플로 단위가 아니라 작업(job) 단위로 조건을 건다. 세부는 환경 구축 채팅에서 정한다.
- **언어 표시**: GitHub의 언어 표시에서 TypeScript가 Java보다 크게 나올 수 있다. 감추지 않고 README 첫머리에 "백엔드는 직접, 프론트는 AI가 작성"이라고 밝힌다(킥오프 ①의 정직한 표기).
## 결정 2: 백엔드 코드 구조
 
- **단일 Gradle 모듈**로 시작한다. 멀티 모듈은 배치나 두 번째 앱처럼 코드를 나눠 쓸 이유가 생기면 새 ADR로 정한다.
- **바깥은 기능별, 안쪽은 모든 기능이 같은 네 층 이름**을 쓴다. 필요 없는 층은 만들지 않는다. 기능 이름은 설계 주간 ERD 뒤에 확정한다.
```
com.<서비스>/
├─ global/             설정, 보안, 예외 처리, 웹 공통, 관측성
├─ template/
│  ├─ api/             컨트롤러, 요청·응답 DTO (운영 화면용 컨트롤러도 여기)
│  ├─ application/     서비스 (트랜잭션 경계, 유스케이스)
│  ├─ domain/          엔티티, 값 객체, 저장소 인터페이스
│  └─ infrastructure/  외부 연동 구현 (QueryDSL 구현, 파일 저장소 클라이언트 등)
├─ drop/ …
├─ order/ …            (라이브러리에 추가 = 주문)
├─ member/ …           (회원, 로그인)
└─ creator/ …          (제작자 프로필)
```
 
- **의존 방향 규칙**
  - api → application → domain, infrastructure → domain. domain은 다른 층을 모른다.
  - 다른 기능의 저장소(repository)를 직접 부르지 않고, 그 기능의 application 서비스를 통해서만 부른다.
  - 기능끼리 순환 참조는 금지한다.
- **규칙은 테스트로 고정한다(ArchUnit).**
  - board에서 `ddl-auto=validate`가 엔티티와 테이블이 어긋나면 기동을 거부했듯이, ArchUnit은 패키지 규칙이 깨지면 테스트를 실패시킨다.
  - 정현이 직접 쓴 코드든, 멘토가 준 빈칸 채우기 뼈대나 AI 도움으로 쓴 코드든, 규칙 위반을 사람보다 테스트가 먼저 잡는다. CI에서도 돌기 때문에 위반한 채로는 병합되지 않는다.
  - Java 25를 지원하는 ArchUnit 버전은 첫날 확인한다.
이유:
1. board에서 기능마다 안쪽 구조가 달라 "어디에 넣지?"가 반복됐다. 규칙을 하나로 정한다.
2. 층 이름이 같으니 리뷰어 AI와 프론트 AI도 코드 위치를 예측할 수 있다.
3. v3 챗봇의 도구(나중에 MCP가 생겨도)는 api 층에 붙어 application을 그대로 쓴다.
버린 선택지:
- **계층 우선**(controller / service / repository가 맨 위): 기능이 늘면 한 패키지에 여러 기능의 파일이 섞여, 기능 단위로 읽기 어렵다.
- **헥사고날(포트·어댑터) 완전 적용**: 인터페이스와 변환 코드가 늘어 4주 v1에는 비용이 크다. 지금 구조가 그 방향의 실용적인 축소판이다.
- **Spring Modulith**: 모듈 경계 검증, 트랜잭션 이벤트를 기록해 두었다가 실패하면 다시 보내는 기능이 있다. 하지만 안쪽 네 층과 기본 규칙이 부딪혀 설정이 더 필요하다. v2에서 이벤트(Kafka)를 붙일 때 다시 검토한다 [보류].
- **멀티 모듈**: 지금은 앱이 하나다.
## 결정 3: 예외 처리
 
킥오프 ① 11/1 초안을 확정하되, board 경험으로 두 군데(2, 4)를 고친다.
 
1. **응답 형식**: RFC 9457 Problem Details(Spring `ProblemDetail`)에 확장 필드 `code`(에러 코드)와 `traceId`를 더한다. 검증 실패는 `errors`(필드와 메시지 목록)로 준다.
2. **에러 코드** (초안의 "enum 하나"에서 바꿈)
   - 공통 인터페이스 `ErrorCode`(코드, HTTP 상태, 기본 메시지, 로그 수준)를 두고, 기능별 enum(`TemplateErrorCode`, `DropErrorCode` …)이 이를 구현한다. `BusinessException`은 인터페이스를 받으므로, 어느 기능의 enum이든 핸들러 하나로 똑같이 처리된다.
   - 바꾼 이유: 결정 2의 "기능에 관한 것은 그 기능 폴더에 모은다"를 에러 코드에도 적용한다. 큰 enum 하나는 모든 기능이 같은 파일을 고치게 되어, 브랜치가 여럿일 때 병합 충돌 지점도 된다.
   - 코드는 읽을 수 있는 문자열로 쓴다(`DROP_SOLD_OUT`, `DROP_NOT_OPEN`, `TEMPLATE_NOT_FOUND`). 숫자 코드는 쓰지 않는다.
3. **예외 클래스**: 부모는 `BusinessException(ErrorCode)` 하나이고, 필요할 때만 자식을 만든다. 핸들러(`@RestControllerAdvice`)는 하나다.
4. **로그 수준은 상태 코드가 아니라 "누구 잘못인가"로 정한다** (초안의 "4xx는 WARN/INFO, 5xx는 ERROR"에서 바꿈)
   - 사용자 잘못은 INFO/WARN, 우리 잘못은 ERROR(Slack 알림으로 이어짐)다. 그래서 `ErrorCode`가 로그 수준을 가진다.
   - board 경험: 같은 404라도 "없는 번호 요청"은 WARN, "DB에는 있는데 파일이 없음"은 ERROR였다.
5. **모르는 예외**: 500과 일반 메시지만 주고 내부 정보는 숨긴다. ERROR 로그를 남겨 traceId로 찾을 수 있게 한다.
6. **보안 필터 예외(401·403)**
   - 이 예외들은 `ControllerAdvice`까지 오지 않으므로, `AuthenticationEntryPoint`·`AccessDeniedHandler`도 같은 형식으로 응답하게 만든다.
   - board의 "/error 위장" 문제(오류가 /error로 넘어가면서 보안 설정에 막혀 엉뚱한 응답으로 바뀜)도 같은 형식으로 막고 테스트로 고정한다.
7. **외부 연동 실패**: infrastructure에서 우리 예외로 바꿔 던지되 원인을 보존한다(board: "예외도 인터페이스 계약의 일부").
8. **에러 코드 표**는 API 문서에 실어 프론트와의 계약으로 쓴다(기획 2의 4번).
9. **화면 문장** [잠정: 4번]: 백엔드의 `detail`은 사용자에게 보여도 되는 문장으로 쓴다. 프론트는 `code`별로 문장을 바꿔 보여 줄 수 있다.
## 결과
 
- 패키지 이름과 기능 목록은 설계 주간에 ERD와 함께 확정한다.
- 환경 구축 채팅에서 할 것: 프론트 AI 경계(지침·권한·CI 검사), CI를 나누는 방법(경로 필터 함정).
- ArchUnit 테스트와 예외 형식 테스트는 첫 기능을 만들기 전에 뼈대와 함께 만든다.
- 4번 안건에서 함께 정할 것: 성공 응답을 board의 `ApiResponse`처럼 한 겹 감쌀지, 데이터를 그대로 줄지.
