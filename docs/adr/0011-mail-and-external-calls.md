# ADR-0011: 메일은 Resend에 SMTP로 맡기고, 응답을 먼저 준 뒤 가입 여부 확인과 메일은 뒤에서 한다

- 날짜: 2026-11-14
- 상태: 승인 (2026-11-14, 정현)
- 작성: 초안은 멘토 AI, 판단은 정현

> **쉽게 말하면**
> 1. 메일은 우리 서버가 메일함까지 직접 배달하지 않고, 메일 서비스 Resend에 맡긴다. 맡기는 방법은 표준 SMTP라서 서비스를 바꿀 때는 설정값만 바꾼다.
> 2. 요청에서는 형식 검사와 레이트 리밋만 하고 바로 "보냈습니다"로 답한다. 가입 여부 확인, 코드 만들기, 메일 보내기는 모두 뒤에서 한다. 그래서 어떤 주소를 넣어도 응답의 문구와 시간이 같다.
> 3. 외부 호출은 기다림의 끝을 정하고(연결 2초, 한 번 읽을 때 5초), 다시 해서 나아질 실패(잠깐의 실패)에만 두 번 더 시도한다.
> 4. 로컬에서는 가짜 메일 서버(Mailpit)가 메일을 받아 화면에 보여 준다.

## 맥락

- v1 메일: 가입 코드(ADR-0008 코드 먼저 가입), 비밀번호 재설정, "이미 가입되어 있습니다" 안내, 비밀번호 변경 알림, 패스키 등록 알림(ADR-0007·0008, 요구사항 X-3). 알림 메일(Kafka)은 v2다. v1 메일은 Kafka 없이 보낸다(인계 문서 1).
- 가입 코드 보내기와 재설정 요청의 응답은 가입된 이메일이든 아니든 같아야 한다(ADR-0007 3-3, 요구사항 A-2·A-4). 문구뿐 아니라 응답 시간으로도 가입 여부를 캐낼 수 없어야 한다(요구사항 N-1).
- ADR-0007 4-5는 "로그인 전 화면에서 이메일을 받아 메일을 보내 주는 주소는 계정 캐내기와 메일 폭탄의 통로가 된다"고 경고했다. 코드 먼저 가입(ADR-0008)은 바로 그런 주소를 만들므로, 이 ADR과 11번(레이트 리밋)이 그 두 통로를 막아야 한다.
- 출시 전 잠금 동안에는 허용 목록(정현의 두 메일)에만 실제로 보낸다(요구사항 X-1).
- board의 Kafka 실습에서 배운 질문: "외부가 느릴 때 누가 기다리는가"(`max.block.ms`).
- Spring Boot 문서: JavaMail의 기본 타임아웃 몇 개는 무한이라, 응답하지 않는 메일 서버에 스레드가 묶일 수 있다. `spring.mail.host`가 있어야 `JavaMailSender`가 자동으로 만들어진다.
- Resend
  - SMTP: 호스트 `smtp.resend.com`, 사용자 이름 `resend`, 비밀번호 자리에 API 키. 465·2465는 처음부터 TLS(SMTPS), 25·587·2587은 STARTTLS. SMTP도 `Resend-Idempotency-Key` 머리글로 중복을 막을 수 있다.
  - 한도: 무료는 하루 100통·월 3,000통(받은 메일도 센다). 하루는 UTC 자정(한국 9시)에 다시 시작하고, 한도에 닿으면 거절할 뿐 쌓아 두었다 보내 주지 않는다. 속도는 팀마다 초당 10건이고 SMTP도 같다.
  - 반송률 4% 미만, 스팸 신고율 0.08% 미만을 지켜야 하고, 넘으면 발송이 잠시 멈출 수 있다.
  - 보내는 지역은 버지니아·아일랜드·상파울루·도쿄 넷이고 무료도 고를 수 있다. 지역은 메일이 어디서 나가는지만 정하고, 계정 데이터·메일 기록은 지역과 관계없이 미국에 저장된다.
  - 대시보드는 보낸 메일의 본문을 보여 주고, 데이터는 30일 보관한다.
- v1의 외부 호출과 이 ADR의 범위

| 외부 호출 | 어디서 정하나 |
| --- | --- |
| 메일(SMTP) | 이 ADR |
| 파일 창고 올리기·지우기(만료 링크 서명은 서버 안 계산이라 호출이 아님) | ADR-0010. AWS SDK 기본 타임아웃·재시도를 쓴다 [확인 필요: 3주 차, 값] |
| Slack 알림 | 10번 |
| 유출 비밀번호 검사(v1에 없음) | ADR-0009 "다시 검토할 때"가 이 ADR로 넘긴 것. 붙인다면 가입·재설정 요청 안에서 바로 부르는 호출이라, 실패했을 때 통과시킬지 거절할지를 그때 정한다 |

  - 공통 원칙: 모든 외부 호출은 기다림의 끝(타임아웃)을 정한다. 다시 해서 나아질 실패만 다시 시도한다.

## 선택지

### 메일 서비스

| | NCP Cloud Outbound Mailer | AWS SES | **Resend (선택)** |
| --- | --- | --- | --- |
| 쓸 수 있나 | 개인 계정은 쓸 수 없다(사업자 계정 필요) | 쓸 수 있다. 새 계정은 샌드박스(확인한 주소에만, 24시간 200통)에서 시작하고, 아무에게나 보내려면 운영 전환 신청서를 내고 심사를 받는다(보통 24시간 안에 첫 답, 거절될 수 있음) | 가입과 DNS 설정만으로 쓸 수 있다 |
| 비용 | — | 2026-07-21부터 새 SES 계정은 Essentials 플랜: 1,000통에 0.16달러, 월정액 없음(us-east-1 자료) [확인 필요: 서울 값]. SES 전용 무료 구간은 새 고객에게 없고, 정현은 AWS 새 고객이 아니라 신규 크레딧도 없다. 월 3,000통이면 약 0.5달러 | 무료 플랜: 매달 3,000통, 하루 100통. 카드가 필요한지는 공식 요금 페이지에 없다 [확인 필요: 가입 때] |
| 데이터 위치 | 한국 | 서울 리전을 고르면 한국 | 미국(국외 이전) |
| 실무 (멘토 판단) | 국내 기업 일부 | 가장 널리 쓰임 | 스타트업·개인 개발자에게 흔함. 발송 경로에 SES가 있다는 2차 자료가 있다(도메인 설정의 SPF가 `amazonses.com`) [확인 필요: 2주 차 DNS 화면] |

### 가입 여부에 따라 갈리는 일을 어디서 하나

```
가. 요청 안에서 (초안)
  가입된 주소    검사 → DB(있음) → 메일 맡김 ──────────────────→ 응답
  처음 보는 주소  검사 → DB(없음) → 코드 만들기·Redis 저장 → 메일 맡김 → 응답 (조금 더 김)
  Redis가 멈추면: 가입된 주소는 200, 처음 보는 주소는 500

나. 뒤에서 (선택)
  어떤 주소든    형식 검사 → 레이트 리밋 → 일을 맡김 → 응답   (늘 같은 일)
  메일 풀(뒤)    DB 확인 → 있음: "이미 가입" 메일 / 없음: 코드 만들기·저장 → 코드 메일
```

- 다. 요청 안에서 하되 두 길이 같은 일을 하게 맞춤: 숫자를 맞추는 일이라 깨지기 쉽다.
- 라. 작은 시간 차이는 감수: 승인한 요구사항 N-1(응답 시간으로도 드러내지 않음)을 낮춰야 한다.

### 한도에 걸렸을 때의 답

- **가. 누구에게나 같은 429 + 코드 하나 (선택)**: 화면은 "잠시 후 다시 시도해 주세요". 규칙은 가입 여부와 관계없이 주소마다 같은 계산이라 캐낼 것이 없다.
- 나. 걸려도 "보냈습니다"로 답하고 조용히 보내지 않음: 사용자가 오지 않을 코드를 기다리고, 문제가 숨는다.

### 맡기는 방법

- **SMTP (선택)**: 메일 서비스들이 공통으로 받는 표준. 로컬의 Mailpit도 SMTP라 로컬과 운영의 코드가 같다. 중복 막기는 `Resend-Idempotency-Key` 머리글로 할 수 있고, 다른 메일 서버는 모르는 머리글을 무시하므로 Resend에 묶이지 않는다.
- Resend 전용 API(HTTP): 보낸 메일의 ID를 돌려줘 대시보드·웹훅과 맞춰 보기 쉽고 오류가 더 자세하다. 대신 Resend에 묶이고 로컬에는 따로 가짜가 필요하다. 속도 한도는 SMTP와 같다.

## 결정

1. **메일 서비스**: Resend 무료 플랜, 보내는 지역은 **도쿄**(한국 메일함에 가까움, 정현 11/14). 보내는 방법은 표준 SMTP(Spring의 `JavaMailSender`)이고 전용 API는 쓰지 않는다. 바꿀 때는 SMTP 주소·계정 설정만 바꾼다. SES 서울 리전은 옮겨 갈 곳으로 적어 둔다(국외 이전을 없애고 싶거나 하루 100통이 모자랄 때).
2. **응답 먼저, 갈리는 일은 뒤에서** (선택지 나)
   - 가입 코드 보내기·재설정 요청: 요청에서는 이메일 정리(A-12)·형식 검사·레이트 리밋(결정 5)만 하고 일을 맡긴 뒤 바로 답한다. 가입 여부 확인, 코드·토큰 만들기와 Redis 저장, 메일 보내기는 메일 풀에서 한다. 응답은 누구에게나 같은 상태와 본문이다(202 "받아 둠"이 뜻에 맞다 [잠정: 껍데기]).
   - 코드 확인의 시도 횟수 제한도 코드가 없는 주소(가입된 주소)에서 똑같이 걸려야 한다(4주 차 테스트).
   - 메일이 어느 흐름에서 맡겨지는가

     | 메일 | 맡기는 때 |
     | --- | --- |
     | 가입 코드, 이미 가입, 재설정 | 요청에서 바로 맡김(트랜잭션 없음). 갈림은 뒤에서 |
     | 비밀번호 변경 알림 | 새 비밀번호를 저장한 커밋이 끝난 뒤(롤백된 일의 메일이 나가지 않게) |
     | 패스키 등록 알림 | 저장은 Spring Security 필터가 한다. 알림을 걸 자리(저장소 감싸기 등)는 5주 차 [확인 필요] |

     - 커밋 뒤에 실행되는 리스너(`@TransactionalEventListener`)는 트랜잭션 없이 발행한 이벤트를 아예 부르지 않는다. 트랜잭션이 없는 흐름에 쓰면 메일이 조용히 안 나간다.
   - **메일 전용 풀**
     - `@Bean(defaultCandidate = false)`로 등록하고 이름으로 골라 쓴다. 그냥 Executor 빈으로 등록하면 Boot의 기본 실행기가 물러나고 모든 `@Async`가 메일 풀로 간다.
     - 스레드 수는 Resend의 초당 한도보다 작게(예: 2), 대기열 크기는 정해 둔다 [잠정: 숫자는 4주 차]. Spring Boot 기본 작업 풀은 대기열에 끝이 없어 메일 서비스가 멈추면 보낼 메일이 메모리에 끝없이 쌓인다. 가상 스레드를 켜면(ADR-0003 12번 실험) 기본 실행기는 대기열 없이 작업마다 스레드를 만드는 방식으로 바뀐다. 메일 풀을 따로 두면 그 실험 때도 메일 쪽은 그대로다.
     - 대기열이 차면 그 메일은 버리고 로그를 남긴다. 기본 거절 정책은 요청 스레드에 예외를 던져 500이 되므로, 거절 정책을 "로그 남기고 버림"으로 직접 정한다. 응답은 그대로다.
   - **우아한 종료**: 배포 때는 대기 중인 메일을 보낼 때까지 잠깐 기다린다. 직접 만든 풀은 기본이 "기다리지 않음"이라 기다림을 켜고 시간을 정한다. 갑자기 죽으면 사라진다.
   - 끝내 실패하면 로그를 남긴다. 코드·재설정 메일은 사용자가 "다시 보내기"로 해결한다. 알림 메일(비밀번호 변경·패스키 등록)은 다시 보내기가 없다(감수하는 것).
   - 실패한 메일을 모아 두었다가 다시 보내는 장치(Outbox)는 v2 알림 때 본다. 후보는 ADR-0004에서 보류한 Spring Modulith의 이벤트 기록이다.
3. **타임아웃·재시도**
   - 연결 2초, 읽기 5초, 쓰기 5초(`mail.smtp.connectiontimeout`·`timeout`·`writetimeout`, 기본값은 무한이라 꼭 정한다) [잠정: 2주 차 실제 측정 뒤]. 읽기 5초는 한 번 읽을 때의 한도다. SMTP는 한 통에 여러 번 주고받으므로 한 통 전체의 한도가 아니다.
   - 다시 시도는 연결 실패·타임아웃과 SMTP의 4xx 응답("잠깐 뒤에 다시")에만 두 번 더 하고, 간격은 1초 → 3초로 늘린다. SMTP의 5xx 응답(인증 실패, 거절 같은 영구 실패)은 다시 하지 않는다. 도구는 Spring Framework 7의 `RetryTemplate`(또는 `@Retryable`)이다. Spring Retry는 보관(archived)되었다. Framework의 다시 시도 횟수는 첫 시도를 빼고 세므로 "두 번 더" = 2다.
   - Resend가 하루 한도·초당 한도를 넘었을 때 SMTP에서 4xx로 답하는지 5xx로 답하는지는 아직 모른다 [확인 필요: 2주 차]. 5xx라면 잠깐의 한도 초과도 버려지므로 스레드 수를 초당 한도보다 작게 둔다.
   - 포트는 465(처음부터 TLS)를 쓴다(클라우드에서 25번은 막히는 경우가 많다). 465가 막혀 있으면 2465. 켜는 법: 프로토콜은 `smtp` 그대로 두고 `mail.smtp.ssl.enable=true`. `spring.mail.protocol=smtps`로 바꾸면 설정 이름이 모두 `mail.smtps.*`로 바뀌어 위 타임아웃이 적용되지 않는다(다시 무한). SSL과 계정은 `application-prod.yaml`에만 둔다(로컬 Mailpit은 평문).
   - `mail.smtp.ssl.checkserveridentity=true`를 명시한다(TLS 호스트 이름 확인). Spring Boot 메일 자동 설정이 이것을 켜지 않던 취약점(CVE-2026-40992, 4.0.0~4.0.6 등)이 있었다. 4.1.x는 영향 목록에 없지만, 명시해 두면 버전에 기대지 않는다. API 키가 로그인(AUTH)으로 지나가는 길이다.
4. **같은 메일 두 번, 옛 코드**
   - 응답만 늦고 실제로는 보내진 경우 다시 시도하면서 두 번 갈 수 있다. 메일마다 UUID를 만들어 `Resend-Idempotency-Key` 머리글로 붙여 이 중복을 막는다(유지 시간 [확인 필요]).
   - 사용자가 "다시 보내기"를 누르면 새 코드를 만들고, 가입 코드와 재설정은 마지막 것만 유효하다. 대기열에 있거나 다시 시도 중이던 옛 코드 메일이 새 코드보다 늦게 도착하면 사용자는 무효 코드를 넣게 된다. 그래서 보내기 직전마다(첫 시도와 다시 시도 모두) "이 코드가 아직 그 주소의 마지막 코드인가"를 확인하고, 아니면 보내지 않는다.
5. **한도와 같은 답** (선택지 가)
   - 같은 주소 다시 보내기 간격(4주 차), 같은 주소 하루 횟수·IP별 한도·전체 하루 상한(5주 차, 11번)에 걸리면 누구에게나 같은 429와 코드 하나로 답한다 [잠정: 코드 이름은 껍데기]. 계산은 가입 여부와 관계없이 정리한 이메일(A-12)마다 같다.
   - 전체 하루 상한은 Resend의 100통보다 낮게, 메일 종류별로 나눠 가입 코드가 재설정·알림 몫까지 쓰지 않게 한다. 하루는 Resend와 같은 UTC 기준이다 [잠정: 숫자는 11번].
6. **로컬·테스트**
   - 로컬은 Mailpit을 `backend/compose.yaml`에 더한다. 이미지는 버전 태그를 붙이고(ADR-0003), 포트는 MySQL처럼 `127.0.0.1`에만 연다(웹 화면에 받은 메일이 다 보인다). 보낸 메일은 밖으로 나가지 않는다.
   - 테스트는 실제 메일 서비스를 부르지 않는다. 4xx·5xx 다시 시도 테스트는 Mailpit의 Chaos 기능(SMTP 단계별로 정한 오류 코드를 돌려줌)으로 한다 [확인 필요: 4주 차, Testcontainers로 띄우기]. 테스트 설정에는 `spring.mail.host`가 없어 `JavaMailSender`가 만들어지지 않으므로, 계약 추출 테스트(ADR-0006)가 앱을 띄울 때 깨지지 않게 가짜를 둔다.
7. **출시 전 잠금**: 허용 목록 밖의 주소에는 실제로 보내지 않는다. 검사는 "보내기 직전 한 곳"에서 메일 다섯 종류 모두에 한다. 뒤에서 하므로 응답은 누구에게나 같다(요구사항 X-1).
8. **로그**
   - 메일 본문과 코드·토큰은 로그에 남기지 않고(N-3), JavaMail의 디버그 출력은 켜지 않는다(SMTP 대화 전체와 본문이 찍힌다). 받는 주소는 가려서 남긴다.
   - 실패 로그에 예외를 통째로 찍지 않는다. SMTP 서버의 답에 받는 주소가 그대로 들어 있을 수 있다. 예외 종류와 SMTP 응답 코드만 남긴다.
   - 메일 스레드의 로그에도 요청의 traceId가 붙게 한다(ADR-0006 결정 5, N-7). Boot 4.1의 `spring.task.execution.propagate-context=true`(기본 꺼짐)를 켜고 메일 풀을 Boot가 주는 빌더로 만든다 [확인 필요: 4주 차 테스트].
   - 로그 수준은 ADR-0004 결정 3의 4번(누구 잘못인가)을 따른다. 주소 문제처럼 사용자 쪽이면 WARN, 인증 실패(535)·연결 실패가 이어짐·대기열 가득처럼 우리 쪽이면 ERROR(Slack 알림)다. 아무 주소나 넣어 Slack 알림을 울리는 길을 막는다.

## 이유

1. NCP 메일은 개인 계정으로 쓸 수 없다. SES는 우리 양이면 월 0.5달러 정도지만 새 고객이 아니라 실제로 청구되고, 샌드박스 운영 전환 심사(결과를 모르는 일)가 여유가 없는 2주 차(M2)에 들어온다. Resend 무료 플랜은 v1 메일 양에 충분하고 청구가 없다.
2. SMTP는 메일 서비스들이 공통으로 받는 표준이라 특정 회사에 묶이지 않는다. Spring Boot가 기본으로 지원하고, 나중에 SES로 옮길 때도 설정만 바꾼다.
3. 응답을 먼저 주면 메일 서비스의 속도가 화면 속도에 영향을 주지 않는다. 가입 여부에 따라 갈리는 일까지 뒤로 보내면, 요청에서 하는 일이 어떤 주소에나 같아져 응답 시간과 상태 코드로도 가입 여부를 캐낼 수 없다(N-1). 숫자를 맞추는 대신 구조로 같게 만든다.
4. 다시 시도는 "다시 해서 나아질 실패"에만 한다. 짧은 타임아웃은 느린 외부 호출이 스레드를 오래 잡지 않게 한다(board의 "누가 기다리는가").
5. 한도에 걸렸을 때 같은 429로 답하면 사용자가 오지 않을 코드를 기다리지 않고, 규칙이 같으니 캐낼 것도 없다. ADR-0007 4-5가 경고한 두 통로(캐내기, 메일 폭탄)를 이 규칙과 11번이 막는다.

## 감수하는 것

- 무료 플랜은 하루 100통을 넘으면 그날(한국 9시까지) 보내지지 않는다. 넘기 시작하면 유료(월 20달러부터) 또는 SES로 옮긴다.
- Resend가 받아 두면(250) 우리 로그에는 "성공"으로 남는다. 없는 주소는 나중에 반송으로 Resend 대시보드·웹훅에만 보이고, 메일이 실제로 도착했는지는 응답 시점에 모른다.
- 누군가 남의 주소·없는 주소를 잔뜩 넣어 코드 메일을 보내게 하면, 하루 100통이 바닥나 진짜 사용자가 코드를 못 받고, 반송률(4%)이나 신고율(0.08%)을 넘겨 Resend 발송이 멈출 수 있다. 출시 전 잠금 동안에는 허용 목록이 막고, 그 뒤에는 결정 5와 11번이 막는다.
- Resend가 멈추면 가입과 재설정이 멈춘다(다른 서비스로 넘기는 장치가 없음). 로그인과 받기는 메일과 관계없다.
- 서버가 갑자기 죽으면 보내던 메일은 사라진다(Outbox가 없음). 알림 메일(비밀번호 변경·패스키 등록)은 끝내 실패하면 그 알림 하나가 가지 않는다. ERROR 로그와 Slack 알림으로만 안다.
- Resend 대시보드는 보낸 메일의 본문(코드·재설정 링크)을 30일 보여 준다. 공유 링크(누구나 48시간 볼 수 있음)는 쓰지 않고, Resend 계정에 2단계 인증을 켜고 [확인 필요: 지원 여부], 열기·클릭 추적은 꺼진 채로 둔다(기본 꺼짐. 켜면 링크가 Resend를 거친다).
- 메일 주소와 본문이 Resend로 넘어가므로 개인정보의 국외 이전이다(저장은 미국, 발송은 도쿄라 일본). 처리방침에 적을 것 [확인 필요: 5주 차, 법 원문]:
  - 이전 근거: 개인정보 보호법 제28조의8 제1항 제3호 가목(계약의 체결·이행을 위한 처리위탁·보관 + 처리방침 공개). 시행령 제31조가 근거도 적게 한다.
  - 제2항의 사항: 이전되는 항목, 나라(미국, 일본)·시기·방법, 받는 회사의 이름·연락처, 이용 목적·보유 기간, 이전을 거부하는 방법·절차·효과(3~5호는 원문으로 확인).
  - 국외 이전과 별개로 업무 위탁(제26조, 수탁자·위탁 업무) [확인 필요]. Resend의 하위 처리자 목록도 함께 본다.
- 네이버·다음 메일함에 잘 도착하는지는 아직 모른다 [확인 필요: 2주 차 실제 발송].
- 무료 플랜의 조건은 바뀔 수 있다 [확인 필요: 2주 차 가입 때 요금 페이지].

## 결과

- **2주 차(7번과 함께)**: Resend 가입과 계정 2단계 인증, 도메인을 **도쿄** 지역으로 만들기, 발신 도메인 설정(SPF·DKIM·DMARC, `damda.dev`의 DNS 위치와 함께), API 키는 "보내기 전용 + `damda.dev` 하나"로 만들어 서버 환경 변수로(공개 저장소에 쓰지 않음), 서버에서 465(안 되면 2465)로 나갈 수 있는지, 네이버·다음·지메일로 실제 발송 확인과 타임아웃 측정, 한도 초과 때의 SMTP 응답 코드, 발송 경로(SPF의 `amazonses.com`) 확인.
- **11/14~15 껍데기**: 가입 코드 보내기·재설정 요청은 누구에게나 같은 상태와 본문(202 [잠정]). 한도의 429 코드 이름.
- **4주 차(메일·계정)**: 메일 보내기 기능(인터페이스는 application, SMTP 구현은 infrastructure, ADR-0004의 의존 방향), 결정 2의 흐름(갈림은 뒤에서, 커밋 뒤는 비밀번호 변경 알림만), 메일 풀(`defaultCandidate = false`, 스레드 수·대기열·거절 정책·종료 때 기다림), 타임아웃·재시도(`RetryTemplate`)·SSL·호스트 이름 확인 설정, 멱등 머리글과 "마지막 코드인가" 확인, traceId 이어 붙이기, Mailpit을 Compose에 더하고 로컬 설정(`spring.mail.host`)에 연결, 메일 문구, 코드 길이·만료, 같은 주소 다시 보내기 간격, 한 통 보내는 데 걸린 시간 메트릭.
  - 테스트: 메일 서비스가 느려도 응답이 바로 나감, 가입된 이메일과 아닌 이메일의 응답(상태·본문)이 같음, 코드 확인의 시도 횟수 제한도 같음, 요청에서 회원 저장소를 부르지 않음, 4xx·연결 실패는 다시 하고 5xx는 하지 않음(Mailpit Chaos), 옛 코드는 보내지 않음, 대기열이 차면 버리고 로그를 남기며 응답은 그대로, 허용 목록 밖은 보내지 않음.
- **5주 차(11번, 처리방침)**: 같은 주소 하루 횟수·IP별 한도·전체 하루 상한(종류별, UTC), 국외 이전과 위탁 문구, 패스키 등록 알림을 걸 자리.
- **7번(운영 구성)**: 컨테이너가 멈출 때 기다리는 시간(Compose `stop_grace_period`)을 Spring의 종료 시간보다 길게 둔다. docker stop은 기본 10초 뒤 강제로 끄고, Spring은 단계마다 기본 30초를 기다린다. 메일 헬스 지표는 끈다(`management.health.mail.enabled=false`). 켜 두면 Resend가 멈출 때 `/actuator/health`가 DOWN이 되어 남의 장애가 우리 서버의 준비됨·배포 판단을 막는다(N-10).
- **10번(관측성)**: 메일 ERROR 알림은 같은 것끼리 묶고, 보낸 수·실패 수·버린 수 메트릭, Resend 대시보드의 반송률·신고율을 주간 점검 때 본다.
- **12번(부하 테스트)**: 메일은 Mailpit으로 돌린다(실제로 보내면 하루 100통이 바닥나고 없는 주소로 반송률이 오른다). ADR-0003의 예측("가상 스레드의 차이는 느린 외부 호출인 메일에서")은 메일이 요청 밖으로 나가 요청 경로에서는 볼 수 없게 되었으므로 비교 대상을 다시 본다.
- **요구사항** (이 ADR의 PR에서 고침): 5번 표의 "메일 서비스, 외부 호출의 타임아웃·재시도, 메일을 응답과 떼어 보내는 방법" 줄을 지운다. N-4에 "가입 코드 보내기·재설정 메일 보내기는 같은 주소 단위로도 세고, 막힐 때의 답은 가입 여부와 관계없이 같다"를 더한다. X-1 ①의 "가입 코드 메일은"을 "메일은(다섯 종류 모두)"로 고친다.
- **용어 사전** (보강 때): SMTP, SMTP 응답 코드(4xx·5xx), 타임아웃, 다시 시도, 메일 전용 풀·대기열, 우아한 종료, Mailpit, SPF·DKIM·DMARC, 반송, 멱등 키, 국외 이전.
- **11/15 점검**: 4주 차 메일 어림 6시간은 위 목록으로는 빠듯하다. 실측과 함께 다시 어림한다.
- **v2**: 알림 메일(Kafka), 실패 메일을 모아 다시 보내는 장치(Outbox, Spring Modulith 후보), 수신 거부 링크, 반송 웹훅을 받아 기록.

## 정현의 판단 (대화에서 옮김)

> 정현의 말을 대화에서 옮겼다. 읽기 쉽게 조금 다듬었지만 뜻은 바꾸지 않았고, 정현이 말하지 않은 이유는 넣지 않았다.

- 메일 서비스 (11/14): NCP를 사업자 계정으로 바꾸는 절차가 복잡한지 물었다(사업자등록이 필요해서 뺌). SES는 "AWS 새 고객이 아니어서 무료 크레딧은 못 받아서 배제". Resend 무료 한도가 매달인지 확인한 뒤 "오케이 좋습니다."
- 응답 먼저, 타임아웃·재시도, Mailpit (11/14): "6-2, 3, 4는 좋네요."
- 첫 검토 (11/14, 같은 채팅): 멘토가 고친 것: SMTP는 HTTP와 반대로 4xx가 잠깐 실패(다시 함)이고 5xx가 영구 실패(안 함)인데 초안이 HTTP 기준으로 적었다. JavaMail의 무한 타임아웃과 Spring 기본 풀의 끝없는 대기열을 적지 않았다. 코드 메일 남용으로 하루 한도가 바닥나는 경우, 국외 이전, 로그, 우아한 종료를 빠뜨렸다.
- 최대 노력 검토 (11/14, 새 채팅): [고침] 26개, [질문] 4개. 멘토가 고친 것(요약):
  - 틀린 사실: SES 값(새 SES 계정은 1,000통 0.16달러, 무료 구간 끝남), "멱등 키는 전용 API만"(SMTP 머리글로도 됨), "실패는 로그로 안다"(반송은 대시보드에만).
  - 요구사항 N-1과 부딪힘: "응답 먼저"는 메일 서비스 속도만 빼고, 요청 안에서 가입 여부에 따라 갈리는 일은 시간 차이로 남았다.
  - 그대로 만들면 다르게 동작할 곳: 커밋 뒤 리스너는 트랜잭션 없으면 불리지 않음, `smtps`로 바꾸면 타임아웃 설정 이름이 바뀜, 전용 풀을 그냥 등록하면 기본 실행기가 물러남, 기본 거절 정책은 500, 메일 헬스 지표가 Resend 장애를 우리 DOWN으로 만듦, docker stop 10초.
  - 빠진 것: 외부 호출의 범위(ADR-0009의 유출 비밀번호 검사 넘김 포함), 호스트 이름 확인(CVE-2026-40992), 옛 코드가 늦게 도착하는 경우, traceId, 로그 수준(ADR-0004), 반송률로 인한 발송 정지, Resend 장애 = 가입·재설정 장애, 대시보드에 남는 본문, 국외 이전에 적을 항목, 7·10·11·12번에 넘길 것.
- 질문의 답 (11/14)
  - 질문 1(메일 서비스): 정현은 "SES를 쓴다는 말인가, 새 계정이 아니어서 청구되지 않나"를 물었다. 멘토가 지금 SES를 쓰는 것이 아니라 바꿀지 묻는 것이고, 새 고객이 아니면 SES는 소액이지만 청구되며 Resend는 청구가 없다고 답했다. → 가(Resend 유지).
  - 질문 2(갈리는 일을 어디서): "좋습니다." → 뒤에서.
  - 질문 3(한도에 걸렸을 때): "가 좋습니다." → 누구에게나 같은 429.
  - 질문 4(발송 지역): "문제가 없다면 좋습니다." 처리방침에 일본이 들어가는 뜻을 물었다. 멘토가 도쿄에서 보내면 메일 주소·본문이 일본에서 처리되므로 처리방침의 나라에 일본을 더 적는다고 답했다. 도쿄와 미국의 차이도 물었다(아래 확인 필요). → 도쿄.
  - "일단 확인입니다."로 반영을 정했다.
