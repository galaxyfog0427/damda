# ADR-0008: 일반 템플릿은 로그인 없이 받고, 로그인한 회원이 받으면 라이브러리에 자동으로 담는다. 드롭은 로그인과 이메일 인증을 요구한다
 
- 날짜: 2026-11-07
- 상태: 승인 (2026-11-07, 정현)
- 작성: 초안은 멘토 AI, 검토·승인은 정현
> **쉽게 말하면**
> 1. 일반 템플릿은 누구나 로그인 없이 받는다(PPT 다운로드, 노션 링크 열기).
> 2. 로그인한 회원이 받으면 그 템플릿이 라이브러리에 자동으로 담긴다. 처음 받을 때 한 번만 담긴다. 로그인하지 않은 사람은 라이브러리가 없으므로 받기만 한다.
> 3. 드롭은 로그인하고 이메일 인증을 마친 회원만 받는다. 계정당 1개를 세야 하기 때문이다.
> 4. 규칙 한 줄: **사람마다 세어야 하는 것에만 로그인을 요구한다.**
> 5. 로그인하지 않은 방문자에게는 세션을 만들지 않는다(ADR-0007). v1에서는 템플릿별 숫자(받은 수)만 모으고, 방문자를 알아보는 값은 모으지 않는다.
> 6. 이메일 가입은 메일로 받은 코드를 넣어야 끝난다. 그래서 "인증 전 회원"이 생기지 않는다. 소셜 가입은 공급자가 확인한 계정으로 보고 따로 인증하지 않는다.
 
## 맥락
 
- 인계 문서 1의 5번 표는 v1 받기를 "로그인 → 라이브러리에 추가(무료 주문) → PPT 다운로드(만료 링크)·노션 링크 → 내 라이브러리"로 적었다. 받으려면 로그인해야 하는 모양이었다. ADR-0001의 흐름도 "둘러보기 → 라이브러리에 추가(주문) → 다운로드"다.
- ADR-0002는 "라이브러리에 추가"를 내부적으로 0원 주문으로 만든다고 정했다. 결제가 붙어도 큰 변경 없이 가능하게 하기 위해서다.
- ADR-0007(로그인과 인증)을 승인하기 전에 정현이 "다운로드에 로그인이 꼭 필요한가"를 물었다. ADR-0007은 로그인을 **어떻게** 하는지 정하고, 어느 기능에 로그인이 **필요한지**는 이 ADR이 정한다.
- ADR-0007 4-5: 드롭은 계정당 1개이고, 이메일 인증을 마친 계정만 받는다. 미인증 계정은 로그인은 되지만 라이브러리 추가와 드롭은 막는다.
- ADR-0007 3-2: 로그인하지 않은 사람에게는 세션을 만들지 않는다(요청 저장 끄기, CSRF 토큰은 쿠키).
- 모든 템플릿은 무료다(ADR-0002). 유료 판매는 보류 층이다. 좋아요·좋아요순은 v2다(인계 문서 1의 5번).
- 인계 문서 1의 12번은 "다운로드순"의 숫자를 무엇으로 셀지(클릭 수 vs 라이브러리에 추가한 회원 수)를 설계 주간에 넘겼다.
## 결정 1: 일반 템플릿은 로그인 없이 받는다. 로그인한 회원이 받으면 라이브러리에 자동으로 담는다
 
```
일반 템플릿의 [받기]
  로그인 안 함          → 다운로드 / 노션 열기                       (주문 없음, 받은 수 +1)
  로그인 + 인증 마침     → 다운로드 / 노션 열기 + 라이브러리에 담김    (처음 받을 때만 0원 주문 1건)
 
드롭 템플릿
  로그인 + 인증 마침     → [라이브러리에 추가] (드롭 조건 안에서 선착순) → 그 뒤 라이브러리에서 언제든 다운로드
  그 밖                  → 로그인·인증 안내
```
 
- 같은 회원이 같은 템플릿을 다시 받으면 주문을 새로 만들지 않는다. "회원 + 템플릿"은 중복 불가로 둔다(board의 좋아요와 같은 방식) [잠정: 설계 주간].
- 라이브러리에 담긴 템플릿은 라이브러리에서 다시 받을 수 있다.
- 결정 4(코드 먼저 가입)로 "로그인했지만 인증 전인 회원"은 생기지 않는다. 그래서 로그인한 회원의 받기는 언제나 라이브러리에 담긴다.
  - 초안에는 "로그인 + 인증 전 → 받기만, 담기지 않음" 줄이 있었다. 결정 4를 정하며 뺐다.
  - 받기 응답에는 "라이브러리에 담겼는지"를 넣는다. 로그인하지 않은 사람에게 안내를 띄우는 데 쓴다(이름은 설계 주간).
- 로그인하지 않은 사람에게 로그인을 강요하는 창은 띄우지 않는다. 받은 뒤 "로그인하면 받은 템플릿이 라이브러리에 모입니다" 같은 안내만 둔다 [잠정: 설계 주간, 화면과 문구].
- [잠정: 설계 주간] 받기는 POST로 한다. 응답으로 PPT의 만료 링크나 노션 링크를 준다.
  - 로그인한 회원의 받기는 라이브러리에 담는다(상태가 바뀐다). ADR-0006의 메서드 규칙상 GET이 될 수 없다.
  - 검색 엔진 봇은 GET 링크를 따라간다. POST면 봇이 지나가며 받은 수를 올리지 않는다.
  - 로그인하지 않은 사람의 POST에도 CSRF 헤더가 필요하다. 토큰은 쿠키(`XSRF-TOKEN`)에서 오므로 세션은 생기지 않는다(ADR-0007 3-2).
선택지:
 
| | A. 받기 전부 로그인 (처음 그림) | B. 일반은 로그인 없이, 드롭은 로그인 (선택) | C. 전부 로그인 없이 |
| --- | --- | --- | --- |
| 처음 온 사람 | 가입해야 받음 | 바로 받음 | 바로 받음 |
| 라이브러리 | 받은 것 전부 | 로그인한 회원이 받은 것 | 쓸 이유가 거의 없음 |
| 드롭 "계정당 1개" | 셀 수 있음 | 셀 수 있음 | 셀 수 없음(드롭이 무너짐) |
| 주문(ADR-0002) | 모든 받기 | 로그인한 회원의 받기, 드롭 | 거의 없음 |
| 받은 수 | 회원 수로 정확 | 로그인 없는 받기는 부풀릴 수 있음 | 부풀릴 수 있음 |
| 봇의 대량 받기 | 막기 쉬움 | 레이트 리밋으로 막음 | 레이트 리밋으로 막음 |
 
이유:
1. 템플릿 사이트를 보면, 사람마다 셀 필요가 없는 무료 자료는 가입 없이 주는 곳이 있다.
   - SlidesCarnival은 가입도 다운로드 제한도 없다.
   - Slidesgo는 무료 사용자의 다운로드를 한 달에 몇 개로 센다. 그래서 가입을 요구하거나, 가입하면 더 준다(자료마다 숫자가 2~10개로 다르고, 시기에 따라 바뀐 것으로 보인다).
   - 우리 일반 템플릿은 세지 않으므로 SlidesCarnival 쪽이고, 드롭은 계정당 1개를 세므로 Slidesgo 쪽이다.
2. 처음 온 사람이 가입 없이 바로 받는다. 가입은 라이브러리와 드롭이 필요할 때 한다.
3. 로그인이 필요한 곳이 한 줄로 정리된다. 사람마다 세어야 하는 것(드롭 계정당 1개, 라이브러리, v2 좋아요, 보류 층의 유료 구매)에만 로그인을 요구한다.
4. ADR-0002의 주문은 그대로 산다. 로그인한 회원의 받기와 드롭은 주문이다. 결제가 붙으면 유료 템플릿은 주문이 있어야 받으므로 로그인이 필요해진다. 받기 규칙에 "가격이 0이 아니면 주문이 있어야 한다"가 더해지는 정도다.
버린 선택지:
- **A**: 처음 그림이다. 받은 수가 정확하고 봇을 막기 쉽지만, 세지 않아도 되는 무료 받기까지 가입을 요구한다.
- **C**: 드롭의 "계정당 1개"를 셀 수 없다.
- **B에서 [라이브러리에 추가]를 따로 누르기**: 멘토가 처음 B를 추천할 때는 이 점을 정하지 않았다. 정현이 "받으면 알아서 라이브러리로"를 더했다.
- **받지 않고 담기만 하기(찜)**: v1에 없다. 필요하면 v2의 좋아요와 함께 본다.
감수하는 것:
- 받은 수가 주문 수보다 많아진다. 로그인하지 않은 받기에는 주문이 없다.
  - "다운로드순"의 숫자(인계 문서 1의 12번)를 설계 주간에 다시 본다. 라이브러리에 담은 회원 수로 세면 부풀리기 어렵지만 로그인하지 않은 받기가 순위에 들어가지 않는다. 받기 횟수로 세면 모두 들어가지만 부풀릴 수 있다.
- 로그인 없이 누구나 받으므로, 봇이 모든 템플릿을 반복해서 받을 수 있다. 전송량이 비용이 된다(9번).
  - 받기 POST를 레이트 리밋 대상에 넣는다(11번).
  - PPT 링크는 만료되므로 링크를 퍼 가도 오래 쓰지 못한다. 받은 파일 자체를 퍼 가는 것은 막지 못한다(로그인을 요구해도 같다).
- 가입할 이유가 줄어든다. 라이브러리와 드롭이 가입할 이유가 된다.
- ADR-0001의 흐름(둘러보기 → 라이브러리에 추가 → 다운로드)은 드롭에만 그대로 맞는다. 일반 템플릿은 이 ADR의 흐름을 따른다. 승인한 ADR-0001·0002의 본문은 고치지 않는다.
## 결정 2: 드롭은 로그인과 이메일 인증을 요구한다
 
- ADR-0007 4-5의 규칙 문장을 그대로 따른다("계정당 1개이고, 이메일 인증을 마친 계정만").
- 드롭 템플릿은 [라이브러리에 추가](선착순)가 먼저고, 다운로드는 그 뒤에 라이브러리에서 한다. 선착순을 정하는 것은 "추가"이지 다운로드가 아니다.
- [설계 주간] 드롭이 끝난 템플릿을 어떻게 할지(계속 드롭 전용 / 일반 템플릿으로 풀기)는 드롭 흐름 그림(인계 문서 1의 12번)과 함께 본다.
## 결정 3: 로그인하지 않은 방문자의 세션과 데이터
 
### 3-1 세션은 만들지 않는다 (ADR-0007에서 정함)
 
```
로그인하지 않은 방문자
  브라우저   XSRF-TOKEN=8f1c…   (아무 뜻 없는 무작위 값. 사람과 묶이지 않음)
  서버       아무것도 남지 않음   (Redis에 세션 없음)
  받기       POST + X-XSRF-TOKEN → 링크를 받음. 이때도 세션은 생기지 않음
```
 
- ADR-0007 3-2 그대로다. 예외는 로그인하려는 순간뿐이다(운영 계정의 패스키 확인 준비, 나중의 소셜 로그인 시작).
- 방문자가 기억해야 할 것(예: 고른 필터)이 생기면 브라우저 안(주소나 localStorage)에 둔다. 서버는 모른다. v1에는 필요한 것이 보이지 않는다.
### 3-2 데이터는 템플릿별 숫자만 모은다 (A, 정현 11/7)
 
모을 수 있는 것을 네 종류로 나눈다.
 
| 종류 | 예 | 방문자를 알아보나 | v1 |
| --- | --- | --- | --- |
| 템플릿별 숫자 | 받은 수 | 아니오 | 모음 (다운로드순) |
| 운영 숫자 | 요청 수, 에러 수, 응답 시간 | 아니오 | 모음 (관측성, 10번) |
| 접속 로그 | 시각, 주소, IP | IP는 사람에 닿을 수 있음 | 남김 (장애 조사, 레이트 리밋. 보관 기간은 7·10번) |
| 방문자 행동 기록 | 이 브라우저가 무엇을 보고 무엇을 받았나 | 예 (방문자 쿠키) | 모으지 않음 |
 
선택지:
- **A. 서버에서 템플릿별 숫자만 (추천)**: 받은 수만 센다. 방문자를 알아보는 쿠키를 새로 두지 않는다.
- **B. 외부 분석 도구(예: Google Analytics)**: 방문자가 어디서 와서 무엇을 보다 나갔는지 공짜로 본다. 대신 방문자 식별 쿠키가 생기고, 데이터가 외부 회사로 간다. 외부 스크립트가 우리 페이지에 들어온다(7번의 CSP). 광고 차단기에 막히면 숫자가 빈다.
- **C. board 방식의 방문자 쿠키**: board에서 비회원 조회수의 중복을 막으려고 `board_visitor` UUID 쿠키를 썼다. 받은 수의 중복을 걸러 낼 수 있지만, 쿠키를 지우거나 쿠키를 무시하는 봇에는 소용이 없다.
- **D. 아무것도 모으지 않음**: 다운로드순을 만들 수 없다.
추천 A의 이유:
1. v1에서 실제로 쓰는 숫자는 다운로드순의 받은 수 하나다. 방문자 흐름은 아직 쓸 곳이 없다.
2. 모으지 않은 개인정보는 새지 않고, 처리방침에 적을 것도 적다.
3. 나중에 붙이기 쉽다. 사이트를 공개(M3)한 뒤 방문자가 생기고 궁금한 것이 생기면 B를 그때 정한다. C는 다운로드 수 정의(설계 주간)에서 중복을 걸러야 한다고 정해질 때 다시 본다.
개인정보 처리방침과의 관계 (어느 선택지든 해당):
- 처리방침에는 보통 "개인정보 자동 수집 장치(쿠키)의 설치·운영 및 거부에 관한 사항" 칸이 있다(카카오, 서울시 누리집, 한국보건사회연구원). 서울시 누리집은 접속 로그, 쿠키, 접속 IP 정보를 처리 항목으로 적는다. 한국보건사회연구원은 Google Analytics 쿠키(`_ga`)를 쿠키 정책에 적는다.
- 쿠키 같은 기술로 행태정보를 모아 맞춤형 광고에 쓰면, 기술의 개념·목적·수집 방법·거부 방법을 처리방침에 적어야 한다(개인정보 보호법 제30조 제1항 제7호). 다른 회사가 우리 사이트에서 행태정보를 모으게 하면 그 회사와 도구도 적는다. B를 고르면 이 부분을 확인한다.
- 그래서 A여도 처리방침(인계 문서 1의 6번 표 10번 항목)에 우리가 쓰는 쿠키(`SESSION`, `XSRF-TOKEN`)와 접속 로그(IP)를 적는다 [확인 필요: 처리방침을 쓸 때 법조문 원문과 개인정보위 작성지침으로].
### 3-3 좋아요(v2)는 로그인을 요구한다 [잠정: v2]
 
- 좋아요는 한 사람이 한 번 누르고, 취소할 수 있어야 한다. 사람마다 세는 일이다.
- 로그인하지 않은 좋아요를 방문자 쿠키로 세면, 쿠키를 지우고 다시 누를 수 있다.
- board에서도 좋아요는 회원만 눌렀다(`post_like`의 게시글 + 회원 중복 불가).
## 결정 4: 가입할 때 인증을 끝낸다 (나, 정현 11/7)
 
ADR-0007은 가입 흐름(인증 전에 무엇을 할 수 있는지)을 설계 주간으로 넘겼고, "미인증 계정은 로그인은 되고 라이브러리·드롭만 막는다"고 정했다(4-5). 정현이 "가입할 때 인증을 받게 할 수는 없나"를 물었다.
 
```
가. 링크 먼저 가입 (ADR-0007이 그린 모양)
   이메일·비밀번호 입력 → 계정 생김(인증 전) → 메일의 링크 누름 → 인증 마침
   → "인증 전 회원"이 존재한다
 
나. 코드 먼저 가입 (선택)
   이메일 입력 → 메일로 6자리 코드 → 코드 입력 → 비밀번호·닉네임 입력 → 계정 생김(인증 마침)
   → "인증 전 회원"이 없다
 
다. 링크 먼저 + 인증 전 로그인 금지 (Supabase 기본값)
   계정은 생기지만 링크를 누르기 전에는 로그인 못 함
```
 
- 나를 골랐으므로 ADR-0007 4-5의 미인증 규칙(로그인은 되고 라이브러리·드롭만 막음, 403 코드, 로그인한 화면에서 인증 메일 다시 보내기)은 쓰일 일이 없다. 규칙은 "로그인했으면 확인된 회원"으로 단순해진다. 승인한 ADR-0007의 본문은 고치지 않고, 이 ADR이 그 상태가 생기지 않게 한다.
  - 뒤에 "이메일 바꾸기" 기능을 넣으면 새 주소도 같은 코드 방식으로 확인한 뒤에 바꾼다(확인 전 주소가 생기지 않게) [잠정].
- 계정 캐내기를 막는 규칙(ADR-0007 3-3)은 그대로 지킨다. 어떤 이메일을 넣어도 "코드를 보냈습니다"로 답하고, 이미 가입된 주소면 코드 대신 "이미 가입되어 있습니다" 메일을 보낸다.
- 감수: 코드는 맞힐 때까지 넣어 볼 수 있으므로 만료 시간과 시도 횟수 제한이 필요하다(11번). 코드와 이메일의 짝을 잠깐 저장해야 한다(예: Redis에 짧은 수명. 세션은 쓰지 않는다) [잠정: 설계 주간]. 메일을 확인해야 가입이 끝나므로 가입 중간에 떠나는 사람이 생길 수 있다.
소셜 가입(붙일 때):
- 카카오·구글 로그인은 공급자가 그 계정을 확인한 것으로 보고, 우리 쪽 이메일 인증을 따로 하지 않는다. 소셜 회원은 처음부터 "확인된 회원"이다.
- 회원은 이메일이 아니라 공급자 회원번호로 구별한다(ADR-0007 4-1). 그래서 카카오가 이메일을 주지 않아도 가입된다.
- 공급자가 준 이메일을 쓸 때는(예: 알림 메일) 구글의 `email_verified` 값처럼 공급자가 확인했다고 표시한 것만 믿는다. 이메일이 같다고 계정을 합치지 않는 규칙(ADR-0007 4-1)은 그대로다.
- [확인 필요: 소셜을 붙일 때] 카카오 계정을 만들 때 어떤 확인(이메일·전화번호)을 거치는지.
- "계정당 1개"(ADR-0007 4-5)는 그대로 계정 단위다. 카카오 계정 하나, 구글 계정 하나, 이메일 계정 하나로 한 사람이 셋을 가질 수 있다(ADR-0007이 이미 감수함).

## 정현의 판단 (대화에서 옮김)
 
> 정현의 말을 대화에서 옮겼다. 읽기 쉽게 조금 다듬었지만 뜻은 바꾸지 않았고, 정현이 말하지 않은 이유는 넣지 않았다.
 
- **질문** (11/7 밤, ADR-0007 승인 전): "우리 템플릿을 다운로드 받을 때 로그인이 굳이 필요할까? 로그인 없이도 우리 템플릿을 다운받을 수 있도록 할 수 있을까? 다만 로그인을 안 했을 때는 라이브러리나 이런 건 못 쓰겠지만, 로그인을 안 해도 템플릿은 다운로드 받을 수 있게. 드롭은 그래도 로그인한 상태에서만 다운받을 수 있게 해야 할까? 큰 이슈 같아서 ADR 승인 전에 말씀드려 봐요."
  - 멘토의 답(요약): 일반 템플릿은 로그인 없이, 라이브러리와 드롭은 로그인(B)을 추천했다. 기준은 "사람마다 세어야 하는 것에만 로그인"이다. Slidesgo(다운로드를 사람마다 셈, 가입 필요)와 SlidesCarnival(가입 없음)을 예로 들었다.
- **결정 1·2** (11/7 밤): "좋습니다. 여기서 다운로드를 하면 원래 알아서 라이브러리로 가게끔 하면 좋을 것 같은데요. 다만 로그인을 안 한 상태라면 갈 라이브러리가 없으니까 못 가게끔요."
- **결정 3의 질문** (11/7 밤): "그러면 로그인 안 한 사용자의 세션은 어떻게 할까요? 로그인을 안 한 사용자의 행동에서도 우리가 수집할 데이터가 있을까요? 좋아요 행위라던지, 등등이요."
  - 멘토의 답(요약): 세션은 ADR-0007대로 만들지 않는다. 데이터는 템플릿별 숫자만 모으는 A를 추천했다. 좋아요는 사람마다 세는 일이라 로그인을 요구한다.
- **결정 3** (11/7 밤): "좋아요는 알겠습니다. 그게 맞는 것 같네요. 3은 A로 갑시다."
- **결정 4의 질문** (11/7 밤): "회원가입을 할 때 인증을 그냥 받게끔 할 수 없나요? 여기서 말하는 인증이 메일 인증이 맞죠? 그렇다면 나중에 소셜로 가입하는 분들의 인증은 어떻게 하죠?"
  - 멘토의 답(요약): 메일 인증이 맞다. 코드를 넣어야 가입이 끝나는 방식(나)을 추천했다. 소셜 가입은 공급자가 확인한 계정으로 본다.
- **결정 4와 승인** (11/7 밤): "나안 좋습니다. 저도 이렇게 생각했습니다. 0008도 승인합니다."
