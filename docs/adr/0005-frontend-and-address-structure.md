# ADR-0005: 프론트는 React SPA로 만들고, 화면과 API는 같은 주소 아래 두며, 운영 화면은 같은 앱의 별도 구역으로 둔다
 
- 날짜: 2026-11-05
- 상태: 승인 (2026-11-05, 정현)
- 작성: 초안은 멘토 AI, 검토·승인은 정현
> **쉽게 말하면**
> 1. 프론트는 React + TypeScript + Vite로 만든다. 빌드하면 HTML·JS·CSS 파일 묶음이 나오고, Nginx가 이 파일을 그대로 내준다. 운영 서버에 프론트용 서버 프로그램(Node)은 없다.
> 2. 사이트 주소는 하나다. 주소가 `/api`로 시작하면 Nginx가 Spring에 넘기고, 나머지는 화면 파일을 준다. 브라우저는 한 곳하고만 이야기하므로 CORS 설정이 필요 없고, 로그인 쿠키도 가장 단순하게 쓸 수 있다.
> 3. 운영 화면은 다른 사이트로 떼지 않고 같은 앱 안의 별도 구역으로 둔다. 운영 화면을 지키는 것은 주소를 숨기는 일이 아니라 서버의 권한 검사다. 공개 저장소라서 주소는 어차피 보인다.
> 4. 카카오톡 링크 미리보기는 v1에서 사이트 공통 카드 하나로 나온다. 템플릿마다 다른 카드는 v2 후보다. 그때는 서버가 HTML에 og 태그를 채워서 보낸다.
 
## 맥락
 
- 프론트는 프론트 AI가 React로 쓰고, 백엔드는 정현이 Spring으로 쓴다(킥오프 ①).
  - 킥오프 ①의 멘토 초안은 React + TypeScript + Vite(SPA)였다.
  - Next.js는 Node 서버가 하나 더 생기므로, 서버 렌더링이 꼭 필요할 때만 보기로 했다.
- 화면은 공개 / 제작자 / 운영 셋이다(인계 문서 4번).
  - 운영 화면은 v1에서 템플릿 공개·내리기, 드롭 개설, 회원 관리를 한다.
  - 운영 화면 보호는 v1, 운영 작업 기록(감사 로그)은 v2다(인계 문서 6번).
- 저장소는 공개한다. 프론트 코드, 화면 주소, API 주소는 누구나 볼 수 있다.
- 운영 서버는 NCP 한 대이고, 앞에 Nginx를 둔다(세부는 기획 2의 7번).
- 링크 미리보기는 HTML만 읽는다.
  - 카카오톡에 링크를 보내면, 카카오 서버가 그 주소의 HTML을 가져가서 og 태그를 읽는다.
  - 화면이 뜬 뒤에 스크립트가 바꾼 og 태그는 읽지 못한다. 카카오 개발자 포럼의 점검 목록이 "og 태그를 프론트 스크립트로 넣으면 curl로 다시 확인하라"고 안내한다. React에서 og 태그를 바꿨더니 미리보기에 기본값만 나왔다는 질문도 있다.
- 실제 사용자와 홍보 계획이 없다(기획 1). 검색 노출은 중요도가 낮다. 링크 미리보기는 정현이 링크를 공유할 때(포트폴리오, 지인) 쓰인다.
- 이 결정이 5번(로그인·쿠키·CORS·CSRF)의 바탕이 된다.
## 결정 1: 프론트는 React + TypeScript + Vite로 만든 SPA
 
- 빌드 결과는 정적 파일(HTML·JS·CSS·이미지)이다. 운영에서는 Nginx가 준다.
  - 운영 서버에 Node 프로세스는 없다. Node 24는 빌드할 때만 쓴다(ADR-0003).
- 주소는 경로 방식(`/templates/12`)으로 한다. `#` 방식(`/#/templates/12`)은 쓰지 않는다.
  - 브라우저와 봇은 `#` 뒤를 서버에 보내지 않는다. 그러면 서버는 어떤 템플릿 페이지인지 알 수 없고, 결정 4의 v2(템플릿별 og)도 할 수 없다.
- 라이브러리(라우터, 서버 데이터 관리, UI 도구)는 프론트 AI가 첫 계획에서 이유와 함께 제안하고, 정현이 승인한다.
  - 기준: 널리 쓰임, 유지보수가 활발함, 라이선스 문제 없음
  - API 호출에는 계약에서 만든 타입만 쓴다(4번).
- 버전은 환경 구축 채팅에서 최신 안정판을 웹 검색으로 확인하고 고정한다.
버린 선택지:
- **Next.js(서버 렌더링)**
  - 장점: 페이지마다 서버에서 HTML을 완성해 보내므로, 템플릿별 미리보기와 검색 노출에 유리하다.
  - 버린 이유: 운영 서버에 Node 서버가 하나 더 생긴다(메모리, 배포, 감시 대상). 로그인 흐름도 Spring과 Node 두 곳에 걸친다.
  - 이 프로젝트에서 서버 렌더링이 필요한 이유는 템플릿별 미리보기 하나다. 그건 결정 4의 더 작은 방법으로 풀 수 있다.
- **빌드할 때 페이지 HTML을 미리 만들기(프리렌더)**: 템플릿은 운영 중에 추가·수정된다. 바뀔 때마다 프론트를 다시 빌드해야 한다.
## 결정 2: 화면과 API를 같은 주소(같은 출처) 아래 둔다
 
운영:
 
```
https://<도메인>/            → Nginx가 받음
  ├─ /api/...                → Spring
  ├─ 소셜 로그인 주소          → Spring (정확한 경로는 5번)
  └─ 그 밖의 모든 주소          → 화면 파일 (없는 파일이면 index.html)
```
 
개발(맥):
 
```
http://localhost:5173/       → Vite 개발 서버가 받음
  ├─ /api/...                → localhost:8080 (Spring, 또는 4번의 가짜 서버)
  └─ 그 밖                    → 화면
```
 
- 개발에서도 브라우저가 보는 주소는 하나다(Vite의 프록시 기능). 개발과 운영이 같은 방식으로 동작하므로, "개발에선 됐는데 운영에선 CORS 에러" 같은 일이 생기지 않는다.
- Nginx는 위 목록에 있는 경로만 Spring에 넘긴다. Spring의 내부 주소(actuator의 헬스체크·메트릭 등)는 밖에서 들어올 수 없게 한다(7번, 10번).
- `/api/` 아래의 없는 주소에는 Spring이 404 ProblemDetail로 답해야 한다.
  - Nginx 설정이 잘못되면 `index.html`이 200으로 나간다. 그러면 프론트가 HTML을 JSON으로 읽다가 깨진다.
  - board의 "/error 위장"과 같은 종류의 함정이다. 첫 배포 때 curl로 확인한다.
- 소셜 로그인 주소도 같은 함정이 있다. 로그인 뒤 돌아오는 주소가 화면 파일 쪽으로 빠지면 로그인이 끝나지 않는다. 경로 목록은 5번에서 정하고 Nginx 규칙에 넣는다.
선택지:
 
| | A. 같은 출처 (선택) | B. API만 하위 도메인 | C. 서로 다른 도메인 |
| --- | --- | --- | --- |
| 예 | `example.com` + `example.com/api` | `example.com` + `api.example.com` | `example.com` + `example-api.com` |
| 브라우저 판정 | 같은 출처 | 다른 출처, 같은 사이트 | 다른 출처, 다른 사이트 |
| CORS 설정 | 필요 없음 | 필요(허락할 출처, 쿠키 허락, 사전 확인 요청) | 필요 |
| 로그인 쿠키 | 가장 단순 | 설정이 늘지만 동작함 | 제3자 쿠키가 되어 사파리 등에서 막힘 |
| 도메인·인증서 | 하나 | 하나(하위 도메인 포함) | 둘 |
| 어울리는 경우 | 웹 화면 하나가 API를 쓸 때 | 모바일 앱·외부 개발자도 API를 쓸 때 | 피한다 |
 
이유:
1. 이 API를 쓰는 곳은 우리 웹 화면 하나다. B의 장점(여러 클라이언트, API만 따로 확장·캐시)이 지금은 필요 없다.
2. CORS와 쿠키 설정이 없으면 틀릴 곳이 줄어든다. 5번에서 로그인을 쿠키로 하면 같은 출처가 가장 단순하다.
3. 도메인과 인증서가 하나다. 학생 팩의 무료 도메인 하나로 충분하다.
버린 선택지:
- **B. API만 하위 도메인**: 실무에서 흔한 구조다. 모바일 앱이나 외부 공개 API가 생기면 다시 본다. 지금 고르면 CORS·쿠키 설정만 늘고 얻는 것이 없다.
- **C. 서로 다른 도메인**: 로그인 쿠키가 제3자 쿠키가 된다. 사파리는 제3자 쿠키를 기본으로 막는다. 크롬은 2025년 4월에 제3자 쿠키를 계속 허용하기로 했지만, 사용자 설정에 따라 막힐 수 있다.
감수하는 것:
- 화면과 API가 같은 Nginx를 지나므로, Nginx 경로 규칙이 둘 사이의 약속이 된다. 규칙은 `docker/`의 설정 파일 하나에 두고, 바뀌면 PR에서 확인한다.
- CORS를 직접 겪을 일이 줄어든다. 면접에서는 "왜 CORS가 필요 없는 구조를 골랐나"로 답한다(이 ADR이 근거).
## 결정 3: 운영 화면은 같은 앱 안의 별도 구역으로 둔다
 
- 화면 셋은 한 SPA 안에서 주소 앞부분으로 나눈다. 예: 공개 `/`, 제작자 `/studio`, 운영 `/ops`. 이름은 설계 주간에 정한다.
- 제작자·운영 구역의 코드는 따로 나눠 싣는다(코드 분할).
  - 공개 화면만 보는 사람은 운영 화면 코드를 내려받지 않는다.
  - 보안 장치가 아니라 공개 화면을 가볍게 하려는 것이다.
- **진짜 문은 서버다.**
  - 운영 API는 주소 앞부분을 따로 둔다(이름은 4번).
  - Spring Security가 운영 권한이 없는 요청을 403으로 막는다.
  - 프론트에서 구역을 막는 것은 화면 안내일 뿐이다. 드롭 카운트다운이 표시일 뿐인 것과 같다.
- 운영 계정의 로그인 방식과 추가 보호(2단계 인증, 접속 IP 제한 등)는 5번에서 정한다.
- 제작자·운영 구역은 검색에 싣지 않는다(결정 4).
선택지:
- A. 같은 앱의 별도 구역 (선택)
- B. 운영 전용 앱을 따로 만들어 하위 도메인(`admin.example.com`)에 둔다
- C. 운영 화면을 Spring의 서버 렌더링(Thymeleaf)으로 만든다
- D. 운영 주소를 숨긴다
이유:
1. v1의 운영 화면은 작다(템플릿 공개·내리기, 드롭 개설, 회원 관리). 앱을 둘로 나누면 빌드·배포·로그인·계약 타입이 두 벌이 된다.
2. 보호의 핵심은 서버의 권한 검사다. 앱을 나눠도 보안이 더 강해지지 않는다.
3. 나중에 옮기기 쉽다. 운영 화면이 커지거나(v2의 검수·신고 처리) 다른 사람이 운영을 맡게 되면 B로 옮길 수 있다. 서버의 운영 API가 이미 따로 나뉘어 있기 때문이다.
버린 선택지:
- **B. 운영 전용 앱**: 운영 쪽 로그인을 공개 화면과 완전히 떼는 장점이 있다. 큰 회사에서는 운영 화면(백오피스)을 따로 된 앱으로 두고 회사 안 네트워크에서만 여는 경우가 흔하다. 하지만 v1 규모에서는 관리할 것만 두 배가 된다. 필요해지면 다시 본다.
- **C. Spring 서버 렌더링**: 백엔드에 화면 기술이 하나 더 생기고, 운영 화면만 로그인·CSRF 방식이 달라진다. 정현이 화면을 직접 쓰게 되어 "프론트는 AI" 역할 분담과도 어긋난다.
- **D. 주소 숨기기**: 공개 저장소라서 숨길 수 없다. 숨기는 것은 보호가 아니다.
공개 저장소와의 관계:
- 운영 화면 주소와 운영 API 주소는 저장소에 보인다. 이것은 괜찮다. 문은 서버의 권한 검사가 지킨다.
- 공개하면 안 되는 것은 운영 서버 안 관리 도구(Grafana, DB, actuator)의 주소와 포트다. 이것들은 공개 도메인으로 아예 열지 않는다(7번, 10번, 기획 3의 공개 범위).
## 결정 4: 링크 미리보기와 검색 노출
 
v1:
- `index.html`에 사이트 공통 og 태그(사이트 이름, 소개, 대표 이미지)를 넣는다. 어떤 주소를 공유해도 같은 카드가 나온다.
  - 카카오가 미리보기로 쓸 수 있는 이미지는 JPG·PNG다.
- 템플릿 상세 주소의 모양(예: `/templates/{id}`)은 설계 주간에 화면 목록과 함께 정하고, 그 뒤로 바꾸지 않는다. 주소는 한 번 퍼지면 바꾸기 어렵다.
- `robots.txt`와 noindex로 제작자·운영·내 라이브러리 구역을 검색에서 뺀다.
v2 후보 [잠정]:
- 템플릿 상세 주소에서만 서버가 og 태그를 채워 보낸다. 템플릿 주소를 카톡에 붙이면 그 템플릿의 썸네일과 제목이 카드로 뜬다.
  - 예: Nginx가 `/templates/{id}`를 Spring에 넘긴다. Spring은 `index.html`의 og 자리에 그 템플릿의 제목·설명·썸네일을 넣어 돌려준다.
  - 사람에게도 같은 HTML이 가므로, 화면은 그대로 SPA로 뜬다.
- 템플릿 목록을 담은 `sitemap.xml`
- 세부 방식(봇에게만 줄지 모두에게 줄지, Spring이 `index.html`을 어떻게 읽을지)은 그때 정한다.
- 카카오는 미리보기를 캐시한다. og를 바꾸면 카카오 개발자 도구에서 캐시를 초기화해야 반영된다.
이유:
1. 실제 사용자와 홍보 계획이 없어서, v1에 템플릿별 미리보기가 꼭 필요하지는 않다. 포트폴리오 링크를 공유하는 데는 공통 카드로 충분하다.
2. 템플릿별 미리보기는 "SPA의 한계를 서버에서 메운" 문제 해결 이야기가 될 수 있어서 v2 후보로 남긴다.
## 결과
 
- **5번(로그인과 인증)의 전제**: 같은 출처라서 CORS 설정이 필요 없다.
  - 쿠키를 쓰면 `HttpOnly`, `Secure`, `SameSite`를 기본으로 하고, CSRF 대비가 따라온다.
  - 세션 vs JWT, 소셜 로그인 경로, 운영 계정 추가 보호는 5번에서 정한다.
- **4번(API 계약)**: 운영 API의 주소 앞부분 이름, 개발용 가짜 서버를 Vite 프록시 뒤에 둘지
- **7번(운영 구성)**
  - Nginx 경로 규칙, 정적 파일을 이미지에 싣는 방법, CDN 여부
  - 캐시 규칙: `index.html`은 캐시하지 않고, 이름에 해시가 붙은 JS·CSS는 오래 캐시한다. 배포 뒤에 옛 화면이 남는 문제를 막는다.
- **10번(관측성)**: actuator·메트릭 주소를 공개 도메인에 열지 않는다.
